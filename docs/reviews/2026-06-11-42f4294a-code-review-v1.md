### Outcome

**Verdict:** Not approved

**Reasoning:** The shared resolver, dispatcher, report layout, and setup migration are largely well implemented and the package check passes, but the registered `/flow:doctor --fix` path does not use the effective-package model when choosing what to repair. That breaks a central requirement for trusted project overrides and can repair the wrong scope.

### Strengths

- The shared bare-node resolver is appropriately isolated in `packages/pi-flow-core/extensions/lib/effective-package.mjs`, uses only Node builtins, and covers npm spec parsing, aggregate-to-core delegation, trust checks, effective resolution, and path abbreviation in one importable module.
- The dispatcher in `packages/pi-flow-core/bin/pi-flow-dispatch.mjs` keeps semantic resolution in the shared module and falls back cleanly to the bootstrap user core when resolution/import fails.
- `packages/pi-flow-core/extensions/setup.ts` preserves the never-overwrite posture while migrating owned legacy symlinks and refreshing only recognized dispatcher copies.
- The new tests cover many important edge cases: npm string/object parsing, aggregate/direct identity normalization, trusted/untrusted project overrides, dispatcher target resolution, dispatcher staleness, inactive installs, strict mode, and setup migration.
- Verification run: `pnpm --filter @aphotic/pi-flow-core check` passed.

### Issues

#### Critical (Must Fix)

- **`packages/pi-flow-core/extensions/doctor.ts:1641`: Registered `--fix` ignores the effective package/scope**
  - **What:** The handler builds an effective diagnosis at lines 1609-1615, but the `--fix` branch does not use `diagnosis.effective`, `diagnosis.effectiveRoot`, or `diagnosis.effectiveScope`. Without `--source`, it resolves the target from `active` plus local declared/loaded roots only, so an npm project override can fall back to the executing user package. It then sets `effectiveTarget` from `resolveScope()` at lines 1659-1660 and chooses `agentsDir` from that value at lines 1668-1671. In the common case where `/flow:doctor` is running from the user install inside a trusted project override, this repairs user-scope agents to the user root and leaves stale project-scope agents untouched.
  - **Why it matters:** Scope-aware `--fix` is a core requirement of this change. Users with a trusted project override can get an OK/active effective model in the diagnosis, then have `--fix` mutate the wrong scope or report success without repairing the effective project agents. The lower-level `runDoctorFix` tests pass only because they inject `effectiveTarget: "project"` and the project agents directory directly; the registered command path does not derive those values the same way.
  - **Recommendation:** In the handler, derive the default fix target and repair scope from the effective model, not from the executing command scope. For default `--fix`, use `diagnosis.effective`/`diagnosis.effectiveScope` as the target/scope when an effective root is resolved, and choose the project vs user agents directory from that. Keep explicit `--source` behavior, but still make the repaired agent scope explicit and covered. Add a handler-level test for a user-installed doctor running in a trusted project npm override where project agents are stale and user agents are already correct.

_None._

#### Minor (Nice to Have)

  - **Why it matters:** This is user-facing metadata and now undersells a meaningful side effect of `/flow:setup`.
  - **Recommendation:** Update the description to mention agent links plus the user helper dispatcher setup.
