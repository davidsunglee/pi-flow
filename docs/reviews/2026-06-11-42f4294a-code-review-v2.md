**Reasoning:** The implementation is well structured and the full `pnpm --filter @aphotic/pi-flow-core check` suite passes, but there is a blocking scope-model regression: user agent links can still be reported as `stale-skew` when the user package is a supported settings-declared install and a trusted project override is active.

### Strengths

- The new shared resolver is a clean architecture boundary (`packages/pi-flow-core/extensions/lib/effective-package.mjs:1`): it keeps bare-node-compatible resolution, npm spec parsing, trust checks, effective-root selection, and path abbreviation in one module with TypeScript declarations.
- The dispatcher keeps launcher-specific bootstrap knowledge separate from semantic resolution (`packages/pi-flow-core/bin/pi-flow-dispatch.mjs:35`), and its fallback path is defensive when the shared module is absent or malformed.
- Setup preserves the never-overwrite posture while adding the required dispatcher migration path (`packages/pi-flow-core/extensions/setup.ts:283`), including legacy managed symlink migration and foreign-file preservation.
- Test coverage is broad and relevant: the package check passed with the new effective-package, dispatcher, doctor, setup, and helper suites.

### Issues

#### Critical (Must Fix)

_None._

#### Important (Should Fix)

- **packages/pi-flow-core/extensions/doctor.ts:643: User-agent comparison ignores settings-declared user packages under project overrides**
  - **What:** When `effectiveScope === "project"`, `buildDiagnosis` derives `userRoot` only from the fixed npm candidate paths via `resolveFirstCoreRoot(userInstallCandidates.map(...))`, then falls back to the project `effectiveRoot`. It does not resolve the user/global package declared in `~/.pi/agent/settings.json`, even though `resolveEffectiveCoreRoot` explicitly supports those user settings entries, including local/path installs outside `~/.pi/agent/npm`.
  - **Why it matters:** A supported user install layout can be falsely classified as `stale-skew`. In a trusted project override, user agents that correctly point to the user/global package compare against the project root instead of the actual user root, so `/flow:doctor` reports skew even though the surface is scope-aligned. That contradicts the main requirement that overridden-but-inactive inventory read as neutral rather than skew.
  - **Recommendation:** Add or reuse a shared resolver that resolves the user/global root independently of project overrides, including `~/.pi/agent/settings.json` entries, and use that for `userRoot` and related inactive-root recognition. Add a doctor regression test with a user settings-declared local package plus a trusted project override where user agents remain non-skew.

#### Minor (Nice to Have)

- **packages/pi-flow-core/extensions/doctor.ts:1531: Fix guidance only recognizes local package declarations**
  - **What:** `declaredSpecsNamingTarget` skips every non-local declaration, so an npm package entry that already names the selected target still produces the "target is not named in .pi/settings.json packages" guidance.
  - **Why it matters:** The repair behavior is safe, but the post-fix advice can be wrong for the npm declarations this change now resolves and reports.
  - **Recommendation:** Resolve npm declarations here with the same shared `resolveSpecToCoreRoot` path used by diagnosis, and count matching npm specs as naming the target.
- **packages/pi-flow-core/extensions/setup.ts:328: Dispatcher refresh paths do not repair execute bits**
  - **What:** Existing dispatcher files are skipped when bytes match, and stale dispatcher files are refreshed with `fs.writeFile(..., { mode: 0o755 })`; on existing files, the mode option does not reliably reset permissions.
  - **Why it matters:** If an owned dispatcher file loses its executable bit, setup or doctor can leave `~/.pi/agent/bin/pi-flow` non-executable even though the content is correct.
  - **Recommendation:** Check the mode for owned dispatcher files and call `chmod(0o755)` after create, refresh, and skip-as-owned paths when needed.

### Recommendations

- Add a focused integration test for the false-skew scenario above, because the shared resolver already has user-settings coverage but doctor does not exercise that path under a project override.
