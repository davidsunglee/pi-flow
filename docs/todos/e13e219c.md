## Problem

When running a pi-flow skill after installing pi-flow as a Git package through Pi, the first invocation of the helper runner often fails with:

```text
/bin/bash: pi-flow: command not found
```

The skill instructions invoke helpers as `pi-flow helper ...`, but Pi's Git package install loads the skills from the cloned package without exposing the package's npm `bin` entry on the shell `PATH`.

## Current evidence

- Skills are loaded from the Git-installed package under `~/.pi/agent/git/github.com/davidsunglee/pi-flow/...`.
- The runner exists and works when invoked directly, e.g.:
  `node ~/.pi/agent/git/github.com/davidsunglee/pi-flow/packages/pi-flow-core/bin/pi-flow.mjs ...`
- Bare `pi-flow` is not currently resolvable from the shell used by Pi tools/subagents.
- Pi prepends `~/.pi/agent/bin` to PATH, but pi-flow does not currently install/link a wrapper there.

## Likely direction

Prefer the package-level fix: make the installed pi-flow package bootstrap or expose a stable `pi-flow` wrapper on PATH, likely under `~/.pi/agent/bin`, so skill instructions can keep using `pi-flow helper ...`.

## Alternatives to evaluate during refinement

1. Package bootstrap/wrapper in `~/.pi/agent/bin/pi-flow` pointing to the installed runner.
2. Change skill instructions to resolve a helper runner once and use either bare `pi-flow` or `node <package-root>/bin/pi-flow.mjs`.
3. Ask/extend Pi package manager behavior so package `bin` entries from Git/npm Pi packages are exposed automatically.

## Acceptance criteria draft

- After installing pi-flow via `pi install git:...`, `command -v pi-flow` succeeds inside Pi bash/tool execution contexts.
- First helper call in `/generate-plan`, `/execute-plan`, and other pi-flow skills no longer fails with `command not found`.
- The solution is robust across Git installs and local development installs.
- The implementation avoids hard-coded user-specific paths.

## Related issue: bundled agents are not discoverable, causing subagents not to auto-exit

During an `execute-plan` run, Pi-backed subagents were not auto-exiting; the workflow only advanced after manually closing their panes.

Likely same class of packaging/bootstrap problem as the missing `pi-flow` CLI:

- `subagents_list` returned `No subagent definitions found.`
- `execute-plan` dispatches tasks with agents like `coder`, `verifier`, and `test-runner`.
- Those agent definitions exist in `packages/pi-flow-core/agents/*.md` and declare `auto-exit: true`.
- But `pi-interactive-subagent` searches project/global agent dirs such as `.pi/agents/` and `~/.pi/agent/agents/`; the pi-flow bundled agent files are not currently installed or symlinked there.
- If the launcher cannot load the agent definition, it misses `auto-exit: true`, so pane-backed Pi subagents behave as interactive/default sessions unless the model explicitly calls `subagent_done`.

Possible workaround:

```bash
mkdir -p ~/.pi/agent/agents
ln -sf ~/.pi/agent/git/github.com/davidsunglee/pi-flow/packages/pi-flow-core/agents/*.md ~/.pi/agent/agents/
```

Refinement should decide whether the package-level bootstrap should also expose bundled agent definitions, not just the `pi-flow` helper runner. Candidate solutions:

1. pi-flow install/bootstrap creates or updates symlinks for `agents/*.md` in a discoverable agent directory.
2. pi-flow ships/installs a package-aware agent discovery mechanism for `pi-interactive-subagent`.
3. Pi package manager grows first-class support for package-provided agent definitions, analogous to skills/prompts/themes.

Additional acceptance criteria draft:

- After installing pi-flow via Git/package install, `subagents_list` shows the bundled pi-flow agents (`coder`, `verifier`, `test-runner`, etc.).
- `execute-plan` subagents receive their intended frontmatter defaults, especially `auto-exit: true`.
- Execute-plan no longer requires manually closing subagent panes for the workflow to advance.
- The solution handles updates cleanly and avoids stale symlinks to old package paths.
