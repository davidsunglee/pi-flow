## Goal

Refactor the artifact-driven workflow terminology and identifiers from `TODO-<id>` to `IDEA-<id>` after the initial `pi-flow` extraction.

## Motivation

`todo` / `TODO` collides with common LLM planning/checklist tools and plugins. The workflow's durable user-intent artifacts should use Flow-specific idea terminology instead.

## Scope

- Rename the user-facing and LLM-facing file-backed todo tool surface to idea terminology.
- Migrate identifier parsing and provenance from `TODO-<8-hex>` to `IDEA-<8-hex>`.
- Audit and update workflow skills, prompts, helper scripts, parser tests, README docs, and examples that mention or parse `TODO-<id>`.
- Decide and implement backward compatibility for existing `TODO-<id>` artifacts and provenance lines.
- Provide migration guidance or tooling for existing `docs/todos/*.md` data if storage paths or metadata names change.

## Acceptance criteria

- Workflow entry points accept `IDEA-<id>` as the canonical durable artifact identifier.
- Specs/plans/briefs/reviews use `IDEA-<id>` provenance in newly generated artifacts.
- Existing `TODO-<id>` artifacts remain usable through an explicit compatibility path or documented migration.
- Tests cover canonical IDEA parsing and legacy TODO compatibility/failure behavior.
- Documentation explains the terminology change and how it avoids clashes with generic todo/checklist tools.

## Notes

Keep this separate from the initial `pi-flow` package extraction. The initial extraction may expose `/flow:idea` and an `idea` tool while retaining legacy `TODO-<id>` artifact compatibility.

Additional note: when implementing the future `idea` extension/tool surface, fold the current `env.ts` behavior directly into that extension instead of requiring users to list a separate runtime extension. In particular, the idea extension should own default storage-path resolution from the active git root, preserve explicit user overrides, and provide any necessary legacy `PI_TODO_PATH` compatibility or migration path if the canonical storage/env name changes.

## Additional scope: remove dependency on legacy `todo` extension

The current `pi-flow` package exposes `/flow:idea` and the `idea` tool, but some workflow skill instructions still assume a separate legacy `todo` tool/extension is installed. The IDEA migration should explicitly remove that runtime dependency.

Concrete points to cover:

- `generate-plan` must stop reading `TODO-<id>` input via the legacy `todo` tool. It should use the new `idea` surface or direct `docs/todos/<id>.md` artifact reads during the compatibility period.
- `execute-plan` must stop closing linked todos via the legacy `todo` tool. It should update the backing artifact directly or use the new `idea` tool/update path.
- Any other skill, prompt, helper, or test that requires a `todo` tool should be migrated or given a compatibility fallback that does not require the old extension.
- Add tests proving the packaged workflows can handle idea/TODO-compatible artifacts when no legacy `todo` command/tool is registered.
- Documentation should state when users can remove the old todos extension from their Pi installation and what compatibility remains for existing `TODO-<id>` artifacts.

Acceptance-criteria additions:

- A repo-wide audit finds no workflow instruction that requires the legacy `todo` tool/extension for normal pi-flow operation.
- `generate-plan` and `execute-plan` tests cover TODO/IDEA artifact handling without a registered `todo` tool.
- The old todos extension is documented as optional/removable after the migration, subject only to legacy user workflows outside pi-flow.
