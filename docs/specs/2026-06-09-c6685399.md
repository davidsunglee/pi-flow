# Make the Flow idea-refine prompt resolve open questions

Source: IDEA-c6685399

## Goal

Reword the Flow idea-refinement prompt so it treats an existing idea's `## Open Questions` as clarification targets to resolve *during* the refinement conversation, rather than a passive catch-all that gets carried forward into the rewritten artifact. After refinement, the canonical idea shape is preserved (including a `## Open Questions` section), but that final section should read `None.` whenever every material question has been answered, and otherwise hold only genuinely-deferred items. The change is confined to the packaged Flow refine prompt plus prompt-text regression coverage; the generic `pi-ideas` package is untouched.

## Context

The Flow refine flow works like this: in the `/flow:ideas` browser, choosing the **refine** action (or `Ctrl+Shift+R`) prefills the editor with the resolved `refinePrompt`, substituting `${idea}` → `IDEA-<id>` (`packages/pi-ideas/extensions/idea.ts`, `substituteIdea` in `config.ts`). The model then reads the existing idea and rewrites it via the `idea` tool's `update` action. The refine prompt is the editor seed, not a constraint the runtime enforces — so this work is entirely about the prompt's wording.

The in-use refine prompt is the **packaged override** at `packages/pi-flow-core/ideas.json` → `refinePrompt`, wired via `registerIdea(pi, { defaultConfigPath: ".../ideas.json" })` in `packages/pi-flow-core/extensions/commands.ts:11`. Config resolves packaged → global (`~/.pi/ideas.json`) → project (`.pi/ideas.json`), last-non-empty-wins (`resolveIdeasConfig`, `pickString` in `pi-ideas/extensions/config.ts`).

That packaged `refinePrompt` currently asks clarifying questions "whose answers would materially change the artifact," says not to rewrite before the user answers, then says: "Once the user has answered enough to draft the structured description, write it into the idea body using exactly these section headers in this order: `## Context` / `## Goal` / `## Scope` / `## Acceptance Sketch` / `## Open Questions`." It lists `## Open Questions` as a required output section but (a) never distinguishes conversation-time clarifying questions from the final written section, (b) never tells the model to inspect the existing idea's `## Open Questions` before rewriting, and (c) never establishes `None.` as the expected default. As a result, refining an existing idea can passively preserve answerable items in `## Open Questions` instead of asking targeted questions that resolve them.

The same canonical 5-section shape also appears in that file's `toolDescription` and `promptSnippet`, but those merely *describe* the shape (for the capture flow) and carry no refinement-behavior framing — out of scope here.

The generic `pi-ideas` package default (`config.ts` `DEFAULT_REFINE_PROMPT`) is deliberately **structure-neutral**: it never mentions the 5-section shape, because standalone `pi-ideas` (used without Flow) should not inherit Flow's rigid workflow structure. That neutrality is pinned by tests that assert on the *prompt/config text* — `config.test.ts:34-37` (resolved `refinePrompt`/`toolDescription`/`promptSnippet` strings) and `idea.test.ts:1413` / `idea.test.ts:2733` (tool description string; the editor-prefill text). None of these execute a model or inspect a generated idea body; they restrict the prompt, not the output.

Test landscape for placement: `pi-flow-core`'s only ideas-touching test is `commands.test.ts`, which exercises the `registerCommands` wiring and depends on *both* packages (it reaches `registerIdea`). No `pi-flow-core` test currently asserts on the packaged `refinePrompt` content, and an audit found no `pi-ideas`-only test misplaced in `pi-flow-core`.

## Requirements

- Reword `packages/pi-flow-core/ideas.json` → `refinePrompt` so it:
  - Distinguishes **clarifying questions asked during the refinement conversation** from **the final `## Open Questions` section written into the artifact** — the former is the active mechanism; the latter is a residue, not a goal.
  - Directs the model to **read the existing idea and inspect its current `## Open Questions` before rewriting**, treating each answerable item there as a clarification target to raise with the user.
  - Requires asking **targeted clarifying questions whose answers would materially change the refined idea**, preserving the existing behaviors already in the prompt (offer a recommendation per question; do not rewrite the body before the user answers).
  - Makes the **default outcome reduce or eliminate answerable open questions**: when all material questions have been answered, the final `## Open Questions` section is written as `None.`.
  - Reserves the final `## Open Questions` for **genuinely unresolved items, deferred decisions, or questions the user cannot answer yet** (legitimate handoffs to the downstream scout/spec stages).
  - Preserves the canonical section order: `## Context` / `## Goal` / `## Scope` / `## Acceptance Sketch` / `## Open Questions`, still written via the `idea` tool's `update` action.
- Add **prompt-text regression coverage in `pi-flow-core`** that asserts on the packaged `refinePrompt` *string* (resolved via `resolveIdeasConfig` against the packaged `ideas.json`, or read from the JSON directly): it must verify the new guidance is present — the conversation-questions vs. final-section distinction, the inspect-existing-`## Open Questions` instruction, and the `None.` default — and that the canonical section order is retained. The test fails if that guidance is removed.

## Constraints

- Scope the prompt change to the `pi-flow-core` packaged `refinePrompt` **only**. Do **not** modify the `pi-ideas` package default `DEFAULT_REFINE_PROMPT`, nor the packaged `toolDescription` / `promptSnippet`.
- Keep `## Open Questions` in the canonical idea shape — do not remove it.
- Regression coverage asserts on the **prompt/config text**, never on model-generated idea output (infeasible to assert in unit tests and undesirable to constrain). Mirror the existing prompt-text testing style.
- `pi-ideas` must remain independent: **no `pi-ideas` test may depend on `pi-flow-core`.** Any test depending on both packages lives in `pi-flow-core`. The new test therefore lives in `pi-flow-core` (it references the `pi-flow-core` `ideas.json` artifact).
- The reworded `refinePrompt` must remain a valid JSON string field and continue to use the `${idea}` placeholder.
- The guidance must degrade gracefully when the existing idea has no `## Open Questions` section yet (e.g., a freshly-created or sparse idea): "inspect existing open questions" must be a no-op in that case, not a failure or a blocker.

## Acceptance Criteria

- Given an existing idea with answerable open questions, the refine prompt directs the model to ask about those questions before rewriting the idea body.
- The prompt no longer frames a populated `## Open Questions` as a sufficient refinement outcome when targeted clarification is possible; it explicitly separates conversation-time clarifying questions from the final written section.
- The prompt instructs writing the final `## Open Questions` as `None.` when all material questions have been answered.
- The prompt preserves the canonical five section headers in order (`## Context`, `## Goal`, `## Scope`, `## Acceptance Sketch`, `## Open Questions`).
- A `pi-flow-core` regression test asserts on the packaged `refinePrompt` text (not model output) and fails if the refinement guidance regresses to treating `## Open Questions` as a passive catch-all (e.g., the distinction, the `None.` default, or the inspect-existing instruction is dropped).
- The `pi-ideas` package default and its structure-neutral tests are unchanged, and the `pi-ideas` test suite remains free of any dependency on `pi-flow-core`.

## Non-Goals

- Removing `## Open Questions` from the canonical idea shape.
- Changing the `pi-ideas` package default `DEFAULT_REFINE_PROMPT` or loosening its structure-neutrality tests.
- Changing the packaged `toolDescription` / `promptSnippet`.
- Asserting on, or otherwise constraining, the model's generated idea body in tests.
- Changing the create/capture flow, the config resolution/merge logic, the `/flow:ideas` TUI, or any workflow command.
- Modifying the idea storage format or the `idea` tool's actions.

## Open Questions
