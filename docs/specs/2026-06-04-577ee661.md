# Explicit Pi Coordinator Dispatch Configuration

Source: IDEA-577ee661

## Goal

Decouple coordinator runtime capability from provider-prefix model dispatch. Coordinator agents (`plan-refiner`, `code-refiner`) must run under the `pi` CLI because nested orchestration tools (`subagent_run_serial`) exist only there — but today their dispatch is resolved through the same tier→provider→`dispatch[prefix]` path leaf workers use, so a perfectly valid leaf-worker config (e.g. `anthropic → claude`, `openai-codex → codex`) leaves no tier resolving to `pi` and breaks coordinator dispatch entirely. Introduce a dedicated `coordinatorDispatch` section in `model-tiers.json` that names the coordinator model chain explicitly, with the Pi requirement hardcoded as a system invariant rather than user configuration, failing hard when the section is missing or unusable.

## Context

- `~/.pi/agent/model-tiers.json` (user-owned, never written by pi-flow) holds tier aliases (`capable`/`standard`/`cheap` + `crossProvider.*`) and a `dispatch` provider-prefix→CLI map. `packages/pi-flow-core/model-tiers.example.json` is the shipped template; `packages/pi-flow-core/docs/model-tier-setup.md` documents the schema and the four canonical leaf-worker error templates.
- `packages/pi-flow-core/skills/_shared/coordinator-dispatch.md` is the single authority for coordinator dispatch today: a fixed four-tier chain (`crossProvider.standard`, `standard`, `crossProvider.capable`, `capable`), resolving each tier through the leaf-worker primitives, silently skipping tiers whose resolved CLI is not `pi`, with two hard-stop error strings ("no tier resolves to a pi CLI" and "all pi-eligible tiers failed"). It is pure markdown procedure — no script implements the chain.
- `packages/pi-flow-core/skills/_shared/model-tier-resolution.md` defines the leaf-worker primitives (tier-path resolution, provider-prefix extraction, dispatch lookup) and four canonical byte-equal failure templates, mechanically implemented by `packages/pi-flow-core/skills/_shared/scripts/resolve-model-dispatch.py` and asserted byte-equal in `skills/_shared/scripts/tests/test_resolve_model_dispatch.py`. Its `## Coordinator dispatch` section cross-references the coordinator chain.
- Consumers of the coordinator procedure: `skills/refine-plan/SKILL.md` (Dispatch resolution under Step 5, dispatch at Step 8, Edge Cases) and `skills/refine-code/SKILL.md` (Dispatch resolution under Step 2, dispatch at Step 4, Edge Cases). Both defer to the shared file as single authority and currently describe it as "the four-tier chain". `refine-code/SKILL.md` Step 2 also lists `crossProvider.standard — coordinator model (pi-backed orchestration path)` in its role-to-tier mapping.
- `skills/_shared/orchestrator-verification-boundary.md` lists "Model-tier resolution via `resolve-model-dispatch.py` and the procedure in `skills/_shared/coordinator-dispatch.md`" as mechanical orchestrator surface.
- Worker subagents dispatched *inside* coordinators re-resolve through the normal leaf-worker path (per `coordinator-dispatch.md` `## Note on worker subagents`) and are unaffected by this change.

## Requirements

- **Schema**: `model-tiers.json` gains a `coordinatorDispatch` section — an object with a single required key `modelChain`, an ordered, non-empty array of exact model identifier strings:

  ```json
  "coordinatorDispatch": {
    "modelChain": ["openai-codex/gpt-5.4"]
  }
  ```

  - Entries are exact model names, not tier aliases. A single-entry chain is valid.
  - Entries are opaque: passed verbatim as the `model` parameter to `subagent_run_serial`. No provider-prefix extraction and no `dispatch[provider]` lookup occurs for coordinator dispatch.
  - There is no `cli` key. The Pi requirement is a system invariant: dispatch attempts hardcode `cli: "pi"`, and the rationale lives in `coordinator-dispatch.md`, not in user config.
  - Unknown extra keys inside `coordinatorDispatch` are ignored, consistent with existing schema handling elsewhere in the file.
- **Resolution semantics**: coordinator dispatch consults only `coordinatorDispatch`. Attempt each `modelChain` entry in order via `subagent_run_serial` with `cli: "pi"`; on dispatch failure (model unavailable, transport error, etc.) record the failure and advance; stop at the first success. No up-front availability probing.
- **Fail-hard validation** (no fallback to tier-based coordinator resolution under any failure):
  - File missing/unreadable → reuse existing canonical Template 1 (`~/.pi/agent/model-tiers.json missing or unreadable — cannot dispatch <agent>.`).
  - Missing `coordinatorDispatch` section → new canonical template, byte-equal:
    `model-tiers.json has no coordinatorDispatch section — cannot dispatch <agent>.`
  - `modelChain` missing, not an array, empty, or containing any non-string or empty entry → rejected wholesale (no entry-skipping) with new canonical template, byte-equal:
    `model-tiers.json coordinatorDispatch has no usable modelChain — cannot dispatch <agent>.`
  - All `modelChain` entries attempted and failed at dispatch time → new canonical template, byte-equal, emitted by the orchestrating procedure (not the script), substituting the last attempted model and its underlying error:
    `coordinator-dispatch: all coordinatorDispatch.modelChain models failed; last attempt: <model> via pi — <error>`
  - `<agent>` is substituted with the coordinator agent name (`plan-refiner`, `code-refiner`), matching existing template parametrization style.
- **Script-backed validation**: a `_shared` helper script (new script or a mode of `resolve-model-dispatch.py` — planner's choice) performs the config validation, emitting validated JSON (including the model chain and the hardcoded `pi` CLI) on stdout on success, and the corresponding canonical template on stderr with non-zero exit on failure. Python tests assert the success shape and each config-failure template byte-equal, in the style of `test_resolve_model_dispatch.py`.
- **Procedure rewrite**: `skills/_shared/coordinator-dispatch.md` replaces the four-tier chain, the skip-silently rule, and both old hard-stop strings with: invoke the validation helper → iterate `modelChain` in order → emit the exhaustion template verbatim if all entries fail. It remains the single authority for coordinator dispatch; the `## Note on worker subagents` contract (workers re-resolve via leaf-worker rules) is preserved.
- **Consumer updates**: `refine-plan/SKILL.md` and `refine-code/SKILL.md` dispatch-resolution references, Edge Cases entries, and role-to-tier mapping lines describing the coordinator tier are reconciled with the new procedure (still deferring to the shared file as single authority, no duplication). `model-tier-resolution.md`'s schema example and `## Coordinator dispatch` section, and `orchestrator-verification-boundary.md`'s mechanical-surface wording, are updated to match.
- **Leaf workers unchanged**: tier aliases, provider-prefix `dispatch` resolution, the four existing canonical templates, and all existing leaf-worker consumers behave exactly as before.
- **Examples and docs**: `model-tiers.example.json` and the schema blocks in `model-tier-setup.md` / `model-tier-resolution.md` show the motivating decoupled config — `dispatch: {"anthropic": "claude", "openai-codex": "codex"}` plus the `coordinatorDispatch` section — demonstrating that no `dispatch` entry needs to resolve to `pi`. `model-tier-setup.md` documents the new section, its canonical templates, and the rationale for why coordinator dispatch is separate from provider-prefix dispatch, and continues to insist users edit the copied example to match their CLI setup.

## Constraints

- Enforcement happens only at coordinator dispatch sites (`refine-plan`, `refine-code`). Leaf-only workflows (`scout`, `define-spec`, `generate-plan`, `execute-plan`, `requesting-code-review`, `fastlane`) never read `coordinatorDispatch` and must not fail when it is absent.
- `coordinatorDispatch` is global: one section applies to all coordinator agents uniformly.
- No silent fallback of any kind: a config that worked under the old four-tier chain but lacks `coordinatorDispatch` hard-fails with the missing-section template. No migration tooling; setup remains manual per `model-tier-setup.md`.
- Canonical templates are contract surface: docs, the procedure, the script, and tests must carry them byte-equal; consumers must not paraphrase or wrap them.
- pi-flow still never writes `~/.pi/agent/model-tiers.json`.
- No validation of `model-tiers.json` in the TS extension layer (`extensions/*.ts` do not read the file today and should not start).

## Approach

**Chosen approach:** Script-backed validation. A `_shared` helper script owns reading and validating `coordinatorDispatch`, emitting validated dispatch JSON on success or the byte-equal canonical template on stderr with non-zero exit. `coordinator-dispatch.md` shrinks to a thin procedure: invoke the helper, iterate `modelChain` via `subagent_run_serial` with hardcoded `cli: "pi"`, emit the exhaustion template if every entry fails. Config-validation templates get byte-equal Python tests alongside the existing `test_resolve_model_dispatch.py` suite. The runtime-exhaustion template necessarily remains LLM-emitted, since only the orchestrating session can attempt `subagent_run_serial`.

**Why this over alternatives:** The repo's direction of travel is mechanizing exactly this contract surface — `resolve-model-dispatch.py` already enforces the four leaf-worker templates byte-equal under test, and `orchestrator-verification-boundary.md` classifies tier resolution as mechanical orchestrator work. The idea's touchpoints explicitly call for tests covering guardrail strings and coordinator resolution behavior, which prompt-procedural validation structurally cannot provide.

**Considered and rejected:**

- Prompt-procedural validation (LLM reads and validates `coordinatorDispatch` inline per a rewritten markdown procedure) — zero new code, but canonical strings would be enforced only by prompt discipline and could never be byte-equal-tested.
- Required `coordinatorDispatch.cli: "pi"` field (the idea's original sketch) — a required field with exactly one legal value is dead configuration that carries no information and only adds a failure mode; the Pi requirement is a system property, and adding an optional `cli` key later (absent → `pi`) is non-breaking if a second orchestration-capable CLI ever appears, whereas removing a required key would break every config.

## Acceptance Criteria

- A `model-tiers.json` with `dispatch: {"anthropic": "claude", "openai-codex": "codex"}` (no entry resolving to `pi`) and a valid `coordinatorDispatch.modelChain` dispatches `plan-refiner` / `code-refiner` via `subagent_run_serial` with `cli: "pi"` and the first available `modelChain` model.
- Worker agents inside those coordinators still resolve through tier aliases plus provider-prefix `dispatch` and may run via `claude` or `codex`.
- With `coordinatorDispatch` absent, the validation helper exits non-zero emitting exactly `model-tiers.json has no coordinatorDispatch section — cannot dispatch <agent>.` (agent name substituted), and `refine-plan` / `refine-code` surface that error without dispatching.
- With `modelChain` missing, empty, non-array, or containing an empty/non-string entry, the helper exits non-zero emitting exactly the no-usable-modelChain template.
- New helper tests assert the success JSON shape and each config-failure template byte-equal; the existing `test_resolve_model_dispatch.py` assertions for the four leaf-worker templates still pass unmodified.
- `coordinator-dispatch.md` contains the helper-invocation procedure, the hardcoded-`pi` invariant with its rationale, and the verbatim exhaustion template; the four-tier chain, the skip-silently rule, and both old hard-stop strings appear nowhere in the package (grep-clean).
- `model-tiers.example.json` parses as valid JSON and shows the codex-routed `dispatch` map plus `coordinatorDispatch`; `model-tier-setup.md` documents the new section, its templates, and why coordinator dispatch is separate from provider-prefix dispatch.
- `refine-plan/SKILL.md` and `refine-code/SKILL.md` defer to the rewritten shared procedure without describing the old chain semantics.

## Non-Goals

- Per-agent coordinator overrides (different chains for `plan-refiner` vs `code-refiner`).
- Per-model metadata in `modelChain` entries (thinking level, execution policy) — entries stay exact strings.
- A `cli` key in `coordinatorDispatch` or support for non-Pi coordinator runtimes.
- Up-front model availability probing before dispatch attempts.
- Any change to leaf-worker tier/dispatch resolution semantics, the four existing canonical templates, or worker re-resolution inside coordinator prompts.
- Schema-wide enforcement: leaf-only workflows validating or requiring `coordinatorDispatch`.
- Migration tooling or automatic editing of user `model-tiers.json` files.
