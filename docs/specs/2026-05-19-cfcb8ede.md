# Extract Core Workflow Package Resources

Source: TODO-cfcb8ede
Scout brief: docs/briefs/TODO-cfcb8ede-brief.md

## Goal

Create the initial `pi-flow` monorepo and extract the reusable core workflow resources from `../pi-config` into package-loadable Pi packages. This first slice establishes the aggregate `pi-flow` package and the `pi-flow-core` package with workflow skills, bundled agent definitions, helper scripts, helper tests, and model-tier documentation/templates. It intentionally stops before implementing `/flow:*` commands, `/flow:setup`, `/flow:idea`, or the UX package.

## Context

`pi-flow` currently has a minimal repository shape with `README.md`, `.gitignore`, `docs/todos/`, `docs/briefs/`, and `docs/specs/`. The source material for the workflow lives in `../pi-config/agent/`.

Pi packages can expose extensions, skills, prompt templates, and themes via a `package.json` `pi` manifest or conventional directories. Pi package docs require `keywords: ["pi-package"]` for discoverability and describe dependency/bundling rules for packages whose resources are exposed through `node_modules/` paths. Pi packages do not currently expose arbitrary `agents/` directories as first-class subagent definitions, so this spec only bundles the agent definition files in `pi-flow-core`; making them discoverable through symlinks or companion-package support belongs to the later setup/commands spec.

The current source workflow includes these non-browser skills under `../pi-config/agent/skills/`: `scout`, `define-spec`, `fastlane`, `generate-plan`, `refine-plan`, `execute-plan`, `refine-code`, `requesting-code-review`, `receiving-code-review`, `commit`, `test-driven-development`, `systematic-debugging`, `verification-before-completion`, `using-git-worktrees`, and `finishing-a-development-branch`. It also includes shared markdown contracts, Python helper scripts, per-skill prompt templates, per-skill helper scripts, and Python tests.

The required workflow agent definitions under `../pi-config/agent/agents/` are `scout`, `spec-designer`, `planner`, `plan-reviewer`, `plan-refiner`, `coder`, `verifier`, `test-runner`, `code-reviewer`, and `code-refiner`. These files remain required source artifacts even though Pi cannot load them directly from a package manifest today.

The source skills currently contain many executable references to paths such as `agent/skills/_shared/scripts/...`, `agent/skills/<skill>/scripts/...`, and `~/.pi/agent/skills/...`. Those paths assume the old personal config checkout or a global skill installation layout and will not work in consumer projects after packaging. The extracted skills need readable, portable helper/template invocations that do not recreate the old `agent/` compatibility layout.

## Requirements

- Create a pnpm workspace rooted at `pi-flow` with root scripts for checking all workspace packages.
- Create an initial package layout with:
  - `packages/pi-flow-core/` for core workflow resources.
  - `packages/pi-flow/` as the primary aggregate install package.
  - No `packages/pi-flow-ux/` yet; the UX package is added by a later spec.
- Add valid package manifests for the root workspace, `pi-flow-core`, and aggregate `pi-flow`.
- Give each distributable package `keywords: ["pi-package"]` and an accurate `pi` manifest for the resources it exposes.
- Make aggregate `pi-flow` expose the initial core resources through dependency or bundled-resource paths rather than duplicating copied source files.
- Document that aggregate `pi-flow` initially exposes core only; UX is a planned later package that will update the aggregate.
- Extract the reusable non-browser skills listed in the Context into `packages/pi-flow-core/skills/`, preserving current live behavior and the `fastlane` spelling.
- Extract runtime prompt/template markdown files used by those skills, including `scout-prompt.md`, `spec-design-procedure.md`, fastlane prompts, generate/refine-plan prompts, execute-plan prompts, refine-code prompts, requesting-code-review prompts, shared dispatch docs, and systematic-debugging subdocs.
- Extract `../pi-config/agent/skills/_shared/` shared markdown contracts and helper scripts into the core package.
- Extract per-skill helper scripts and fixtures/tests needed by `define-spec`, `fastlane`, `execute-plan`, `refine-plan`, and `refine-code` into the core package.
- Extract the required agent definition files into `packages/pi-flow-core/agents/` as bundled resources for later `/flow:setup` handling.
- Preserve marker/subagent completion contracts in prompts and agent definitions, including final-message artifact markers and documented `subagent_done(...)` sentinel calls.
- Provide a package-local, stable helper runner command for skill-invoked helper and template operations. The skill text should use readable logical invocations such as `pi-flow helper _shared/resolve-model-dispatch ...`, `pi-flow helper execute-plan/parse-coder-report ...`, or an equivalent documented command shape.
- The helper runner must resolve packaged helper scripts/templates internally from logical resource identifiers; it must not require the consumer project to contain `agent/skills/...`, `~/.pi/agent/skills/...`, or symlinks that mimic those paths.
- Update executable instructions in extracted skills and prompts so they no longer call `python3 agent/skills/...` or `python3 ~/.pi/agent/skills/...` directly.
- Keep human-facing cross-references readable by using package-relative logical paths such as `skills/_shared/model-tier-resolution.md` where appropriate.
- Include a model-tier example/template based on `../pi-config/agent/model-tiers.json` and documentation that the runtime source of truth remains the installed user's `~/.pi/agent/model-tiers.json`.
- Declare and document `pi-interactive-subagent` as a required companion for workflows that dispatch subagents, while deferring agent-discovery setup to the later setup/commands spec.
- Exclude `web-browser`, personal docs/state from `../pi-config/docs/`, auth/session/cache files, `.worktrees`, `node_modules`, `__pycache__`, `.DS_Store`, and unrelated personal utility extensions.
- Do not include `pi-web-access` or `pi-processes` as core runtime requirements unless an extracted core resource directly depends on them.
- Keep runtime dependencies in `dependencies` or `peerDependencies` as appropriate for Pi packages; keep test/build tooling dev-only.
- Standardize scripts on pnpm and Node-compatible TypeScript/Python. Do not introduce Bun as a runtime or test requirement.
- Migrate existing helper-script tests and add package smoke tests for manifests, resource discovery, exclusions, and helper-runner behavior.

## Constraints

- This spec must not implement `/flow:setup`, `/flow:idea`, `/flow:scout`, `/flow:spec`, `/flow:plan`, `/flow:refine-plan`, `/flow:execute`, `/flow:refine-code`, or `/flow:fastlane`; those active commands belong to the later setup/commands spec.
- This spec must not include the `todos.ts` UI/tool extension or rename TODO artifacts to IDEA artifacts. Idea/TODO command/storage compatibility is handled in the later setup/commands spec, and the durable IDEA migration remains tracked separately by TODO-d9644bc0.
- This spec must not create global or project-local agent symlinks as a package-load side effect.
- This spec must not create an empty UX package stub. UX resources and `packages/pi-flow-ux/` belong to the later UX spec.
- Do not preserve the old `agent/` directory as the published package boundary just to avoid path fixes.
- Do not intentionally depend on the personal `../pi-config` checkout at runtime.
- Do not require changes to `pi-interactive-subagent` for this first slice.

## Approach

**Chosen approach:** Stage the extraction around package-loadable core resources and a readable helper-runner abstraction. The initial workspace contains aggregate `pi-flow` and `pi-flow-core`. Core skills are copied into package-level directories and updated to invoke packaged helpers/templates through a stable logical command rather than old checkout-relative paths. Agent definitions are bundled in core for later setup, but not made discoverable automatically in this slice.

**Why this over alternatives:** This keeps the first implementation focused on passive package resources and path portability, while avoiding both brittle installed absolute paths and fake `agent/skills` compatibility directories. It also leaves the more stateful command/symlink behavior to a dedicated follow-up spec.

**Considered and rejected:**

- Package-relative absolute paths embedded in every skill — direct, but brittle unless Pi exposes a reliable package-root variable to skill text in every install mode.
- Setup-created `agent/skills` compatibility symlinks — easy for copying, but it preserves the old personal layout, makes setup mandatory for ordinary skill execution, and conflicts with the explicit no-side-effect setup boundary.
- A single all-in-one extraction spec — simpler administratively, but it mixes passive resource packaging with command registration, agent symlink setup, idea storage, and UX behavior that have separate risks and tests.
- Creating an empty `pi-flow-ux` package now — adds noise and ambiguous smoke-test expectations before UX resources are actually extracted.

## Acceptance Criteria

- The repository has a pnpm workspace with root check/test scripts and package roots for `packages/pi-flow-core/` and `packages/pi-flow/`.
- `packages/pi-flow-ux/` is absent after this slice.
- `pi-flow-core` has a valid `package.json` with `keywords: ["pi-package"]`, accurate `pi` resource declarations for core skills and any minimal core extension/resource needed by the helper runner, and correct runtime/dev dependency placement.
- Aggregate `pi-flow` has a valid `package.json` with `keywords: ["pi-package"]` and exposes core resources through dependency or bundled `node_modules/pi-flow-core/...` resource paths, without duplicating copied core source files.
- A package-loading smoke test for `pi-flow-core` shows the expected core skills are discoverable.
- A package-loading smoke test for aggregate `pi-flow` shows the same initial core resources are discoverable through the aggregate package.
- Package-loading smoke tests do not create global or project-local agent symlinks.
- The fifteen intended non-browser skills are present under `pi-flow-core`, loadable as Pi skills, and preserve the current `fastlane` spelling.
- `web-browser` and unrelated personal utility extensions are absent from package resources.
- Required agent definition files are present under `pi-flow-core/agents/` as bundled package files for later setup work.
- Shared markdown contracts, prompt templates, Python helper scripts, fixtures, and helper-script tests needed by the extracted workflow are present in package-level directories.
- Executable instructions in extracted skills/prompts no longer refer to `python3 agent/skills/...`, `python3 ~/.pi/agent/skills/...`, or the personal `../pi-config` checkout.
- Extracted skills use a documented helper-runner command with logical resource identifiers for helper and template operations.
- The helper runner can execute representative shared and per-skill helpers from an installed or package-loaded context, including model-tier resolution, artifact-handoff parsing, execute-plan report parsing, and prompt/template filling.
- Helper-runner tests prove missing/unknown logical helper names fail clearly rather than falling back to unsafe path guesses.
- Existing Python helper tests are migrated and pass under the new package layout.
- Tests cover path-portability-sensitive helpers that import shared modules such as `fence_aware.py` and `plan_fence_hardening.py`.
- Package manifest/resource tests verify included resources, excluded resources, and aggregate resource forwarding.
- README or package docs explain the package split, the initial core-only aggregate behavior, the required `pi-interactive-subagent` companion, model-tier configuration, artifact directory conventions, and the fact that `/flow:*`, `/flow:setup`, `/flow:idea`, and UX extraction are follow-up slices.

## Non-Goals

- Implementing `/flow:*` commands or `/flow:setup`.
- Making bundled agent definitions discoverable through symlinks or companion-package integration.
- Implementing `/flow:idea`, `idea` storage, or `todos.ts` extraction.
- Rebranding durable artifacts from `TODO-<id>` to `IDEA-<id>`.
- Extracting the custom footer, working indicator, working config, or nord theme.
- Shipping `web-browser`, personal utility extensions, `pi-web-access`, or `pi-processes`.
- Publishing to npm.
- Depending on `../pi-config` at runtime.

## Open Questions

- Does Pi's package install path make npm `bin` entries available to the shell environment used by skill-invoked commands? If not, the implementation must provide an equally readable, tested runner invocation without reverting to consumer-project `agent/skills` paths.
- Should the final published package names be unscoped (`pi-flow`, `pi-flow-core`) or scoped? The implementation may keep these as working names until publish-time naming is decided.
- Can any future `pi-interactive-subagent` version discover package-bundled agents directly? If so, the later setup/commands spec may use that support instead of symlinks, but this first slice should still bundle the agent definitions.
- Some source helper tests or fixtures contain historical `agent/skills/...` strings as sample content. Those may remain only when they are intentional fixture data; executable package instructions must use the new portable runner form.
