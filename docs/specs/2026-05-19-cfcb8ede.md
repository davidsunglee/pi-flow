# Extract pi-config Workflow into pi-flow Packages

Source: TODO-cfcb8ede

## Goal

Extract the reusable artifact-driven workflow from the personal `../pi-config` checkout into a distributable `pi-flow` monorepo. The result should be installable as Pi packages, with a primary `pi-flow` aggregate package and separately installable core workflow and UX packages, so a fresh Pi setup can use the workflow without depending on the old personal config repository.

## Context

`pi-flow` is currently a nearly empty repository with a README, `.gitignore`, and the source todo. The source material lives in `../pi-config`, whose checked-in reusable pieces include:

- `agent/skills/` — workflow skills, discipline skills, prompt templates, helper scripts, and helper-script tests.
- `agent/agents/` — subagent definitions for `scout`, `spec-designer`, `planner`, `plan-reviewer`, `plan-refiner`, `coder`, `verifier`, `test-runner`, `code-reviewer`, and `code-refiner`.
- `agent/extensions/` — local TypeScript extensions including todo storage, `PI_TODO_PATH` setup, custom footer, working indicator, and several personal utilities.
- `agent/themes/nord.json` — the theme tuned with the custom footer / compact UI experience.
- `agent/model-tiers.json` — a personal example of the model-tier matrix used by the workflow skills.
- `README.md` — useful documentation for the artifact-driven flow, model tiers, subagents, packages, and development commands.

Pi packages can distribute extensions, skills, prompt templates, and themes via `package.json` `pi` manifests or conventional directories. They do not currently expose `agents` as a first-class Pi package resource. `pi-interactive-subagent` is the required companion for the workflow because the skills and coordinators dispatch subagents via `subagent_run_serial` / `subagent_run_parallel` and rely on agent definitions plus `subagent_done` completion. Its current agent discovery covers project-local `.pi/agents/`, global `~/.pi/agent/agents/`, and agents bundled inside the `pi-interactive-subagent` package itself; therefore `pi-flow` must provide a setup path that makes its bundled agent definitions visible from the matching install scope.

Pi extension commands can use colon-style names such as `/flow:setup`, and Pi exposes command APIs/input expansion that can support Flow-facing commands even if the underlying `/skill:*` commands are later hidden. The current workflow skills reference paths under the old `agent/skills/...` layout and many extension imports still use the older `@mariozechner/...` package names, so extraction must include portability and import cleanup rather than a blind copy.

## Requirements

- Build a pnpm-workspace monorepo with conceptual package boundaries:
  - `pi-flow` as the primary documented aggregate install.
  - `pi-flow-core` for workflow skills, subagent definitions, setup, Flow commands, and idea/todo-compatible storage.
  - `pi-flow-ux` for the compact/mobile-friendly UI layer: custom footer, working indicator, and nord theme.
- The aggregate `pi-flow` package must re-export or expose bundled `pi-flow-core` and `pi-flow-ux` Pi resources through package dependencies rather than duplicating files.
- Each distributable package must have a valid `package.json` with `keywords: ["pi-package"]` and a `pi` manifest matching its actual resources.
- Extract the intended workflow skills and their shared helper scripts/tests from `../pi-config/agent/skills` into root-level package directories, not an `agent/` compatibility layout.
- Extract all workflow subagent definitions needed by the skills into the core package, including planner/coder/verifier/reviewer/refiner/test-runner/scout/spec-designer definitions.
- Provide an explicit `/flow:setup` command that makes bundled agent definitions discoverable by `pi-interactive-subagent` after a real package install.
- `/flow:setup` must be install-scope aware: global installs set up global agents, project-local installs set up project-local agents, and it must not intentionally mix scopes.
- `/flow:setup` must be conservative and idempotent: create missing symlinks, leave matching symlinks alone, refuse to overwrite real files or symlinks pointing elsewhere, and report exact conflicts for manual resolution.
- Temporary `pi -e` usage should be treated as a package-loading smoke test. It must not create project-local or global agent symlinks unless the user explicitly runs setup, and setup should avoid pretending a temporary package load is a durable install.
- Provide Flow-facing commands in the core package:
  - `/flow:setup`
  - `/flow:idea`
  - `/flow:scout`
  - `/flow:spec`
  - `/flow:plan`
  - `/flow:refine-plan`
  - `/flow:execute`
  - `/flow:refine-code`
  - `/flow:fastlane`
- `/flow:*` workflow commands must invoke the packaged skills directly enough that they continue to work even if underlying `/skill:*` commands are hidden or disabled later.
- Package the durable intent-capture surface as `idea` / `/flow:idea` for the initial release, while preserving compatibility with existing `TODO-<id>` files, IDs, and provenance lines.
- Keep the full `TODO-<id>` to `IDEA-<id>` artifact/provenance migration out of this extraction; it is tracked separately as `TODO-d9644bc0`.
- Preserve the workflow's consumer-project artifact conventions (`docs/todos`, `docs/specs`, `docs/briefs`, `docs/plans`, `docs/reviews`, `docs/test-runs`) as runtime conventions. Do not package personal artifacts copied from `../pi-config/docs/`.
- Include `pi-interactive-subagent` as the required companion package for the core workflow and document its installation/setup relationship clearly.
- Do not document or bundle unrelated general productivity Pi packages such as `pi-processes` or `pi-web-access` as part of `pi-flow` requirements.
- Exclude the local `web-browser` skill from the initial package.
- Exclude unrelated personal utility extensions from the initial package, including `/answer`, `/context`, `/files`, session breakdown, usage bar, guardrails, and Herdr state.
- Include the custom footer, working indicator modules, and nord theme in `pi-flow-ux`.
- Audit and fix old layout assumptions such as `agent/skills/...`, `~/.pi/agent/skills/...`, and personal `../pi-config` references so skills and helpers work from installed package locations.
- Update TypeScript extension imports to current Pi package names such as `@earendil-works/...` unless a deliberate compatibility reason is documented.
- Provide model-tier setup documentation and an example/template `model-tiers.json`, while preserving user-owned model configuration as the runtime source of truth.
- Keep runtime dependencies in `dependencies` or `peerDependencies` as appropriate for Pi packages; keep tests and development tooling dev-only.
- Standardize development on Node-compatible TypeScript with pnpm workspaces and Node-based tests. Bun is out of scope.
- Migrate or replace existing helper-script and included-extension tests, and add smoke tests for package manifests/resource discovery and setup symlink behavior.

## Constraints

- Do not blindly copy personal state or generated artifacts from `../pi-config`, including sessions, auth files, run histories, node_modules, caches, worktrees, `docs/todos`, `docs/specs`, `docs/plans`, `docs/reviews`, or similar runtime state.
- Do not preserve the old `agent/` directory as the package boundary just to avoid path fixes.
- Do not make agent symlink creation an automatic startup side effect; setup should be explicit.
- Do not require changes to `pi-interactive-subagent` for the initial extraction, unless implementation discovers already-available companion support that can be used without blocking the release.
- Do not use Bun as a runtime or test requirement for this package.
- Do not rename the durable artifact format from `TODO-<id>` to `IDEA-<id>` in this work.
- Do not include `web-browser`, `pi-web-access`, `pi-processes`, or personal utility extensions in the initial package scope.

## Approach

**Chosen approach:** Start with a pnpm monorepo / multi-package design. The primary install remains `pi-flow`, but the repository publishes or can publish `pi-flow-core` and `pi-flow-ux` as separate packages. The aggregate package depends on and re-exports bundled subpackage resources instead of duplicating them.

**Why this over alternatives:** The user wants separable workflow and UX layers from the start, while preserving a simple default install path. This design keeps package boundaries explicit without forcing users to assemble the default experience manually.

**Considered and rejected:**

- Single `pi-flow` package only — simpler initial release, but it would blur the workflow engine and compact-UX layer that the user wants independently packageable.
- Modify `pi-interactive-subagent` to discover arbitrary package-bundled agents directly — potentially cleaner long term, but it couples this extraction to companion-package changes and release timing.
- Preserve the old `agent/` layout inside `pi-flow` — easier copying, but it carries personal-config assumptions into the published package boundary.

## Acceptance Criteria

- The repository has a pnpm workspace layout with package roots for aggregate, core, and UX packages.
- Root scripts use pnpm and can run package build/test/check commands across the workspace.
- `pi-flow`, `pi-flow-core`, and `pi-flow-ux` each have valid package manifests with `pi-package` keywords and accurate Pi resource manifests.
- The aggregate package exposes core and UX resources through bundled/dependency paths rather than duplicated source copies.
- Core workflow skills from `../pi-config/agent/skills` are present, loadable from the package, and no longer rely on the old `agent/skills/...` path layout.
- Required subagent definitions are included in `pi-flow-core` and `/flow:setup` can make them visible to `pi-interactive-subagent` from the matching install scope.
- `/flow:setup` is explicit, idempotent, scope-aware, conflict-safe, and reports what it created or refused to overwrite.
- `/flow:idea`, `/flow:scout`, `/flow:spec`, `/flow:plan`, `/flow:refine-plan`, `/flow:execute`, `/flow:refine-code`, and `/flow:fastlane` are registered and can invoke the packaged workflow entry points without relying on visible `/skill:*` commands.
- The packaged idea surface avoids generic `todo` command/tool naming while remaining compatible with existing `TODO-<id>` storage and provenance for the initial release.
- `pi-flow-ux` includes the custom footer, working indicator, and nord theme, with current `@earendil-works/...` imports and correct runtime peer dependencies.
- Personal utilities, web-browser, `pi-processes`, `pi-web-access`, personal docs artifacts, auth/session files, node_modules, and generated caches are absent from the distributed package contents.
- README/docs explain the monorepo packages, primary install path, required `pi-interactive-subagent` companion, `/flow:setup`, model-tier configuration, artifact directory conventions, and basic workflow entry points.
- A local package-loading smoke test such as `pi -e <package>` confirms expected skills/extensions/themes/commands are available without creating unintended agent symlinks.
- A real install/setup verification confirms subagent definitions are discoverable after `/flow:setup` and the workflow can dispatch at least a minimal subagent-backed path.
- Migrated helper-script and included-extension tests pass, including manifest/resource and setup-symlink smoke tests.

## Non-Goals

- Rebranding durable artifact IDs and provenance from `TODO-<id>` to `IDEA-<id>`; that follow-up is tracked by `TODO-d9644bc0`.
- Publishing or configuring unrelated Pi packages such as `pi-processes` and `pi-web-access`.
- Shipping the local `web-browser` skill in the initial package.
- Shipping personal productivity extensions unrelated to the core workflow or compact UX layer.
- Automatically mutating global/project agent directories on package load.
- Maintaining the old `../pi-config` checkout as a runtime dependency.
- Supporting Bun as an alternate runtime.

## Open Questions

- This remains a broad extraction spanning packaging, skills, agents, extensions, setup, docs, and tests. The user intentionally chose a single spec, so downstream planning should decompose carefully into dependency-ordered work.
- Exact npm package names may need scoping or adjustment based on availability, but the conceptual package roles are `pi-flow`, `pi-flow-core`, and `pi-flow-ux`.
