# Reusable Release skill (`@aphotic/pi-release`)

Source: IDEA-863a3580

## Goal

Create one reusable, project-agnostic Release skill — shipped as a new standalone package `@aphotic/pi-release` — that drives the full release workflow for both single-package and monorepo projects through a single interface. The skill auto-detects project shape (with user confirmation and override), runs the shared release gates and guardrails — including a full security audit (secret scan, dependency vulnerability audit, clean-tree check, audit artifact) on every path — and absorbs project-specific idiosyncrasies from a governed `.pi/release-profile.md` when present, so projects no longer maintain forked release runbooks. pi-flow's existing `docs/RELEASING.md` knowledge moves into the skill (generic parts, including its security audit) and into pi-flow's profile (irreducible specifics), leaving `docs/RELEASING.md` removable or reduced to a pointer. Credentialed actions stay user-owned.

## Context

- **Baseline skill.** `/Users/david/Code/pi-mux-subagents/.pi/skills/release/SKILL.md` is the reference process: a refreshable todo checklist (Step 0) plus steps for version determination, commit-derived release notes (conventional-commit grouping into emoji sections, written to a temp file), a mandatory manual release-notes review/approval pause, single-`package.json` version bump, readiness gates (`git status`, `pnpm run check`, `gitleaks`), publish, and verify. Two behaviors differ from the safety model this idea wants: the baseline has the *agent* run `git push` and `gh release create` directly; only npm publish is user-owned. Its gate set is also narrower than pi-flow's — no dependency vulnerability audit and no audit artifact.
- **pi-flow release runbook.** `docs/RELEASING.md` documents pi-flow's monorepo process: four publishable packages (`@aphotic/pi-ideas`, `@aphotic/pi-flow-core`, `@aphotic/pi-flow-ux`, and the aggregate `@aphotic/pi-flow`) plus a private workspace root; an all-manifests version bump to one shared version; a richer security audit (`git status`, `git rev-parse HEAD`, `pnpm audit`, `pnpm audit --prod`, `gitleaks`, captured to an artifact file, with explicit blocking conditions and a re-run rule for post-audit changes); ordered dry-run/publish (non-aggregate first, then aggregate); and a `pi install` post-publish smoke test. The richer security audit is generic practice and is **promoted into the core skill** by this spec, not kept as a pi-flow profile extra. Its load-bearing hazard: the aggregate uses `bundledDependencies`, which fails under pnpm's isolated linker, so it must be packed/published via its `pack:aggregate`/`publish:aggregate` scripts and never via raw `pnpm pack`/`pnpm publish`.
- **Workspace and skill export.** pi-flow is a pnpm workspace (`pnpm-workspace.yaml`: `packages/*`). `@aphotic/pi-flow-core` exports skills via `"pi": { "skills": ["skills/*/SKILL.md"] }`; the aggregate `@aphotic/pi-flow` bundles core/ux/ideas via `dependencies` + `bundledDependencies`. Existing workflow skills live at `packages/pi-flow-core/skills/<name>/SKILL.md`. `@aphotic/pi-ideas` is precedent for a *standalone* extension package (it drops the `pi-flow-` infix).
- **Release-notes convention.** pi-flow keeps prose release notes in `docs/releases/<version>.md` (e.g. `0.9.0.md`), committed with the release — distinct from the baseline's ephemeral temp-file notes.
- **Maintainer guidance.** `.pi/skills/writing-workflow-skills/SKILL.md` directs skill authors to move rare branches and long prompts into adjacent files one level deep, and to preserve gates/guardrails.

## Requirements

- Ship the skill as a new **standalone package `@aphotic/pi-release`** at `packages/pi-release/`, exporting `skills/release/SKILL.md` via its own `"pi": { "skills": [...] }` manifest. It must not require `@aphotic/pi-flow-core`, so single-package projects can install it alone.
- Add `@aphotic/pi-release` to the `@aphotic/pi-flow` aggregate's `dependencies` + `bundledDependencies`, making it a **fifth publishable package** that joins pi-flow's version alignment and ordered publish.
- Base the skill's structure and gates on the baseline `release` skill: a refreshable **todo checklist**, version determination, commit-derived **release-notes generation**, a **mandatory manual release-notes review/edit pause**, readiness gates, publish, and end-to-end verification.
- **Auto-detect project shape** (single-package vs monorepo) from repository/package structure — workspace metadata (`pnpm-workspace.yaml` / `workspaces`), presence of multiple publishable manifests, etc. **Ask the user to confirm** the detected shape and **allow an explicit override** before proceeding.
- Run the **core security audit** on **every** path, as part of the skill's shared gates (project-agnostic, adapting commands to the project's package manager):
  - **Secret scan** — `gitleaks` (or approved equivalent) with redacted output; stop on any candidate leak; never skip silently (if the scanner is unavailable, stop and ask).
  - **Clean-tree check** — `git status --short --branch`; block on unexpected local changes.
  - **Dependency vulnerability audit** — both a full audit and a prod-only audit (e.g. `pnpm audit` and `pnpm audit --prod`, or the package-manager equivalent).
  - **Record the audited commit** — `git rev-parse HEAD`.
  - **Audit artifact** — capture the exact commands, exit codes, and redacted output to a working file with a generic naming convention (e.g. `/tmp/<project>-security-audit-<version>.md>` shape, no hardcoded project names).
  - **Blocking semantics** — the release is blocked if a dependency audit reports a vulnerability that should be remediated before release, the secret scan reports any candidate leak, git status reveals unexpected local changes, or the audit commands cannot be run or their results cannot be reviewed.
  - **Re-run rule** — re-run the audit if dependency, release-tooling, or other non-version-only changes are introduced after the audit.
- Preserve the remaining shared gates/guardrails on **every** path: **release-readiness** checks (the project's `check`/test suite); release-notes **format/style guidance**; the **manual review/edit** opportunity; and explicit **instructions** for user-run npm auth + publish, git pushes, tag pushes, and GitHub release publication.
- Keep **all credentialed actions user-owned**: the skill prints exact commands and pauses for confirmation; it does **not** itself run npm publish, `git push`, tag pushes, or `gh release create`. (This tightens the baseline, which runs push/`gh` itself.) npm OTP / web auth never enter the agent session.
- Handle **monorepo** mechanics generically, with no hardcoded project names: enumerate the workspace's publishable packages, bump **all** manifests (including the private root) to one shared version, publish in **dependency order** (dependencies before dependents, derived from the workspace graph), and **honor a package's own `pack:`/`publish:` script when it defines one** — a package that defines `publish:aggregate` is published via that script and never via raw `pnpm publish`.
- Implement the **pluggable governed profile**: the skill checks `.pi/release-profile.md`. When present it **absorbs** the project's overrides (extra gates, publish ordering/tooling, post-publish smoke tests, hazards/notes) and folds them into its run; when absent it runs purely generically with no error and no extra prompt. The profile is **markdown the LLM absorbs**, with a recommended (not rigidly parsed) section layout the skill publishes. Profiles may *add* gates but never *remove or weaken* the core security audit.
- Provide a **generic release-notes default** (commit-derived draft written to a working file for review). The profile may define a **persistent notes destination/format** (pi-flow → `docs/releases/<version>.md`, committed in the release commit). The reviewed notes feed the user-run GitHub release.
- **Migrate pi-flow's `docs/RELEASING.md`**: generic content — **including the full security audit section** — is covered by the skill; irreducible pi-flow specifics move into pi-flow's **`.pi/release-profile.md`** — the publishable-package set + ordering, the aggregate `publish:aggregate`/`pack:aggregate` tooling + isolated-linker hazard, the `pi install npm:@aphotic/pi-flow@<v>` smoke test, and the `docs/releases/<version>.md` notes destination. After migration, pi-flow's profile carries **no security-audit content** — the audit is uniform core behavior. `docs/RELEASING.md` is then removed or reduced to a one-line pointer to the skill.
- Decompose the skill so it stays readable: a **spine `SKILL.md`** plus **two one-level-deep shape reference files** (single-package and monorepo mechanics), loaded only after shape confirmation so the LLM pulls just the path it needs. Exact filenames/layout are the planner's to finalize.

## Constraints

- The generic skill must contain **no project-specific hardcoding** (no `@aphotic` package names, no fixed package list); all project specifics come from detection or the absorbed profile.
- **Safety gates — including the full core security audit — and the user-owned-action guardrails live in the always-loaded spine**, never only in a shape reference file or a profile — they must apply on every path. Shape reference files hold *mechanics*, not guardrails.
- Skill-internal references stay **one level deep** from `SKILL.md` (shape files do not fan out further). The project-side `.pi/release-profile.md` is distinct from these shipped references and is read from the consumer's repo at runtime.
- Preserve the guardrail **semantics**: stop on any secret-scan finding, blocking dependency vulnerability, unexpected working-tree change, or readiness-check failure; never skip the secret scan or dependency audit silently (if a tool is unavailable, stop and ask).
- The skill must **not** publish the private workspace root, and must never raw-`pnpm pack`/`pnpm publish` a package that defines aggregate pack/publish scripts.
- pi-flow continues to use **manual version bumps** — no Changesets or automated versioning tooling.

## Approach

**Chosen approach:** A single reusable, standalone `@aphotic/pi-release` skill that auto-detects project shape and absorbs a governed `.pi/release-profile.md` (option **c** from the architecture round). Internally, a **spine `SKILL.md`** carries the single interface, shape detection/confirmation/override, all shared gates and guardrails (including the full core security audit), profile absorption, and the user-owned-action instructions; two **one-level-deep shape reference files** (single-package, monorepo) carry the shape-specific mechanics and are loaded only after the user confirms shape. Project idiosyncrasies live in the markdown profile, absorbed at runtime; pi-flow's specifics populate pi-flow's own profile.

**Why this over alternatives:** Only this option delivers one shared workflow/interface *and* keeps the generic skill free of any single project's quirks, satisfying both the reuse goal and the user's longer-term goal of decomposing `pi-flow-core` into smaller packages. The spine + per-shape reference split keeps the skill readable and lets the LLM load only the path it needs, matching the repo's own skill-authoring guidance; keeping guardrails in the spine keeps safety uniform across both paths.

**Considered and rejected:**

- **Per-project fork** — copy and customize the baseline per project; simplest locally but re-creates the divergence/drift this idea exists to eliminate.
- **Single shared skill with project specifics hardcoded inline** — one skill, but couples the "generic" skill to `@aphotic` package names/tooling and bloats it as projects are added; not genuinely reusable.
- **One monolithic `SKILL.md` (no shape reference files)** — avoids indirection but produces a long, hard-to-scan file mixing both shapes; rejected for readability and to let the LLM load only the relevant branch.
- **Structured-config profile (JSON/YAML schema)** — more deterministic but rigid; can't carry arbitrary prose caveats (like the isolated-linker hazard) and adds a parser; rejected in favor of LLM-absorbed markdown.

## Acceptance Criteria

- A `@aphotic/pi-release` package exists at `packages/pi-release/` exporting `skills/release/SKILL.md`, installable standalone (no `pi-flow-core` dependency), and bundled into `@aphotic/pi-flow`.
- Invoking the skill drives a **single-package** release end-to-end via the shared interface (todos → version → notes → review → gates → user-run publish/push/release → verify).
- Invoking the skill on a **monorepo** project enumerates publishable packages, aligns versions, publishes in dependency order, and routes aggregate-style packages through their `publish:aggregate`/`pack:aggregate` scripts rather than raw `pnpm publish`.
- The skill **detects** project shape, **asks the user to confirm**, and **honors an explicit override**.
- The skill runs the **full core security audit on every path** — secret scan, clean-tree check, full + prod-only dependency audit, audited-commit recording, and audit-artifact capture — and **stops** per the blocking semantics, never silently skipping the secret scan or dependency audit, on single-package and monorepo projects alike.
- The skill generates release notes, gives format/style guidance, and **pauses for manual review/edit** before any publication step.
- The skill **never** runs npm publish, git push, tag push, or GitHub-release creation itself; it prints exact commands and pauses for the user.
- When `.pi/release-profile.md` is present, the skill **absorbs** its overrides; when absent, it runs generically with no error and no extra prompt.
- pi-flow has a populated `.pi/release-profile.md` capturing its publishable set/order, aggregate tooling + isolated-linker hazard, `pi install` smoke test, and persistent notes destination — and **no security-audit content**, since the audit is core; releasing pi-flow through the skill reproduces the current `docs/RELEASING.md` outcome.
- `docs/RELEASING.md` is removed or reduced to a pointer to the skill, with no loss of essential pi-flow release knowledge.
- The skill's `SKILL.md` stays a reasonable size, with shape-specific mechanics in one-level-deep references loaded after shape confirmation.

## Non-Goals

- Migrating pi-mux-subagents to adopt the shared skill, or deduping/renaming its existing project-local `release` skill.
- Automating any credentialed action (npm publish, pushes, GitHub release) — these stay user-run by design.
- Introducing Changesets or automated version tooling; bumps stay manual.
- Building a rigid structured-config profile schema or a profile parser.
- Decomposing the rest of `pi-flow-core` into smaller packages; this idea adds one new package, and broader decomposition is a separate effort.
- Actually cutting a pi-flow release as part of this work.
