# `/flow:doctor` — Keep pi-flow shims and symlinks aligned to the intended package version

Source: IDEA-b79bac29

## Goal

pi-flow development environments suffer **version skew**: the `~/.pi/agent/bin/pi-flow` helper shim, the bundled-agent symlinks, the project/user package installs, and the session's *active* skills can each resolve to a different pi-flow version or source tree. The symptom looks like a workflow or subagent bug, but the root cause is that helper/template/skill resolution silently runs against the wrong package. Build a pi-flow-owned `/flow:doctor` command that **diagnoses** this skew — reporting every relevant surface's resolved realpath and pi-flow version relative to the package actually executing the session — and, on explicit request, **repairs** the links pi-flow itself manages (the helper shim and the agent symlinks), either reconciling them to the active/declared source or repointing them to a target the user names. The "intended version" is derived from Pi's existing package declaration; doctor introduces no competing pin store of its own.

## Context

What exists today that this work builds on:

- **The repo self-hosts, and the skew is live here.** `.pi/settings.json` loads pi-flow twice — `npm:@aphotic/pi-flow` (installed under `.pi/npm/node_modules/`) and the local checkout `../packages/pi-flow`. The helper shim points at one of them; the session's active skills may come from the other.
- **`/flow:setup` already manages the two surfaces doctor will repair** (`packages/pi-flow-core/extensions/setup.ts`): the bundled-agent symlinks (`~/.pi/agent/agents/` for user scope, `{cwd}/.pi/agents/` for project scope) and the helper-runner shim `~/.pi/agent/bin/pi-flow` → `{ownPackageRoot}/bin/pi-flow.mjs` (realpath-resolved). It resolves install scope via `resolveScope()`, which matches `pi.getCommands()` → `sourceInfo.baseDir` realpath against the executing package root. It follows a strict **never-overwrite-silently** posture, reporting `created` / `skipped` / `conflict` / `preserved-other` and refusing to clobber real files or divergent symlinks.
- **The helper runner has a no-fallback guarantee** (`packages/pi-flow-core/bin/pi-flow.mjs`): it resolves helpers/templates against `PACKAGE_ROOT` (the realpath parent of `bin/`) and, if the computed path is missing, fails immediately — it never searches alternative locations. A stale shim therefore silently resolves helpers/templates from the wrong package/version. This is exactly the failure mode doctor diagnoses.
- **Relevant surfaces** for the inventory: the helper shim; the agent symlinks; the project install (`.pi/npm/node_modules/@aphotic/pi-flow`); user-level installs under `~/.pi/agent/npm`; `node_modules/.bin` entries; and `.pi/settings.json`'s `packages` array — the declared source, which already encodes pinned-vs-floating via the npm spec (e.g. `npm:@aphotic/pi-flow@0.8.0` vs unversioned) and local checkout paths. (`~/.pi/agent/flow.json` is pi-flow's model-dispatch config, part of the config landscape but **not** a version surface.)
- pi-flow has no access to Pi's package-manager internals, and installing the package has no lifecycle side effects (no pre/post-install scripts create the shim).

## Requirements

- Provide a pi-flow-owned `/flow:doctor` command in the pi-flow-core extension surface, a sibling to `/flow:setup`, reusing its scope / active-package resolution machinery.
- **Default invocation is read-only diagnosis.** It reports, for every relevant surface (helper shim, agent symlinks, the active executing pi-flow package, project `.pi` install, user `~/.pi/agent/npm` install, relevant `node_modules/.bin`, and the `.pi/settings.json` declared packages): the path, its resolved realpath, and the pi-flow version / source tree it points at.
- Identify the pi-flow package **actually executing the session** (via the `pi.getCommands()` → `sourceInfo` mechanism `resolveScope` already uses) and treat that as "intended" for diagnosis.
- **Flag skew.** Any surface whose realpath resolves to a different pi-flow package/version than the active package is reported as skew. In particular, doctor must signal failure clearly when helper/template/skill resolution could come from a different pi-flow version than the active skills.
- **Classify, don't guess.** A link that resolves into a checkout within the active project's working tree is labeled a **local-dev override** (informational), distinct from a **stale/skew** link that points at neither the active package nor a recognized checkout.
- **Repair is explicit and opt-in via a `--fix` flag.** `/flow:setup` and upgrade flows remain non-destructive — no silent auto-repair fires during normal setup/upgrade.
- `--fix` in **reconcile mode** repoints pi-flow's **managed links only** — the helper shim and the agent symlinks — to the active/declared source. It must honor the never-overwrite-silently posture and must not clobber a local-dev override.
- `--fix` also supports **targeted repoint**: the user can name a different target installation and doctor repoints the managed links to it. The accepted target forms must be **enumerated and shown with examples** in `--help` and in the maintenance docs; doctor must **validate the target** and emit a clear, actionable error when the format is unrecognized or the target is not a usable pi-flow package.
- **Mutation boundary.** doctor mutates only the links pi-flow owns (helper shim + agent symlinks). It must **not** edit Pi's package config (`.pi/settings.json`), run installs, or modify package installs. Where aligning Pi's config is required to make a choice durable, doctor prints actionable guidance instead of editing.
- **Source of truth for intended version is Pi's existing declaration** (`.pi/settings.json` `packages` + the installed version), not a pi-flow-owned pin. The "explicit pins stay pinned; unpinned tracks latest" policy is expressed through Pi's npm-spec semantics; doctor reads and validates these and reconciles managed links to them. doctor must not introduce a competing pin store.
- When `--fix` runs and the intended target is **genuinely ambiguous** (multiple pi-flow packages declared/loaded, as in this repo), doctor requires the user to name the target rather than silently choosing one.
- **Documentation** (in the helper-runner / setup docs family, alongside `helper-runner.md` / `flow-config-setup.md`) must explain: how to verify which pi-flow version a session is using; how to pin a version and how to track latest (via Pi settings / npm spec); how to use a local checkout for pi-flow development; and the `--fix` target format with examples.

## Constraints

- Reuse and stay consistent with `/flow:setup`'s scope / active-package resolution (`resolveScope`) and its never-overwrite-silently behavior; reuse the existing `created` / `skipped` / `conflict` / `preserved-other` vocabulary where it applies.
- No npm install lifecycle side effects — preserve "installing pi-flow-core has no side effects." doctor acts only when explicitly invoked.
- doctor must reason about resolution exactly as `bin/pi-flow.mjs` does (`PACKAGE_ROOT` = realpath parent of `bin/`, no fallback) so its version verdicts match real helper/template resolution.
- Implemented as a TypeScript extension consistent with `setup.ts`; Node ≥ 20; symlink handling via `lstat` / `readlink` / `realpath` as the existing code does (macOS / Linux).
- doctor must not become a package manager (no install / upgrade / uninstall, no `pi install`) and must not introduce a new persistent pin/config surface owned by pi-flow.

## Approach

**Chosen approach:** Pi's existing package declaration is the source of truth for intended version. doctor derives "intended" from the package actually executing the session and from `.pi/settings.json`'s declared `packages` (which already encode pinned-vs-floating via npm specs and checkout paths). It reconciles its own managed links (helper shim + agent symlinks) to that declared/active source, and supports a one-shot **targeted repoint** of those links; the durability of a deliberate choice comes from aligning Pi's settings, which doctor advises on but never edits. No pi-flow-owned pin store is introduced.

**Why this over alternatives:** It is the only option consistent with every other decision in this spec — it honors the "doctor advises on Pi config, doesn't edit it" mutation boundary, it directly answers the idea's own worry about *not* reimplementing Pi's package manager, and it avoids creating a second source of truth that could itself drift from the loaded package (a new skew class — ironic for a tool whose entire job is killing skew). The idea's pin policy maps cleanly onto Pi's npm-spec semantics, so no new mechanism is needed to satisfy it. The repoint the user asked for still happens immediately on the links pi-flow owns; only its permanence rides on a settings change doctor walks the user through.

**Considered and rejected:**

- **No pin concept, always reconcile to active** — simplest and stateless, but descopes the idea's explicit-pin acceptance criterion: there is no pin to honor.
- **pi-flow owns a new pin store** (a field/file pi-flow controls) — gives durable first-class pins, but adds a competing source of truth that can disagree with Pi's actually-loaded package, a new skew class doctor would then have to detect, and contradicts the no-competing-pin boundary above.

## Acceptance Criteria

- `/flow:doctor` with no arguments prints a report listing each relevant surface with its path, resolved realpath, and resolved pi-flow version / source tree, and names the package currently executing the session.
- The report flags any surface that resolves to a different pi-flow package/version than the active package, and distinguishes a **stale/skew** link from a **local-dev override**.
- doctor signals failure clearly (non-zero / explicit error state) when helper/template/skill resolution could resolve to a different pi-flow version than the active skills.
- `/flow:doctor --fix` repoints only the helper shim and the agent symlinks to the active/declared source, leaves Pi's package config and non-managed files untouched, and refuses to clobber a local-dev override or a divergent real file (reporting it, per setup's posture).
- `/flow:doctor --fix` with an explicit target repoints the managed links to that target; an invalid/unrecognized target produces a clear, actionable error; the accepted target forms appear in `--help` and the docs with examples.
- When the intended target is ambiguous (multiple pi-flow packages declared/loaded), `--fix` requires an explicit target and does not silently pick one.
- doctor never writes `.pi/settings.json`, never runs an install, and never creates a pi-flow-owned pin file; when settings alignment is needed it emits actionable guidance.
- Documentation exists in the helper-runner / setup docs family covering: verifying the active pi-flow version, pinning vs tracking latest via Pi settings, using a local checkout, and the `--fix` target format with examples.

## Non-Goals

- Becoming a package manager: no installing, upgrading, or uninstalling pi-flow packages; no invoking `pi install`.
- Editing Pi's `.pi/settings.json`, user-level Pi settings, or any package install on the user's behalf (detect-and-advise only).
- Introducing a new persistent pin/config surface owned by pi-flow (explicitly rejected by the chosen approach).
- Managing shims or symlinks unrelated to pi-flow.
- Auto-repair during `/flow:setup` or upgrade; repair is opt-in via `--fix`.
- Changing the helper runner's no-fallback resolution semantics.
