# Centralize project-aware pi-flow flow config resolution

Source: IDEA-eb099e54
Scout brief: docs/briefs/IDEA-eb099e54-brief.md

## Goal

Introduce a single project-aware flow-config resolution contract — explicit `--flow-config` override, then project-local `<working-dir>/.pi/flow.json`, then user/global `~/.pi/agent/flow.json` — with a shared executable implementation, so that workflow skills, dispatch and provenance helpers, diagnostics (`/flow:doctor`), setup guidance (`/flow:setup`), and docs all agree on which `flow.json` is active. Project-pinned pi-flow installs gain project-scoped dispatch configuration without losing the existing user/global fallback, eliminating the current mixed-version risk where project-pinned workflow code executes against a global config intended for a different pi-flow-core version.

## Context

- Four Python helpers default `--flow-config` to `~/.pi/agent/flow.json`: `skills/_shared/scripts/resolve-model-dispatch.py`, `skills/_shared/scripts/resolve-coordinator-dispatch.py`, `skills/_shared/scripts/validate-review-provenance.py`, and `skills/refine-plan/scripts/validate-and-parse-plan-review.py` (which invokes `validate-review-provenance.py` as a subprocess without passing `--flow-config`).
- `skills/refine-plan/SKILL.md` Step 5 and `skills/refine-code/SKILL.md` Step 2 `cat ~/.pi/agent/flow.json` directly, each with a guardrail-tested stop string (`refine-plan requires ~/.pi/agent/flow.json — see flow config setup.` and the refine-code equivalent).
- Canonical Template 1 (`~/.pi/agent/flow.json missing or unreadable — cannot dispatch <agent>.`) is duplicated byte-equal in the two dispatch helpers, `skills/_shared/dispatch-contract.md`, and `docs/flow-config-setup.md`, and pinned by `__tests__/guardrail-strings.test.mjs`, `test_resolve_model_dispatch.py`, and `test_resolve_coordinator_dispatch.py`. `validate-review-provenance.py` uses the shorter JSON failure label `flow.json missing or unreadable`.
- `dispatch-contract.md` names `~/.pi/agent/flow.json` as the input source in its `## Input` section and coordinator procedure prose, and lists 12 dispatch call sites that invoke the resolution helpers without `--flow-config`.
- pi-flow already supports project-local package installs and project-scoped `.pi` state; this repo carries a complete `.pi/flow.json` at its root. The helper/template runner resolves scripts from the active package root (`docs/helper-runner.md`, grammar `_shared/<name>` → `skills/_shared/scripts/<name>.py`, strict no-fallback), but dispatch configuration remains global-only.
- The coordinator prompts (`refine-plan-prompt.md`, `refine-code-prompt.md`) already carry `{WORKING_DIR}` and `{FLOW_CONFIG}` placeholders; the fill-prompt helpers receive `--flow-config <path>` and substitute the file's *content* into `{FLOW_CONFIG}`. The prompts' "Dispatch resolution" sections instruct the coordinator to run `resolve-model-dispatch` without `--working-dir`. Neither prompt hardcodes the global path.
- `extensions/doctor.ts` builds its diagnosis from exported pure functions with injected `cwd`/`homeDir` paths (no subprocesses) and reports package-root surfaces only; `extensions/setup.ts` manages the helper shim and agent symlinks with a strict never-overwrite posture and has no flow-config awareness. `doctor.test.ts` seeds fake directory trees and tests the pure functions in-process.

## Requirements

1. **Contract document.** Add `skills/_shared/flow-config-resolution.md` as the single normative authority for: the resolution precedence, the `working-dir` definition, selection semantics (existence + readability only), the no-fallback-past-selection rule, the contents and ordering of the `searched` list, the `<locations>` rendering rules, and the canonical missing-config error clause with its per-consumer suffixes. Call sites and docs reference this file instead of duplicating path logic.
2. **Shared executable resolver.** Add shared resolution logic under `skills/_shared/scripts/`, consumed by the dispatch and provenance helpers so behavior cannot drift from the contract, plus a public diagnostic CLI `pi-flow helper _shared/resolve-flow-config` that prints single-line JSON `{"path": "<abs>", "scope": "explicit|project|user", "searched": ["<abs>", ...]}` on success. The `path` and `searched` values are absolute normalized paths; `searched` lists, in resolution order, only the locations actually consulted.
3. **Precedence.** (i) Explicit `--flow-config <path>` wins after `~` expansion and absolute normalization; if unreadable, fail — never fall back. (ii) Else project-local `<working-dir>/.pi/flow.json` when it exists and is readable. (iii) Else user/global `~/.pi/agent/flow.json`. (iv) If none is usable, emit the canonical missing-config error (Requirement 6) on stderr and exit 1.
4. **Selection semantics.** The resolver selects on existence + readability only and never parses JSON. JSON validity remains the consumer's concern: when a selected config later fails to parse, the consumer emits the canonical error naming the locations consulted up to and including the selected one, and does **not** fall through to a lower-precedence config. A project file that exists but is unreadable is skipped (resolution falls through to user/global) yet still appears in `searched`.
5. **Working-dir definition and helper flags.** `working-dir` is the active workflow workspace root. `resolve-flow-config`, `resolve-model-dispatch`, `resolve-coordinator-dispatch`, `validate-review-provenance`, and `validate-and-parse-plan-review` accept `--working-dir`, defaulting to process cwd. `validate-and-parse-plan-review` threads the same resolution (working dir or resolved config path) to its `validate-review-provenance` subprocess so both resolve identically. Explicit `--flow-config` override behavior is preserved on every helper. Git worktrees use the worktree root; a worktree without `.pi/flow.json` falls back to user/global unless an explicit override was supplied.
6. **Canonical wording migration.** Template 1 becomes `flow.json missing or unreadable; searched <locations> — cannot dispatch <agent>.` At runtime `<locations>` renders the `searched` list comma-space separated in resolution order, with the home-directory prefix abbreviated to `~`. The doc copies in `dispatch-contract.md` and `flow-config-setup.md` keep the literal `<locations>` placeholder. The bare `resolve-flow-config` helper emits the clause without the dispatch suffix: `flow.json missing or unreadable; searched <locations>.` The `validate-review-provenance` failure label becomes `flow.json missing or unreadable; searched <locations>`. All copies and their test assertions move in lockstep.
7. **Skill flow-config reads.** `refine-plan/SKILL.md` Step 5 and `refine-code/SKILL.md` Step 2 replace `cat ~/.pi/agent/flow.json` with a `resolve-flow-config` invocation threading their `WORKING_DIR`; the resolved `.path` feeds the existing fill-prompt `--flow-config` arguments and any subsequent display. The stop strings become, byte-equal: `refine-plan: flow.json missing or unreadable; searched <locations> — see flow config setup.` and `refine-code: flow.json missing or unreadable; searched <locations> — see flow config setup.` (literal `<locations>` in the SKILL.md template, substituted at runtime).
8. **Prose and threading updates.** `dispatch-contract.md` (the `## Input` section, Template 1 block, and coordinator-procedure prose) says "resolved flow config" and references the contract document instead of hardcoding the global path. The coordinator prompts' "Dispatch resolution" sections instruct passing `--working-dir "{WORKING_DIR}"` on `resolve-model-dispatch` invocations so nested worker resolution matches the orchestrator's. Dispatch sites that already compute `WORKING_DIR` pass it explicitly; top-level sites may rely on the cwd default.
9. **Doctor.** `/flow:doctor` reports the resolved flow config path and scope for the current cwd, visually distinct from the active/effective package root, and warns when (a) no usable flow config exists, or (b) a project-local package is effective but flow config resolution falls back to user/global. The resolution is implemented in-process in TypeScript per the contract (no subprocess), following the existing pure-function injected-path pattern. The `DoctorDiagnosis` field shape and report layout are planner decisions.
10. **Setup.** `/flow:setup` guidance is updated without changing its mutation boundary: it never creates or overwrites flow config files, but tells the user where project-local vs user/global config lives and how to copy `flow.example.json` when config is missing.
11. **Docs.** `docs/flow-config-setup.md` documents both scopes, the precedence, the new canonical templates, and `resolve-flow-config` verification; `docs/helper-runner.md` gains the new helper's entry; `docs/version-alignment.md` gains a short cross-reference noting that project-pinned packages pair with project-local flow config and that doctor surfaces both; `README.md` (the flow-config paragraph) describes project `.pi/flow.json` for pinned/project-specific workflows with `~/.pi/agent/flow.json` as the user/global fallback.
12. **Tests.** Following existing patterns: precedence matrix (explicit / project / user / missing) and `--working-dir` behavior in the dispatch-helper suites; unreadable-explicit fail-hard; unreadable-project skip-and-record; a new `test_resolve_flow_config.py` covering all three scopes, the `searched` field, and the missing-config error; updated byte-equal canonical strings in `test_resolve_model_dispatch.py`, `test_resolve_coordinator_dispatch.py`, and `guardrail-strings.test.mjs` (Template 1 form and both stop strings); `doctor.test.ts` additions for the flow-config report line, scope reporting, and the project-package-with-user-config warning.

## Constraints

- No separate trust gate for project-local `.pi/flow.json`: package-resolution trust remains a separate concern, and workflow execution already occurs in the project context. The resolver is a plain file read regardless of Pi trust state.
- The resolver never walks up parent directories and never detects worktree roots itself; the caller's working dir (or its cwd default) is authoritative.
- `/flow:setup`'s mutation boundary is unchanged — guidance only, no flow-config file writes.
- `doctor.ts` and `setup.ts` must not invoke `pi-flow helper` subprocesses for flow-config resolution (doctor must keep working when the shim is broken).
- The helper-runner grammar and no-fallback guarantee are unchanged; the new helper fits the existing `_shared/<name>` → `skills/_shared/scripts/<name>.py` rule.
- Byte-equal canonical-template discipline holds: every template copy and every test assertion changes atomically; no consumer paraphrases the templates.
- Workspaces without `.pi/flow.json` behave exactly as today (user/global config), apart from the new error wording.
- Python helpers stay stdlib-only and follow existing conventions: single-line stderr failure + exit 1, single-line JSON on stdout.
- Fallback skips happen only at selection time per Requirement 4 — never after a config has been selected.

## Approach

**Chosen approach:** One normative contract document (`skills/_shared/flow-config-resolution.md`) with two implementations bound to it. Python consumers share a single resolver in `skills/_shared/scripts/` — the dispatch and provenance helpers consume it directly, and the public `resolve-flow-config` CLI is a thin wrapper over it. The doctor/setup extension layer implements the same precedence in-process in TypeScript, in the existing pure-function injected-path style. Both sides carry tests asserting the contract's precedence and canonical strings.

**Why this over alternatives:** The precedence logic is two existence/readability checks plus an ordering rule — cheap to mirror once across the language boundary — while routing doctor through the helper subprocess would couple the diagnostic surface to the component it diagnoses: with a broken or stale shim, `/flow:doctor`'s flow-config reporting would fail or mislead exactly when the user runs it to find out what is wrong. In-process TypeScript also preserves doctor's fast pure-function test pattern.

**Considered and rejected:**

- Single executable source (every consumer, including doctor/setup, subprocesses `pi-flow helper _shared/resolve-flow-config`) — zero duplication, but circular for broken-install diagnosis and breaks doctor's in-process test pattern at a subprocess seam.
- Hybrid (doctor subprocesses the helper when available, with a TypeScript fallback) — two code paths in doctor for no added correctness; worst of both.

## Acceptance Criteria

- From a project containing `.pi/flow.json`, `pi-flow helper _shared/resolve-model-dispatch --model-tier modelTiers.frontier --agent planner` (no `--flow-config`) uses the project config and succeeds even when the user/global config lacks that tier.
- Passing `--flow-config /some/path/flow.json` uses only that explicit file; if it is unreadable, the helper exits 1 with the canonical error naming only that path — no fallback occurs.
- Running from a workspace without `.pi/flow.json` continues to use `~/.pi/agent/flow.json`.
- `pi-flow helper _shared/resolve-flow-config` reports the resolved absolute path, a scope of `explicit`, `project`, or `user`, and the `searched` list (absolute paths, resolution order, only locations actually consulted).
- With no usable config anywhere, consumers emit the canonical error listing both searched paths comma-space separated with the home prefix rendered as `~`, and exit non-zero.
- A selected-but-malformed project config causes the consumer to fail with the canonical error naming it; the user/global config is not silently used instead.
- `refine-plan`, `refine-code`, their coordinator prompts, and nested helper calls thread the same `WORKING_DIR` and therefore resolve the same config consistently.
- `/flow:doctor` shows both the active pi-flow package root and the resolved flow config path/scope, with actionable warnings for missing config and for a project-local package paired with user/global config fallback.
- `/flow:setup` remains non-destructive while giving current guidance for creating either project-local or user/global flow config.
- README and `flow-config-setup.md` explain when to use project `.pi/flow.json` versus `~/.pi/agent/flow.json`.
- The guardrail, Python helper, and doctor test suites pass with the new canonical wording and stop strings.

## Non-Goals

- No auto-creation, migration, or dual-read of flow config files — setup and doctor never write config.
- No trust gating of project-local config.
- No directory walk-up or worktree detection inside the resolver.
- No changes to the package-resolution (effective-package) logic itself — active package root and active flow config remain independently resolved, with doctor reporting both.
- No flow.json schema changes; the config shape in `dispatch-contract.md` is untouched.
- No self-resolution in the fill-prompt helpers — `fill-refine-plan-prompt.py` and `fill-refine-code-prompt.py` keep their required, caller-threaded `--flow-config`/`--working-dir` arguments.
- No TypeScript rewrite of the existing Python helper scripts (raised during design; deliberately out of scope — the chosen approach tolerates the small, contract-pinned TS/Python duplication instead).
