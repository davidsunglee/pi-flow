# Make /flow:doctor scope-aware for global and project pi-flow installs, with a stable per-cwd helper dispatcher and a readable report

Source: IDEA-42f4294a

## Goal

Teach `/flow:doctor` to model Pi's effective-package semantics so it reports a clean, non-skewed state whenever the *effective* runtime surfaces are aligned — even while both a user/global pi-flow and a project pi-flow override are installed. An installed-but-overridden global install, or a leftover project install that the active user package shadows, must read as *inactive inventory*, not as resolution `[SKEW]`.

Two supporting changes make that possible and durable:

1. **A stable per-cwd helper dispatcher.** Replace the single-root `~/.pi/agent/bin/pi-flow` symlink (which can only ever be correct for one scope at a time) with a stable dispatcher that resolves the *effective* pi-flow-core root for the current working directory at runtime — honoring a project override when the project is trusted, and falling back to the user/global target otherwise.
2. **A redesigned report.** The current two-lines-per-surface format with raw absolute realpaths wraps and shatters alignment in the Pi notify panel. Replace it with a grouped, status-led layout and aggressive path abbreviation so the report is scannable at any panel width.

The effective-package model, npm-spec resolution, and trust check are extracted into a single plain-`.mjs` module shared by both the bare-node dispatcher and the TypeScript extension, so the two never drift — drift between resolvers is exactly the failure class this work removes.

## Context

`/flow:doctor` lives in `packages/pi-flow-core/extensions/doctor.ts`. It inventories the managed pi-flow surfaces (helper shim, user/project agent symlinks, npm installs, declared packages, node bins), classifies each against a single `activeRoot` (the executing package's realpath), and renders a report.

Current behavior and its gaps (all confirmed in source):

- **One active root, no effective-scope model.** `classifySurface` (`doctor.ts`) only compares `realpath === activeRoot`; anything else that isn't an in-tree checkout becomes `stale-skew`. `buildDiagnosis` unconditionally inventories *both* project and user installs/node bins regardless of which scope is effective. So an installed-but-overridden global install, or a stale project `.pi/npm` install, is classified `stale-skew`.
- **`[SKEW]` leaks into inactive inventory.** `hasSkew` counts only the four "resolution" kinds (`helper-shim`, `user-agents`, `project-agents`, `node-bin`), but `renderReport`'s `TAGS` map prints `[SKEW]` for *any* row classified `stale-skew` — including `project-install`/`user-install`/`declared-package` inventory rows. The report therefore shows `[SKEW]` lines even when `hasSkew === false`.
- **npm specs are mis-parsed.** `parseDeclaredPackages` treats every *string* entry as a `local` path and only honors `npm:` for object-form `source`. Against the live `~/.pi/agent/settings.json`, the bare string `"npm:@aphotic/pi-flow"` is mis-classified `local`. `declaredSurfaceReports` only resolves `kind === "local"`, so every npm declaration reports `unresolved`. There is no aggregate→core resolution.
- **Single-root helper symlink.** `~/.pi/agent/bin/pi-flow` is a symlink to one concrete `bin/pi-flow.mjs` (set by `runHelperShimSetup` in `setup.ts`). It cannot be simultaneously correct for global-only sessions and for projects that override pi-flow with a different root/version. `bin/pi-flow.mjs` is a plain-JS launcher (shebang `#!/usr/bin/env node`) that computes `PACKAGE_ROOT` from its own location.

Runtime/build facts that constrain the design:

- There is **no build step**. Pi loads the `.ts` extensions directly via `node --experimental-strip-types`; the extensions import each other by `.ts` path. `bin/pi-flow.mjs` runs under **bare `node`** (no strip-types), so the dispatcher **cannot import any `.ts` file at runtime**. Shared logic must be plain `.mjs`.
- `@earendil-works/pi-coding-agent` is a peer dependency and is not resolvable as an introspectable package in this workspace; doctor already does its own filesystem resolution (`package-resolution.ts`) and reads `pi.getCommands()` `sourceInfo` for scope/root detection (`resolveScope` in `setup.ts`).
- Pi records project trust in `~/.pi/agent/trust.json` as a `{ "<path-prefix>": true }` map; a cwd is trusted iff some key equals it or is a path ancestor (e.g. `"/Users/david/Code": true` covers `/Users/david/Code/pi-flow`).
- Pi packages can be installed as the **aggregate** `@aphotic/pi-flow` (a wrapper that depends on `@aphotic/pi-flow-core`) **or** as individual components installed directly (`@aphotic/pi-flow-core`, `@aphotic/pi-mux-subagents`). Doctor and the dispatcher must work in both cases.

### Decisions settled during spec design

- **Inactive installs are shown, not hidden.** Inactive installs render by default with a neutral `[inactive]` tag and a sub-type (`overridden` / `shadowed`); `[SKEW]` is reserved strictly for genuine resolution divergence. A `--all` mode adds deeper inventory (e.g. absent candidate locations).
- **Report layout = grouped sections.** Verdict header, then surfaces grouped under `Effective surfaces` / `Inactive installs` / `Skew`, with fixed-width status tags and abbreviated paths. No borders (degrades gracefully at any panel width). Path abbreviation (`$HOME`→`~`, elide the predictable install-boilerplate middle such as `.../node_modules/@aphotic/`) is a shared helper used everywhere a path is printed.
- **Dispatcher trust = trusted-only override.** The dispatcher honors a project pi-flow override only when the project is trusted (prefix match in `trust.json`); otherwise it ignores the project entry and falls back to the user/global target. It reads `trust.json` directly.
- **No dispatcher cache.** The dispatcher resolves fresh on every invocation (a handful of `readFile`/`realpath` calls, negligible next to the `python3` spawn it then does). Nothing is cached, so there is no staleness to invalidate after reinstalls, version bumps, project moves, or trust changes.
- **`local-dev` is clean by default, plus `--strict`.** An in-tree source checkout keeps its own `[local-dev]` tag and never counts as skew by default. A `--strict` flag additionally requires every effective surface to resolve to the *same* install root, flagging local-dev divergence for an airtight check.
- **Single spec (not split).** Decomposing the dispatcher into its own spec was considered and declined; see Open Questions.

## Requirements

### 1. Shared effective-package module (`.mjs`)

Add a plain-`.mjs` module (e.g. `packages/pi-flow-core/extensions/lib/effective-package.mjs`) with **no third-party imports** (node builtins only) so it is importable by both bare-node `bin/pi-flow.mjs` and the strip-types `.ts` extensions. It owns:

- **npm-spec parsing** for declared `packages` entries in both forms:
  - string form: `"npm:@aphotic/pi-flow"`, `"npm:@aphotic/pi-flow-core"`, `"npm:@aphotic/pi-flow@0.8.0"` (pinned);
  - object form: `{ "source": "npm:@aphotic/pi-flow", ... }`;
  - local/path form (string or `source`) as today.
  Classify `kind` (`npm` / `local`), extract the package name and any pinned `@<version>`.
- **Package-identity normalization (aggregate↔core).** Map both the aggregate `@aphotic/pi-flow` and the direct `@aphotic/pi-flow-core` to the **same** logical pi-flow identity, so project-overrides-user works whichever form each scope uses (aggregate on one side, direct core on the other, or a mix). Resolve a normalized identity to its concrete `@aphotic/pi-flow-core` root: directly for a core install, and via the aggregate wrapper's `@aphotic/pi-flow-core` dependency for an aggregate install (mirroring `resolveBinToCore`'s existing delegation).
- **Effective-package resolution** for a given cwd: apply Pi's project-overrides-user rule — a project with a pi-flow `packages` entry overrides the user install; a project with no pi-flow entry inherits the user install.
- **Trust check:** read `~/.pi/agent/trust.json` and return whether a given cwd is trusted (exact or path-ancestor key match with value `true`). Missing/malformed file ⇒ untrusted.
- **Path abbreviation** helper: `$HOME`→`~`, and elide the predictable install-boilerplate middle (e.g. `.../node_modules/@aphotic/<pkg>` → `.../…/<pkg>`), used by all path rendering.

The `.ts` extensions import this module and keep their typed wrappers around it. Existing pure helpers in `package-resolution.ts` may be reused by the `.mjs` only if they are first moved/duplicated into the `.mjs` (the `.ts` cannot be imported by the bare-node dispatcher). The shared module is the single source of truth for resolution; no resolution logic is duplicated between the dispatcher and the extension.

### 2. Effective-package model in doctor

- Extend `buildDiagnosis` to compute, before classifying surfaces, the **effective pi-flow root** for `(cwd, homeDir)` via the shared module: the project override root when the project declares (and is trusted for) one, else the user/global root. Continue to derive the active/executing root from the extension's own location and `pi.getCommands()` `flow:*` `sourceInfo` (as today).
- Replace the single-`activeRoot` comparison with classification against the effective model. Add classifications:
  - `inactive-overridden` — a real install whose identity is overridden by a higher-priority scope (e.g. a user/global install shadowed by a trusted project override).
  - `inactive-shadowed` — a real install in a scope that is not effective for this cwd (e.g. a stale project `.pi/npm` install while no project entry is declared and the user package is effective).
  - Keep `active`, `local-dev`, `stale-skew`, `absent`, `unresolved`, `non-pi-flow`.
- `stale-skew` is now reserved for a *resolution* surface (helper shim, agent symlinks, node bin) that resolves to a root that is **neither** the effective root **nor** a recognized inactive install **nor** an in-tree checkout — i.e. genuine divergence between what executes and what the effective package is.
- `hasSkew` counts only resolution-kind surfaces classified `stale-skew` (unchanged intent). Inactive installs never set `hasSkew`.
- **`--strict`:** when set, additionally require every *effective* resolution surface to resolve to the **same** root; a `local-dev` or otherwise-divergent effective surface fails strict mode (reported distinctly) even though it is clean by default.

### 3. npm declared-package resolution

- Fix `parseDeclaredPackages` (or its replacement in the shared module) so string `npm:` entries are classified `npm`, object `source` npm entries are classified `npm`, pinned `@<version>` is detected on both forms, and only genuine path specs are `local`.
- `declaredSurfaceReports` resolves npm declarations to their installed concrete core root (direct or aggregate→core) and classifies them against the effective model, instead of reporting every npm declaration `unresolved`.

### 4. Report rendering (grouped sections)

Rewrite `renderReport` (pure over `DoctorDiagnosis`) to emit the grouped layout:

- A verdict header line (`pi-flow doctor — OK, no skew` / `… — SKEW DETECTED`) and the active/effective package identity with its abbreviated path and a parenthetical scope note (e.g. `(project override)` / `(user/global)`).
- Sections in order: **Effective surfaces**, **Inactive installs**, **Skew**. Each row: fixed-width status tag (`[active]`, `[inactive]`, `[local-dev]`, `[SKEW]`, …), short surface label, version, abbreviated path; sub-type / notes (e.g. `overridden by project package`) on an indented continuation line. Empty sections render `(none)`.
- Inactive installs appear by default with `[inactive]` + sub-type; `[SKEW]` never appears for inactive inventory.
- `--all` adds an inventory section listing absent candidate locations (today silently skipped) and any deeper diagnostics.
- All paths pass through the shared abbreviation helper. No bordered table (it misaligns in an unknown-width notify panel).

### 5. Stable per-cwd helper dispatcher

- Replace the single-root symlink at `~/.pi/agent/bin/pi-flow` with a **stable dispatcher**: a real, self-contained launcher file (not a symlink to a versioned core root) so it survives core version changes and is simultaneously correct for global-only sessions and for projects that override pi-flow.
- At invocation the dispatcher resolves, via the shared module, the **effective** `@aphotic/pi-flow-core` root for `process.cwd()`: honor a project override only when the project is trusted, else fall back to the user/global target; then delegate to that core's `bin/pi-flow.mjs` with the original argv. No caching.
- The dispatcher must resolve aggregate npm installs and direct-core npm installs. Local/git package sources are best-effort: resolve them when the declared path/root resolves to a usable core; otherwise fall back to the user target (do not crash). Document the local/git limitation if not fully supported.
- The dispatcher is installed/refreshed by `/flow:setup` (user scope) and repaired by `/flow:doctor --fix`. Because the dispatcher is a copy of the active package's bundled launcher, doctor treats the installed dispatcher as a surface and detects when it is stale relative to the active package's launcher, offering to refresh it under `--fix`.
- Preserve the current never-overwrite posture: refuse to clobber a real file/dir or a divergent non-pi-flow target at the shim path; for project scope with no shim present, emit the existing guidance to run user-scope setup rather than silently creating one.

### 6. Scope-aware agent symlink management

- Keep user and project agent symlink management separate and scope-aware: a trusted project override may install project agents under `<cwd>/.pi/agents` while the user install continues to provide user agents under `~/.pi/agent/agents`. Doctor classifies each agents surface against the scope it belongs to (project agents against the effective project root; user agents against the user root), so the presence of both does not produce skew when each is internally aligned.

### 7. `--fix` scope discipline

- `/flow:doctor --fix` repairs only the **active/effective-scope** resolution surfaces (helper dispatcher, the effective scope's agent symlinks). It must **not** require deleting valid inactive installs to reach a clean report, and must never delete an inactive install.
- Preserve existing `--source` / reconcile-target / never-edit-settings behavior.

## Constraints

- **No drift between resolvers.** The dispatcher and the extension share one `.mjs` resolution module; resolution logic is not duplicated. Re-introducing a second resolver is disallowed.
- **Bare-node importability.** The shared module is plain `.mjs` with node-builtin imports only; it must run under `node bin/pi-flow.mjs` with no `--experimental-strip-types`.
- **No hard dependency on Pi internals.** Reimplement just enough package resolution; do not take a runtime dependency on `@earendil-works/pi-coding-agent` package-manager internals. Continue using `pi.getCommands()` `sourceInfo` (already available to the extension) for active-root/scope detection.
- **Trusted-only project overrides.** The dispatcher honors a project override only for trusted projects (prefix match in `~/.pi/agent/trust.json`); untrusted projects fall back to the user/global target. Trust is read directly from disk.
- **No dispatcher cache.** Resolution is computed fresh per invocation; no resolved-target cache file is written.
- **Read-only `--fix` boundary preserved.** Doctor never edits `.pi/settings.json`, never installs packages, never creates a pin file, and never deletes inactive installs. Making a repoint durable remains the user's job (edit `packages`).
- **Dispatcher stability.** `~/.pi/agent/bin/pi-flow` must not be a symlink into a versioned core root; it is a stable self-contained launcher independent of any single core version.
- **No bordered table.** Report output goes through `ctx.ui.notify` into an unknown-width panel; rendering must not assume a terminal width.

## Acceptance Criteria

Diagnosis (with injected `cwd`/`homeDir`/sandbox roots, as in the existing `doctor.test.ts`):

- **Global-only pi-flow:** no `[SKEW]` rows, `hasSkew === false`.
- **Global + project override at the same version (different root):** project root is active/effective, `hasSkew === false`, no `[SKEW]`; user install rows render `[inactive]` (`overridden`), not `[SKEW]`.
- **Global + project override at a different version:** project root is effective, `hasSkew === false`, no `[SKEW]`; the user install is `[inactive]` (`overridden`).
- **No project pi-flow entry + global install + stale project `.pi/npm`:** user root stays effective; the stale project install renders `[inactive]` (`shadowed`), not `stale-skew`; `hasSkew === false`.
- **Aggregate vs direct-core forms interoperate:** override resolution treats a user aggregate `npm:@aphotic/pi-flow` and a project direct `npm:@aphotic/pi-flow-core` (and the reverse) as the same identity; project overrides user in both directions.
- **npm declarations resolve:** `"npm:@aphotic/pi-flow"` (string), `{ "source": "npm:@aphotic/pi-flow" }` (object), and a pinned `"npm:@aphotic/pi-flow@0.8.0"` all parse as `npm`, detect the pin where present, and resolve to the installed concrete core root (direct or aggregate→core) — none report `unresolved` when the install exists.
- **Genuine skew still flagged:** a helper/agent/node-bin surface resolving to a root that is neither effective, nor a recognized inactive install, nor an in-tree checkout, classifies `stale-skew` and sets `hasSkew === true`.
- **`--strict`:** with an effective surface on a `local-dev` checkout while another effective surface is on the installed package, default mode is clean but `--strict` reports the divergence.

Dispatcher (with injected `cwd`/home/settings/trust):

- Invoked from a **trusted** project that overrides pi-flow, the dispatcher resolves the **project** effective core root.
- Invoked from a project with **no** pi-flow entry, it resolves the **user/global** core root.
- Invoked from an **untrusted** project that declares an override, it ignores the override and resolves the **user/global** core root.
- Resolves both aggregate and direct-core installs to the correct `bin/pi-flow.mjs` delegate.
- With no project override and a present user install, it delegates to the user core; it does not crash on a missing/malformed project `settings.json` or `trust.json`.

Rendering & fix:

- `/flow:doctor` output is visually clean (no `[SKEW]` rows) while both a user and a project pi-flow package are installed and the effective surfaces are aligned.
- The report uses the grouped layout with abbreviated paths and renders legibly without relying on a fixed terminal width; `--all` surfaces absent-candidate inventory.
- `/flow:doctor --fix` repairs only active/effective-scope surfaces, reaches a clean report without deleting any inactive install, and refreshes a stale installed dispatcher.
- The existing pi-flow test suite (`pnpm --filter @aphotic/pi-flow-core check`) passes after the change.

## Non-Goals

- Editing `.pi/settings.json`, installing packages, creating pin files, or deleting inactive installs from `/flow:doctor` (the read-only/never-delete boundary is preserved).
- Taking a runtime dependency on `@earendil-works/pi-coding-agent` package-manager/settings internals, or otherwise reimplementing full Pi package resolution beyond what doctor and the dispatcher need.
- Caching resolved dispatcher targets anywhere on disk.
- Full git/local package-source support in the dispatcher beyond the best-effort resolution described above (resolve when the declared root resolves to a usable core; otherwise fall back to user). A richer git-source story can follow later.
- Splitting the dispatcher into its own spec (declined — see Open Questions), or reworking `/flow:setup`'s agent-symlink semantics beyond the scope-awareness required here.
- A bordered-table report format.

## Open Questions

- **Single spec vs. split.** During design, a split was recommended — the scope-aware doctor diagnosis (effective model, classification, rendering, npm resolution) and the stable helper dispatcher are largely independent subsystems that run in different execution contexts and share only a conceptual model. The decision was to keep them in **one** spec. If implementation reveals the dispatcher workstream is large enough to sequence separately, it can be lifted into a companion spec without changing this design; the shared `.mjs` module is the natural seam.
- **Dispatcher source-of-truth refresh.** The installed dispatcher is a copy of the active package's bundled launcher. The exact staleness-detection mechanism (e.g. version stamp vs. content compare) and whether refresh is automatic on `/flow:setup` or only offered under `/flow:doctor --fix` should be pinned during implementation.
- **Local/git override resolution depth.** How far the dispatcher should resolve local/git package sources (vs. falling back to user) before this ships is left to implementation, bounded by the best-effort constraint above.
