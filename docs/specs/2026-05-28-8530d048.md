# Extract idea extension into its own package

Source: IDEA-8530d048

## Goal

Extract the idea extension from `@aphotic/pi-flow-core` into a standalone, publishable monorepo package named `@aphotic/pi-ideas`. The package should have no required dependency on pi-flow-core workflow commands. Work-menu actions, selector quick-key shortcuts, the refine prompt, and the slash-command name are driven by external JSON configuration files, allowing any consumer to plug into the ideas work menu without coding against the ideas package.

## Context

The idea extension currently lives in `packages/pi-flow-core/extensions/idea.ts` and `storage.ts`, registered via `commands.ts`. It has several hardcoded dependencies on pi-flow-core workflow concepts:

- `registerIdea` registers the idea-browser command as `flow:ideas` (invoked as `/flow:ideas`); the `flow:` namespace prefix is a pi-flow-specific convention baked into the ideas extension.
- `IdeaWorkSubmenuComponent` hardcodes four pi-flow skills: fastlane, scout, spec, plan.
- `IdeaWorkSubmenuHost.dispatch` types its parameter as `"fastlane" | "scout" | "spec" | "plan"` and the TUI constructs prompts using the `/flow:<skill> IDEA-<id>` pattern.
- `IdeaSelectorComponent` hardcodes three quick-key shortcuts (Ctrl+Shift+R refine, Ctrl+Shift+F fastlane, Ctrl+Shift+S spec) that bypass the action menu.
- The `IDEA_SELECTOR_HINT` constant hardcodes these shortcuts in the hint bar text.
- `buildRefineIdeaPrompt` hardcodes a 5-section body structure (Context, Goal, Scope, Acceptance Sketch, Open Questions) specific to the pi-flow workflow.
- `IDEA_TOOL_DESCRIPTION` and the tool's `promptSnippet` reference the same 5-section structure. In the pi extension model, `description` is the tool-definition description supplied to the LLM as the tool's authoritative purpose, and `promptSnippet` is a short one-line entry included in the default system prompt's Available tools section when the tool is active. Today both fields tell the assistant about the canonical 5-section idea body shape.

The monorepo currently has three packages: `@aphotic/pi-flow-core`, `@aphotic/pi-flow-ux`, and `@aphotic/pi-flow` (aggregate). The `@aphotic/pi-flow` aggregate lists extensions from its dependencies in its `package.json` `pi` section. The pi-flow workflow commands themselves (`flow:scout`, `flow:spec`, `flow:plan`, `flow:fastlane`, etc.) are registered separately in `workflow.ts` and remain in pi-flow-core.

## Requirements

- Create a dedicated workspace package named `@aphotic/pi-ideas` with publication-ready metadata, exports, dependency declarations, build configuration, and tests.
- Move the idea extension source (`idea.ts`, `storage.ts`), tests, and relevant package-level configuration into the new package.
- Remove all hardcoded references to pi-flow-core workflow commands, skill names, the `/flow:<skill>` prompt pattern, and the `flow:` slash-command namespace from the ideas package.
- The slash-command name under which the idea browser is registered is configurable through a top-level `command` field in the ideas config, resolved with project-over-global precedence (consistent with the file's overall project-over-global merge, like `refinePrompt`). The built-in default is `ideas` (invoked as `/ideas`), with no product-specific namespace prefix.
- The ideas package reads work-menu action configuration from JSON files at two scopes:
  - Global: `~/.pi/ideas.json`
  - Project: `<project-root>/.pi/ideas.json`
- Project configuration merges over global configuration following these rules:
  - Start with global actions in their declared order.
  - Process project entries sequentially: an object whose `name` starts with `-` removes the matching action from the merged result; an object with a matching name replaces the global action in place (preserving position); an object with a new name appends at the end.
- Each work-menu action is a JSON object with:
  - `name` (required): submenu label and merge key. A leading `-` signals negation (other fields ignored).
  - `prompt` (required for non-negation entries): free-form string inserted into the editor. The `${idea}` placeholder is replaced with the full `IDEA-<hex>` id of the selected idea.
  - `description` (optional): shown alongside the label in the work submenu.
  - `shortcut` (optional): displayed in the selector hint bar.
- The work submenu is hidden (and the `work` item removed from the action menu) when no work-menu actions are present after config resolution.
- Selector-level quick-key shortcuts for workflow actions are driven by the work-menu configuration: each action with a `shortcut` field registers both a selector key handler and a hint-bar entry. A maximum of 3 configured shortcuts are displayed in the hint bar (first 3 from config order).
- The built-in `Ctrl+Shift+R` refine shortcut on the selector remains a built-in, not driven by config.
- The hint bar is built dynamically: always starts with `↑↓ select • enter actions`, includes the built-in `ctrl+shift+r refine`, inserts configured action shortcuts (up to 3) in config order, and always ends with `esc close`. All hint bar text across all screens is lowercase.
- The action menu order is: view, refine, work (when configured), other, close/reopen.
- The refine prompt is overridable via a `refinePrompt` field in the config file. The `${idea}` placeholder receives the same substitution. The built-in default omits any body-section structure:
  ```
  Refine the idea ${idea}.

  Before rewriting or updating the idea, ask the user clarifying questions whose answers would materially change the artifact. Provide a recommendation for each question. Do not rewrite the idea body before the user answers.

  Once the user has answered enough, update the idea via the `idea` tool's `update` action.
  ```
- The default `IDEA_TOOL_DESCRIPTION` (the tool-definition description supplied to the LLM) and the tool's default `promptSnippet` (the one-line Available-tools entry shown in the default system prompt) must both be structure-neutral — they describe the tool's actions and identifier shape without prescribing the 5-section body structure. Pi-flow-core restores its section-specific guidance through configuration, so the section structure continues to reach the assistant on pi-flow installs.
- Update `@aphotic/pi-flow-core` to provide the existing workflow actions, the section-structured refine prompt, and the `flow:ideas` command name through a `.pi/ideas.json` config file (shipped as part of the pi-flow-core package or the pi-flow workspace).
- Update the `@aphotic/pi-flow` aggregate package to include `@aphotic/pi-ideas` as a dependency and wire its extension.
- Add minimal README/docs for configuring work-menu actions, including the required fields, `${idea}` placeholder behavior, optional shortcut display, the max-3 shortcut display limit, negation syntax, global/project merge behavior, the configurable command name, and no-actions submenu hiding behavior.
- Preserve current behavior for existing pi-flow workflows after configuration is wired through.
- Do not publish the package as part of this implementation.

## Constraints

- The ideas package must have no runtime dependency on `@aphotic/pi-flow-core` or any pi-flow-specific module.
- The ideas package's built-in default command name must be free of any product-specific namespace prefix (default `ideas`, not `flow:ideas`); consumers such as `@aphotic/pi-flow-core` opt into a namespaced command via configuration.
- The ideas package depends on `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui` as peer dependencies, consistent with the existing extension model.
- Configuration is read from the filesystem at extension registration time. No programmatic inter-extension configuration channel is required.
- The `${idea}` placeholder in prompt templates and the refine prompt expands to the full canonical `IDEA-<hex>` form (e.g., `IDEA-8530d048`), not the bare hex. Because `${…}` is shell parameter-expansion syntax, examples that show a prompt on a command line in docs/tests need standard shell quoting (single quotes or escaped `$`); inside JSON config files this is a non-issue.
- The negation convention (`-name` prefix on the `name` field) follows the spirit of Pi settings' `!`/`-` prefix exclusion patterns for arrays.

## Approach

**Chosen approach:** File-based configuration at `~/.pi/ideas.json` (global) and `<project-root>/.pi/ideas.json` (project), with merge semantics following Pi settings conventions. The ideas package reads and merges these files at registration time to build its work-menu actions, selector shortcuts, refine prompt, and command name.

**Why this over alternatives:** Zero coupling — any extension or user can contribute work-menu actions or rename the command by writing a JSON file without importing or coding against the ideas package. Follows existing Pi config patterns (global/project split, `-` prefix negation). Declarative and user-editable. No extension load-ordering concerns.

**Considered and rejected:**

- Library-first programmatic API (consumer calls `registerIdea(pi, config?)`) — requires consumers to import and code against the ideas package, defeating the goal of decoupled extensibility.
- Post-registration setter (ideas package exports a module-level `addWorkMenuActions()` function) — requires extension load ordering guarantees, introduces shared mutable module state, complicates testing.

## Acceptance Criteria

- The monorepo includes a standalone `@aphotic/pi-ideas` package in workspace configuration.
- The package is publishable/public-ready (correct metadata, exports, license), but no publication is performed.
- The ideas package does not import, require, or reference `pi-flow-core` workflow commands, skill names, the `flow:` command namespace, or private implementation paths.
- With no `ideas.json` config files present, the idea browser command registers as `ideas` (invoked as `/ideas`), the work submenu is hidden, no workflow quick-key shortcuts appear in the selector, and the refine prompt uses the structure-free default.
- A `command` field in the config overrides the default command name (e.g., `flow:ideas` registers the browser as `/flow:ideas`), with project config taking precedence over global.
- With a global `~/.pi/ideas.json` providing actions, the work submenu displays those actions, configured shortcuts appear in the selector, and prompt templates are inserted with `${idea}` correctly substituted.
- Project `.pi/ideas.json` correctly merges over global: negation entries remove actions, matching names replace in place, new names append.
- A project negation entry (e.g., `{ "name": "-fastlane" }`) successfully removes a globally configured action.
- The hint bar displays at most 3 configured shortcuts (first 3 from config order), with all text lowercase across all screens.
- The action menu order is: view, refine, work (when present), other, close/reopen.
- A `refinePrompt` field in the config overrides the built-in refine prompt, with `${idea}` substitution.
- With no consumer-supplied overrides, the idea tool's `description` and `promptSnippet` are structure-neutral (no 5-section body shape baked in).
- `@aphotic/pi-flow-core` supplies its existing four workflow actions (fastlane, scout, spec, plan), its section-structured refine prompt, and the `flow:ideas` command name through configuration, preserving current pi-flow behavior end-to-end (the idea browser remains `/flow:ideas`, and section-structure guidance still reaches the assistant via the tool description / prompt snippet on pi-flow installs).
- Relevant tests, type checks, and builds pass after the extraction.
- README/docs explain how to configure work-menu actions, including all fields, placeholder behavior, shortcut display limit, negation syntax, merge semantics, and the configurable command name.

## Non-Goals

- Publishing the `@aphotic/pi-ideas` package to a registry.
- Supporting configuration scopes beyond global (`~/.pi/ideas.json`) and project (`<project-root>/.pi/ideas.json`) — additional scopes (per-user-per-project, workspace, env-var override, etc.) are out of scope.
- Making the action menu items (view, refine, other, close/reopen) configurable — these are intrinsic to idea management.
- Hot-reloading config changes — config is read at extension registration time.
- Supporting placeholders other than `${idea}` (e.g., `${title}`, `${tags}`) — can be added later without breaking changes.

## Open Questions

- The `IDEA_TOOL_DESCRIPTION` and `promptSnippet` currently embed section structure. The default in `@aphotic/pi-ideas` should omit it, and `@aphotic/pi-flow-core` should restore it. The specific override mechanism (additional config fields such as `toolDescription` / `promptSnippet`, a single `ideaStructure` field that the package weaves into both, or another shape) is left to the planner.
- The exact top-level shape of the `ideas.json` file (e.g., an object carrying `actions`, `refinePrompt`, and `command`) and how `@aphotic/pi-flow-core` ships its config so it reaches the resolver alongside user-authored global/project files are left to the planner.
