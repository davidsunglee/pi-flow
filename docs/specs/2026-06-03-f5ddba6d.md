# Tidy startup header via pi-flow-ux

Source: IDEA-f5ddba6d

## Goal

Replace pi's visually busy startup surface with a calm, deterministic, terminal-width-responsive startup header owned by `@aphotic/pi-flow-ux`. The header supports three detail levels — `none` (logo/version plus session message), `compact` (one summary row per literal resource category), and `full` (exhaustive per-item listing, on demand only) — selected by a new `tui.json` setting `header.details` in combination with core pi's `quietStartup`, and surfaced through the existing `/tui` command. Resource data comes from a per-category, loaded-truth-first resolver built on pi 0.78.0's public extension APIs, with no factory execution and no upstream pi changes required.

## Context

**pi-flow-ux today** (`packages/pi-flow-ux/`):

- `extensions/header.ts` installs a custom header via `ctx.ui.setHeader` on every `session_start` (reinstalled per `extensions/index.ts`). It renders a gradient logo (4 variants from `tui.json` `header.logo`), a `version <X>` line, and a humanized reason line — `"hello"` (startup), `"a fresh start"` (new), `"session reloaded"` / `"session resumed"` / `"session forked"` (reload/resume/fork).
- `extensions/settings.ts` owns the `TuiSettingsStore` (`tui.json` at `~/.pi/agent/tui.json` with packaged defaults), its normalization pattern (invalid values fall back to defaults), and the `/tui` command with `key value=x` grammar (`/tui working indicator=…`, `/tui header logo=…`); bare `/tui` describes current settings.
- `extensions/editor.ts` routes the cwd border field through the `success` theme token (`BORDER_TOKENS.cwd`), and already instantiates the host's exported `SettingsManager` (`SettingsManager.create(cwd)`) — precedent for using exported host classes.
- `themes/nord.json` defines `mdHeading` = nord13 (subtle yellow) and `toolOutput` = nord4 (bright gray).

**Host behavior (pi 0.78.0)** — verified against the installed package's `.d.ts`/`dist`:

- The built-in header (logo + keybinding help) and the busy "loaded resources" listing (`showLoadedResources`: Context/Skills/Prompts/Extensions/Themes sections) are both gated on `!quietStartup` (or `--verbose`). The listing is printed into the **chat container**, separate from the header component; a custom header replaces only the header component, and extensions have **no API to suppress the chat listing**.
- `ExtensionContext` exposes no resource snapshot; the host's `resourceLoader` is unreachable from extensions.
- Available public building blocks: `pi.getCommands()` → `SlashCommandInfo { name, description?, source: "extension" | "prompt" | "skill", sourceInfo { path, source, scope, origin, baseDir? } }`; `ctx.ui.getAllThemes()` → `{ name, path: string | undefined }[]` (built-ins have no path); `ctx.ui.getTheme(name)` / `ctx.ui.theme`; `SettingsManager.getQuietStartup()` and `SettingsManager.getTheme()`; `loadProjectContextFiles({ cwd, agentDir })` (exported standalone, no loader needed) plus `getAgentDir()`; `DefaultPackageManager.resolve(onMissing?)` → `ResolvedPaths { extensions, skills, prompts, themes }` at entry-file granularity with `{ path, enabled, metadata }`, without executing extension factories. `DefaultResourceLoader.reload()` exists but executes factories, so it is not a safe inspection path.

**Why the modes are shaped this way:** when `quietStartup` is false the host's own busy listing always prints, so any pi-flow-ux summary would duplicate it ("everything displayed twice"). The calm compact experience is therefore reserved for `quietStartup: true`, where the host is silent and pi-flow-ux restores discoverability.

## Requirements

Settings and command surface:

1. `tui.json` `header` gains a `details` key with values `"none" | "compact"`. The code default is `compact`. Missing or invalid values normalize to the default, following the existing `normalizeTuiSettings` pattern; the existing `header.logo` setting is unaffected.
2. `/tui header details=none|compact` sets and persists the value with immediate header re-render, matching the existing `/tui` set-command behavior (notify on success, usage text on invalid value). The `/tui` usage text and the bare `/tui` settings description both include the new key.
3. Bare `/tui header details` (no `=`) prints the **full details view** into chat scrollback on demand. It works regardless of `quietStartup` or the configured `details` level.

Mode selection:

4. When core pi `quietStartup` is **false**, the startup header always renders the `none` level, regardless of `header.details`.
5. When `quietStartup` is **true**, the startup header renders the configured `header.details` level. `quietStartup` is read via the exported `SettingsManager`; pi-flow-ux never writes it.
6. The full level is never rendered automatically at startup; it is reachable only via the on-demand command.

Header content:

7. `none` level: logo (existing variant setting) and a version line formatted `v<version>` (e.g. `v0.78.0`, replacing the current `version <X>` wording). When the session start reason is `reload`, `resume`, or `fork`, a session message line follows (existing labels: `session reloaded` / `session resumed` / `session forked`). The `hello` and new-session messages are dropped entirely — no reason line for `startup` or `new`.
8. `compact` level: the `none` content, then a blank separator line, then one summary row per **non-empty** literal category in the fixed order `context`, `prompts`, `skills`, `extensions`, `themes`. Empty categories are omitted.
9. Every header and detail line (all levels, and the full view) carries a left margin of exactly two spaces, and one blank line follows the startup header block for breathing room.
10. The session message uses the same theme token family as the border editor's cwd field (currently `success`).

Compact rows:

11. Each compact row shows the category label followed by item names. Labels use the `mdHeading` token; item names use the `toolOutput` token.
12. Rows are terminal-width-responsive and never wrap: as many items as fit are shown, and a `+N` suffix is appended only when items were elided, where N is the number of hidden items. When all items fit, no suffix appears.
13. Context entries display as abbreviated paths (project-relative where applicable, `~` for home); skills, prompts, and extensions display as short human-recognizable names (bare names, no slash prefix); themes display as theme names.

Full details view:

14. The full view is exhaustive: a title line (`pi header details`), then every category — including empty ones, shown as `<name> (0)` with a `none` placeholder — with a per-category item count and every item on its own line. No `+N`, no `… N more`, no caps. Tall output is acceptable; chat scrollback is the display surface.
15. The full view has two layouts: a wide layout when usable width (terminal width minus margin) is ≥ 72 columns, which adds an indented source sub-line per item (owning package name or abbreviated path); and a narrow layout below that, which omits the sub-lines.

Themes category (both compact and full):

16. Only user-, project-, and package-provided themes are counted and listed; built-in themes are excluded, except that the active theme, if built-in, is included so the active state is explainable. The active theme is marked (e.g. `nord*` in compact, `nord *active` in full).

Data and lifecycle:

17. Resource data reflects the live session per the Approach section's per-category sources; data is refreshed on every `session_start` (including reload), and the on-demand full view reflects the current session state at invocation time.
18. The startup header renders immediately (logo/version/session message at minimum) without blocking on resource enumeration; rows backed by async sources may appear in a follow-up repaint, after which the header is stable for the session.
19. Output is deterministic: identical resources, settings, and terminal width produce identical output. Within-category ordering is stable and deterministic (exact ordering rule is the planner's choice).

## Constraints

- All implementation lives in `packages/pi-flow-ux`; no changes to core pi, `pi-flow-core`, or other packages.
- Never execute extension factories for inspection — `DefaultResourceLoader.reload()` (and instantiating the loader generally) is off limits.
- The resolver must never trigger package installs or network activity: `DefaultPackageManager.resolve()` must be invoked with an `onMissing` callback that answers `"skip"`.
- Core pi settings are read-only to this feature; `quietStartup` is never mutated, and the host's chat listing is not fought or suppressed by side effects.
- Only public, exported pi APIs may be used (peer dependency stays `@earendil-works/pi-coding-agent >= 0.78.0`).
- Existing `/tui` grammar and existing `tui.json` keys remain backward-compatible; existing saved files without `header.details` load cleanly.
- No semantic classification of skills/extensions — literal categories only.
- Compact rows must never wrap at any terminal width.

## Approach

**Chosen approach:** a per-category, loaded-truth-first best-effort resolver inside pi-flow-ux, using the most authoritative public source for each category:

| Category | Source | Fidelity |
| --- | --- | --- |
| skills | `pi.getCommands()` filtered to `source === "skill"` | loaded truth (includes `resources_discover` and temporary CLI contributions — they became commands) |
| prompts | `pi.getCommands()` filtered to `source === "prompt"` | loaded truth (same) |
| themes | `ctx.ui.getAllThemes()` (built-ins identified by `path === undefined`), active name via `SettingsManager.getTheme()` | loaded truth |
| context | `loadProjectContextFiles({ cwd, agentDir })` | deterministic re-discovery matching host behavior |
| extensions | `DefaultPackageManager.resolve()` extension entries (entry-file granularity, install-suppressed) | configured-not-loaded approximation |

**Why this over alternatives:** four of five categories are exact loaded truth; the building blocks are exported public API with in-repo precedent (`editor.ts` already instantiates `SettingsManager`); entry-file granularity is required to render nested packages (e.g. one configured `@aphotic/pi-flow` fanning out to `pi-flow-ux`, `pi-ideas`) as separate extension rows, which package-level `listConfiguredPackages()` cannot do; and nothing blocks on pi's release timeline. The single approximation — the extensions category lists configured entries, so it misses temporary `-e` CLI extensions and cannot distinguish load-failed extensions — is accepted and recorded as the upstream ask in Open Questions, with no special marking in the UI.

**Considered and rejected:**

- Upstream-first (request a readonly resource-snapshot API on `ExtensionContext` and gate compact/full on it) — exact parity for every category, but blocks the feature on a timeline this repo doesn't control.
- Extension-API-only (derive extensions from `getCommands()` `sourceInfo` alone, never instantiate host classes) — most stable surface, but silently omits extensions that register no commands, which is worse than an over-inclusive configured list.

## Acceptance Criteria

Behavior matrix:

| `quietStartup` | `header.details` | Startup header |
| --- | --- | --- |
| `false` | (ignored) | `none` content |
| `true` | `none` | `none` content |
| `true` | `compact` (default) | `none` content + compact category rows |
| any | any | full view only via bare `/tui header details` |

Observable outcomes:

- With `quietStartup: true` and defaults, a fresh startup shows the two-space-margined logo, `v<version>`, a blank line, compact rows for each non-empty category in canonical order, and a trailing blank line — with no `hello` line.
- With `quietStartup: false`, the header shows only logo/version (+ session message when applicable) even when `header.details=compact` is configured.
- After `/reload`, the header shows `session reloaded` colored with the border editor's cwd token family, and compact/full data reflects post-reload resources.
- `/tui header details=none` takes effect immediately, persists to `tui.json`, and survives restart; `/tui header details=bogus` prints usage and changes nothing; bare `/tui` output mentions `header.details`.
- Bare `/tui header details` prints the full view into chat: title line, all five categories with counts (empty ones as `(0)` / `none`), every item on its own line, source sub-lines present at ≥ 72 usable columns and absent below.
- Narrowing the terminal never wraps a compact row; elided items collapse into a correct `+N`; no `+N` appears when everything fits.
- Themes rows list non-built-in themes with the active theme marked; built-ins appear only when one is the active theme.
- A skill or prompt contributed via `resources_discover` or a temporary CLI flag appears in compact/full output (skills/prompts are loaded truth).
- Rendering the header twice with identical inputs yields byte-identical lines.

## Non-Goals

- No `details: "full"` configuration value — full is on-demand only. (Extending the enum later is backward-compatible if demand appears.)
- No suppression of, or interference with, the host's own `showLoadedResources` chat listing when `quietStartup` is false.
- No exact parity for the extensions category (configured vs loaded; temporary `-e` extensions missing) — accepted divergence, no special UI marking.
- No upstream pi API work in this spec; upstream asks are recorded as Open Questions only.
- No semantic classification or grouping of skills/extensions beyond the five literal categories.
- No interactive scrollable overlay for the full view — chat scrollback is the surface.
- No changes to the border editor, footer, working indicator, or logo variant system beyond the header content described here.
- No display of model scope, keybinding help, changelog, or other host startup output — only the five resource categories plus logo/version/session message.

## Open Questions

- **Upstream ask — readonly resource snapshot:** a small pi API (e.g. a readonly loaded-resource snapshot on `ExtensionContext`) would give exact parity for the extensions category (loaded vs configured, including temporary `-e` extensions and load failures). Worth requesting upstream; when it lands, the resolver's extensions source can be swapped without changing the header design.
- **Upstream ask — host listing integration:** there is no extension API to suppress the host's `showLoadedResources` chat listing when a custom header is installed. If pi ever offers one, the `quietStartup: false` path could also opt into the compact experience instead of being forced to `none`.
