# Restore Flow Ideas UX Parity with the Old Todos Tool

Source: IDEA-b14e6caf

## Goal

Restore the human-facing workflow ergonomics that were lost when Flow migrated from the old `todo` / `TODO-<id>` surface to the new `idea` / `IDEA-<id>` surface. Ship a `/flow:ideas` TUI browser/manager, expand the `idea` tool API with the missing actions and filters, add custom transcript rendering for the `idea` tool, and teach the LLM how to produce polished idea artifacts via a canonical 5-section body shape. Preserve Flow-specific semantics (`IDEA-<id>`, `docs/ideas/<id>.md`, durable artifacts) and deliberately drop old todo behaviors that don't fit durable intent artifacts (GC, locks, claim/release).

## Context

### Current state of the Ideas surface

Existing extension at `packages/pi-flow-core/extensions/`:

- `idea.ts` registers `/flow:idea` (raw direct capture: first-line title + remaining body) and the `idea` tool with only `list / read / create / update`. `list` rejects all filter fields, so `{ action: "list", status: "open" }` fails with `invalid fields for list: status` ([`idea.ts:91-100`](../../packages/pi-flow-core/extensions/idea.ts)).
- `storage.ts` provides `getIdeaDir / generateIdeaId / normalizeIdeaId / readIdea / writeIdea / listIdeas / parseIdeaArtifact / formatIdeaArtifact` and the `IdeaArtifact` type. `writeIdea` uses atomic temp-file + rename. `parseIdeaArtifact` hard-rejects any status other than `"open"` or `"done"` ([`storage.ts:89`](../../packages/pi-flow-core/extensions/storage.ts)).
- No transcript rendering for the `idea` tool — calls/results show with the default text renderer only.
- No TUI: nothing equivalent to old `/todos`.

### Existing Flow workflow plumbing this spec interacts with

- `workflow.ts` registers `/flow:scout / spec / plan / refine-plan / execute / refine-code / fastlane`; each routes through `router.ts:routeArgs` and dispatches the resolved prompt via `pi.sendUserMessage(...)`.
- `router.ts:EXACT_INPUT_MATRIX`: `scout`, `define-spec`, `generate-plan` accept `IDEA-<id>` in exact mode; `fastlane` does **not** (only `specs` exact-mode + `empty: true` freeform fallback). `/flow:fastlane IDEA-<id>` therefore routes through the interpreted-prompt path.
- `pi-tui` primitives (`Container`, `Input`, `SelectList`, `Markdown`, `DynamicBorder`, `Spacer`, `Text`, `TUI`, `fuzzyMatch`, `matchesKey`, `Key`, `keyHint`, `truncateToWidth`, `visibleWidth`) are available through the `@earendil-works/pi-coding-agent` re-exports used by the old todos extension.
- TUI primitives: `ctx.ui.custom()`, `ctx.ui.setEditorText(...)`, `ctx.ui.notify(...)`, `ctx.ui.input(...)`, `copyToClipboard(...)`, `getMarkdownTheme()`, `keybindings.matches(keyData, "tui.select.*")`.

### Old todos extension (reference)

`~/.pi-config/agent/extensions/todos.ts` — single-file ~2000 LOC extension that registered the `todo` tool with `list / list-all / get / create / update / append / delete / claim / release`, custom `renderCall`/`renderResult` formatters, and the `/todos` TUI. TUI composition: `TodoSelectorComponent` (search + list), `TodoActionMenuComponent` (modal), `TodoDeleteConfirmComponent` (yes/no), `TodoDetailOverlayComponent` (markdown overlay), driven by an `activeComponent` swap pattern wrapping `ctx.ui.custom()`. Storage at `.pi/todos/<id>.md` (with optional `PI_TODO_PATH` override), `<id>.lock` files (30-min TTL) gating mutations, `settings.json` configuring GC, `garbageCollectTodos` deleting closed todos older than `gcDays` on `session_start`. Handoffs prefilled the editor via `ctx.ui.setEditorText(...)`.

## Requirements

### Tool API (`idea` tool)

1. The tool exposes six actions: `list`, `read`, `create`, `update`, `append`, `delete`. No `list-all`, no `get` alias, no `claim`, no `release`.
2. The `list` action accepts two optional filters: `status` (`"open" | "closed" | "all"`, default `"open"`) and `query` (case-insensitive substring matched against `IDEA-<id>` + raw id + title + tags). Unknown fields produce an error message naming the offending fields (matching the existing rejection pattern).
3. The `read` action accepts `id` (`IDEA-<id>` or raw 8-hex), returns the full artifact including body.
4. The `create` action accepts `title` (required), `body`, `tags`, `status` (default `"open"`). Returns the new `IDEA-<id>` and absolute file path in the text content; the full artifact in `details`.
5. The `update` action accepts `id` (required) plus any subset of `title / body / tags / status`. Omitted fields are preserved.
6. The `append` action accepts `id` (required) and `body` (required). Appends to the existing body separated by a blank line (no separator if existing body is empty); preserves all other fields.
7. The `delete` action accepts `id` (required); removes the file; returns the deleted artifact in `details`.
8. All mutating actions return `details` containing the post-mutation (or deleted) artifact for custom rendering. The `list` action returns `details.list` as a flat array.
9. The tool's `description` and `promptSnippet` teach the LLM to (a) use this tool when the user asks naturally to capture or refine an idea, (b) author the body in the canonical 5-section shape (`## Context`, `## Goal`, `## Scope`, `## Acceptance Sketch`, `## Open Questions`), (c) ask one clarifying question only when missing info would materially change the artifact, otherwise create immediately and report the resulting `IDEA-<id>`.

### `/flow:idea` slash command

10. Existing raw-direct-capture behavior is preserved unchanged: first line of arguments → title, remaining lines → body. Empty arguments either prompt interactively via `ctx.ui.input` or print a usage error when `!ctx.hasUI`.
11. The command's `description` text is updated to explicitly spell out the title/body convention so it surfaces in slash-command help and completion.
12. No `--raw` flag; raw is the default and only behavior.

### `/flow:ideas` slash command (new)

13. With UI, opens a TUI browser/manager over `docs/ideas/*.md`.
14. Without UI, prints a grouped text list (Open ideas first, then Closed) using the same heading and item format as the renderer's expanded view.
15. Accepts an initial search query as positional argument. `/flow:ideas regression` populates the TUI search input (interactive) or filters the listing (non-interactive).
16. Accepts the flags `--open`, `--closed`, `--all` in non-interactive mode to scope the printed listing. Default is `--all` so the grouped-list output is identical to running `/flow:ideas` with no flags.

### TUI: list / selector

17. **Header** reads `Ideas (N open, M closed)` styled with the theme's `accent` + `bold` tokens.
18. **Search input** is a single-line text input; typing filters the visible list live. The search corpus per idea is the concatenation of `IDEA-<id>` + raw id + title + space-separated tags + status. Body content is **excluded** from the corpus. Multi-token fuzzy match via `pi-tui`'s `fuzzyMatch`; each token must match for the item to qualify, with scores summed for ranking.
19. **Sort order**: open ideas before closed ideas; within each group, chronological by `created_at`. When the search input is non-empty, the within-group secondary sort switches to ascending fuzzy score (best match first), matching old todos' filter-time sort behavior.
20. **Row rendering**: selection prefix (`→ ` selected, `  ` not), then `IDEA-<id>` (accent), then title (text or dim depending on status), then `[t1, t2]` tag suffix (muted) when tags present, then status suffix `(open)` / `(closed)` (success / dim). Closed ideas render dim across the row.
21. **Hint line** below the list reads: `Type to search • ↑↓ select • Enter actions • Ctrl+Shift+R refine • Ctrl+Shift+F fastlane • Ctrl+Shift+S spec • Esc close` (dim color).
22. **Quick keys fire directly from the list view** without opening the action menu: `Ctrl+Shift+R` dispatches refine on the selected idea; `Ctrl+Shift+F` dispatches fastlane; `Ctrl+Shift+S` dispatches spec. Implementation pattern matches old `Ctrl+Shift+W/R` handling at `todos.ts:427-436`.
23. **Initial selection** is the first item. Navigation uses the injected `keybindings.matches(keyData, "tui.select.up" | ".down" | ".confirm" | ".cancel" | ".pageUp" | ".pageDown")` matchers — not hard-coded escape sequences.
24. **Empty / no-match states**: when the on-disk set is empty, render `No ideas` (muted). When the on-disk set is non-empty but no items match the current search, render `No matching ideas` (muted).

### TUI: action menu

25. Selecting an idea (Enter or `tui.select.confirm`) opens an action menu with five top-level items, in this order:
    - `view`
    - `refine`
    - `work ▶` (submenu)
    - `close` (when status is `"open"`) or `reopen` (when status is `"closed"`)
    - `other ▶` (submenu)
26. The menu shape is identical for open and closed ideas; only the `close` ↔ `reopen` slot toggles based on status.
27. `view` opens the detail overlay (Requirements 32–35).
28. `refine` closes the TUI and prefills the editor with the canonical refine prompt (Requirement 36).
29. `work ▶` opens a nested submenu with four items in this order: `fastlane`, `scout`, `spec`, `plan`. The submenu's default-highlighted item is `fastlane` (first in the list). Selecting an item closes the TUI and prefills the editor with `/flow:<skill> IDEA-<id>` (e.g., `/flow:scout IDEA-abcd1234`).
30. `close` / `reopen` toggles the idea's `status` on disk via the storage helpers (equivalent to the tool's `update` action); the TUI refreshes the list in place and notifies `Closed idea IDEA-<id>` or `Reopened idea IDEA-<id>` via `ctx.ui.notify(..., "info")`. The action menu re-renders against the updated status (toggling the slot label).
31. `other ▶` opens a nested submenu with three items in this order: `copy path`, `copy text`, `delete`. 
    - `copy path` writes the absolute path of `docs/ideas/<id>.md` to the clipboard via `copyToClipboard` and notifies.
    - `copy text` writes `# <title>\n\n<body>` (or `# <title>` if body is empty) to the clipboard and notifies.
    - `delete` opens a yes/no confirm dialog reading `Delete idea IDEA-<id>? This cannot be undone.`. On yes, deletes the file via the storage helpers, refreshes the list, notifies `Deleted idea IDEA-<id>`, returns to the selector. On no, returns to the action menu.
32. The action menu and submenus are dismissed with `tui.select.cancel` (Esc), returning to the parent (top-level menu → selector; submenu → top-level menu). Submenus reuse the `activeComponent` swap pattern from old todos at [`todos.ts:1819-1837`](../../../pi-config/agent/extensions/todos.ts).

### TUI: detail overlay

33. Opened via the `view` action. Rendered as an overlay (`overlay: true`, `overlayOptions: { width: "80%", maxHeight: "80%", anchor: "center" }`) matching old `TodoDetailOverlayComponent`.
34. Shows the title centered in the top border, then a meta line with `IDEA-<id>` + status + tags (or `no tags`), then the body rendered as Markdown via `pi-tui`'s `Markdown` with the theme returned by `getMarkdownTheme()`.
35. Supports scrolling: `tui.select.up` / `tui.select.down` = single-line; `tui.select.pageUp` / `tui.select.pageDown` or `←` / `→` = one page. Footer indicates scroll position when content exceeds view height.
36. `Enter` (`tui.select.confirm`) closes the overlay and returns to the action menu — does **not** directly dispatch any action (unlike old todos, where Enter dispatched `work` directly). `Esc` (`tui.select.cancel`) also returns to the action menu.

### Refine prompt

37. The TUI's `refine` action and the `Ctrl+Shift+R` quick key both invoke a `buildRefineIdeaPrompt(id, title)` that produces a prefill mirroring old `buildRefinePrompt` at [`todos.ts:1115-1121`](../../../pi-config/agent/extensions/todos.ts), with these adaptations:
    - `task TODO-<id>` → `idea IDEA-<id>`
    - `the todo` → `the idea`
    - The clause `provide a recommendation for each question` is preserved verbatim.
    - An additional final sentence is appended: instruct the agent that when ready to draft the structured description, write it into the idea body using exactly these section headers in this order — `## Context`, `## Goal`, `## Scope`, `## Acceptance Sketch`, `## Open Questions` — and update the idea via the `idea` tool's `update` action when complete.

### Custom transcript renderers

38. The `idea` tool registers `renderCall` and `renderResult` callbacks (matching the old todos pattern at [`todos.ts:1716-1785`](../../../pi-config/agent/extensions/todos.ts)) using `details` for structured access.
39. `renderCall` produces a compact single-line `Text` reading `idea <action> IDEA-<id> "<title>"`. Any of action / id / title may be absent (rendered fields use accent/dim theming consistent with old todos).
40. `renderResult` for `list`: groups items into `Open ideas (N)` and `Closed ideas (M)` headers, shows up to 3 items per group when not expanded with a `... K more` muted line if truncated; when expanded, shows all items. Appends a `(<keyHint("app.tools.expand", "to expand")>)` hint when collapsed and there are hidden items.
41. `renderResult` for single-idea actions (`read`, `create`, `update`, `append`, `delete`): renders the idea heading (`IDEA-<id>` + title + tag suffix) on the first line. For `create`/`update`/`append`/`delete`, prepends a `✓ <Verb> ` prefix (`Created` / `Updated` / `Appended to` / `Deleted` — no `Claimed`/`Released`). When expanded, additionally renders status, tags, created timestamp, and body content.
42. `renderResult` for errors renders the error message in the theme's `error` color.

### Storage / schema

43. The `status` field accepts `"open"` and the canonical-going-forward `"closed"`, while remaining **read-tolerant** of `"done"` (existing files written by the current extension). `parseIdeaArtifact` accepts `"open" | "done" | "closed"`; on read, `"done"` is normalized internally to `"closed"`. `writeIdea` always serializes `"closed"` (never `"done"`).
44. The `IdeaArtifact` TypeScript type's `status` field becomes `"open" | "closed"` (post-normalization). Internal call sites that previously discriminated on `"done"` now discriminate on `"closed"`.
45. `storage.ts` is extended with helpers that the tool and TUI share:
    - An append-body helper that reads, appends with the blank-line separator rule, and writes atomically; returns the updated artifact or `undefined` if not found.
    - A delete helper that reads to capture the record, unlinks the file, and returns the deleted record or `undefined` if not found.
    - `listIdeas` is extended to optionally accept `{ status?, query? }` filters; existing zero-arg callers are unaffected.
46. The slash commands and the tool both use the storage helpers in `storage.ts`. No duplicate file parsing/writing logic.

### Backward compatibility

47. Existing `docs/ideas/*.md` files with `status: "done"` continue to parse, render in the TUI/renderer as `"closed"`, and are rewritten as `"closed"` the next time they are mutated. No standalone data-migration commit is required.
48. `parseIdeaArtifact` ignores (does not reject) unknown JSON fields it doesn't recognize, so future schema additions don't break existing files.

## Constraints

- Keep `IDEA-<id>` as the only accepted/displayed identifier prefix. Do not resurrect `TODO-<id>` parsing or display.
- Keep `docs/ideas/<id>.md` as the canonical storage location. No `.pi/todos/` fallback. No `PI_TODO_PATH`-equivalent environment variable override.
- Keep statuses to `"open"` and `"closed"` only (with `"done"` read-tolerance per Requirement 43).
- Do not add `assigned_to_session` metadata, `claim` / `release` actions, or `force` parameters. Lock files (`<id>.lock`) and `withTodoLock`-style wrappers are not ported.
- Do not auto-garbage-collect closed ideas at `session_start` or any other lifecycle hook. Ideas are durable artifacts.
- Do not introduce a `settings.json` file for the ideas surface.
- All TUI handoffs use `ctx.ui.setEditorText(...)`; none auto-send via `pi.sendUserMessage(...)`. Workflow handoffs prefill the slash-command form `/flow:<skill> IDEA-<id>` so dispatch round-trips through the existing `workflow.ts:handleWorkflowCommand`.
- Do not change the on-disk `IdeaArtifact` schema beyond the `"done"` → `"closed"` normalization. No new fields (priority, position, pinned, etc. — see Open Questions).
- TUI components use the injected `keybindings.matches(keyData, "tui.select.*")` matchers for navigation/confirm/cancel rather than hard-coded escape sequences, with the exception of the three quick-key shortcuts (`Ctrl+Shift+R`, `Ctrl+Shift+F`, `Ctrl+Shift+S`) which use `matchesKey(keyData, Key.ctrlShift(...))` directly.
- The `idea.ts` extension grows in place. Do not split it into multiple files or introduce a `packages/pi-flow-core/extensions/idea/` directory — that's a separate refactor concern.

## Acceptance Criteria

- A user runs `/flow:ideas` interactively and browses `docs/ideas/*.md` in a TUI whose visual structure (header counts, search input, sort, status coloring, hint line) matches the old `/todos` UI.
- From the TUI, a user can: search by id / title / tags / status (not body); open an action menu; view the markdown body in an overlay; close/reopen an idea; copy its path; copy `# title\n\nbody`; delete it with a yes/no confirm; and reach refine + the four workflow handoffs (`fastlane / scout / spec / plan`) via the `work ▶` submenu and `refine` top-level item.
- `Ctrl+Shift+R`, `Ctrl+Shift+F`, `Ctrl+Shift+S` from the list view prefill the editor with the corresponding handoff text and close the TUI.
- `/flow:ideas` in non-interactive mode prints a grouped text list. `/flow:ideas <query>` filters it; `--open` / `--closed` / `--all` flags scope the output.
- `/flow:idea <text>` continues to perform raw direct capture (first-line title convention) with no LLM elaboration, identical to today.
- `idea` tool `list` accepts `status: "open" | "closed" | "all"` and `query: <substring>` filters. `list-all`, `get`, `claim`, and `release` actions do not exist.
- `idea` tool `append` adds markdown to the body separated by a blank line; preserves all other fields.
- `idea` tool `delete` removes the file and returns the deleted record in `details`.
- The `idea` tool's `description` / `promptSnippet`, when read by an LLM responding to natural-language idea-capture requests, results in the tool being called with a body that uses the canonical 5-section shape.
- The refine prompt (TUI action and quick key) prefills text that (a) asks clarifying questions with a recommendation per question, (b) instructs the agent not to rewrite the idea body before user answers, (c) instructs the agent to eventually write into the canonical 5-section shape.
- The `idea` tool's transcript rendering shows: a compact call line; a grouped/expandable list result for `list`; and single-idea results with a success prefix for mutating actions (`✓ Created`, `✓ Updated`, `✓ Appended to`, `✓ Deleted`).
- An existing `docs/ideas/*.md` file with `status: "done"` parses, displays as "closed" in the TUI and renderer, and is rewritten with `status: "closed"` the next time it is mutated. No proactive migration commit is required.

## Non-Goals

- Implementing a priority field (`Low / Medium / High` or equivalent) on the idea schema or in the TUI. Deferred — see Open Questions.
- Implementing manual ordering of ideas (pinned boolean, fractional position field, separate manifest, or keyboard reorder mode). Deferred — see Open Questions.
- Porting old todos' `assigned_to_session` metadata, `claim` / `release` actions, lock files (`<id>.lock`, `withTodoLock`), `force` parameter, or stale-lock-steal confirmation flow.
- Porting old todos' `garbageCollectTodos` GC behavior, `settings.json`, or `PI_TODO_PATH`-equivalent env override.
- Changing `/flow:idea`'s existing raw-direct-capture behavior. No LLM-elaboration handoff. No `--raw` flag. No soft-deprecation.
- Splitting `idea.ts` into multiple files or introducing a `packages/pi-flow-core/extensions/idea/` directory.
- Fuzzy-search of body content in the TUI, or any body-content indexing.
- Auto-sending TUI handoffs via `pi.sendUserMessage(...)`. All TUI handoffs prefill the editor; the user presses Enter to dispatch.
- A one-shot data-migration commit rewriting existing `docs/ideas/*.md` files from `status: "done"` to `status: "closed"`. The read-tolerant + write-canonical approach is the only migration strategy.
- Conditionally hiding any action menu item based on idea status. The menu shape is identical for open and closed; only the `close` ↔ `reopen` label toggles.
- Resurrecting a flat menu (the old shape was 8-10 items at one level). The 5-top-level + 2-submenus structure is deliberate.

## Migration Parity Summary

Intentional differences from the old `~/.pi-config/agent/extensions/todos.ts` extension. Each entry is captured in Requirements / Constraints / Non-Goals above; this section is the cross-cutting map for reviewers and audit.

### Identity and storage

- `IDEA-<id>` and `docs/ideas/<id>.md` only; no `TODO-<id>`, no `.pi/todos/`, no `PI_TODO_PATH`-equivalent env override.
- On-disk status `"open"` / `"closed"`; read-tolerant of legacy `"done"`.
- No `assigned_to_session` field. No `.lock` files. No `settings.json`. No `garbageCollectTodos`. No "steal stale lock?" confirm dialog.

### Tool API

- Actions: `list / read / create / update / append / delete` (was: same set plus `list-all / get / claim / release`).
- `list` accepts `status` and `query` filters; previously rejected all fields. Default `status` is `"open"` for old todo parity.
- No `force` parameter.
- Tool description / promptSnippet rewritten to teach the canonical 5-section refine shape.

### Slash commands

- New `/flow:ideas` opens the TUI (was `/todos`).
- `/flow:idea <text>` keeps existing raw-direct-capture; description updated to spell out first-line-is-title convention. No `--raw` flag.

### TUI menu structure

- 5 top-level items with 2 submenus: `view / refine / work ▶ / close|reopen / other ▶` (was: flat 8-10 items).
- `work ▶` submenu: `fastlane / scout / spec / plan` (in that order; fastlane first by deliberate UX bias — default-highlighted item when submenu opens).
- `other ▶` submenu: `copy path / copy text / delete`.
- Old `work` top-level action removed (was: prefilled `work on todo TODO-<id> "<title>"`). The `work` name now identifies the workflow submenu category, not a direct action.
- Old `release` action removed (claim/release dropped at the tool layer).
- Detail-overlay Enter → back to action menu (was: dispatched `work` directly).
- Menu shape is identical for open and closed ideas; only `close` ↔ `reopen` slot toggles.

### Quick keys

- `Ctrl+Shift+R` = refine (preserved from old).
- `Ctrl+Shift+F` = fastlane (new).
- `Ctrl+Shift+S` = spec (new).
- `Ctrl+Shift+W` unbound (was: work; removed because the old `work` action no longer exists).

### Handoff mechanism

- All TUI handoffs prefill via `ctx.ui.setEditorText` (mechanism preserved from old). Content changes:
  - `refine` prefills `buildRefineIdeaPrompt` — long Q&A prompt with the preserved "provide a recommendation for each question" clause, plus a final sentence instructing the canonical 5-section body shape on completion.
  - `scout` / `spec` / `plan` / `fastlane` prefill the slash-command form `/flow:<skill> IDEA-<id>`. Dispatch round-trips through the existing `workflow.ts:handleWorkflowCommand`.

### TUI list / selector

- Header `Ideas (N open, M closed)` (was `Todos (N open, M closed)`).
- Hint line updated to reflect new quick keys.
- Sort: open before closed; within group, chronological by `created_at`; secondary fuzzy-score sort within group when search is active (was: open-assigned → open-unassigned → closed, since the assigned/unassigned distinction is gone).
- Search corpus: `IDEA-<id>` + raw id + title + tags + status (preserved-from-old shape; no body; no assignment text since claim/release dropped).
- Initial search query from command args preserved (`/flow:ideas <query>`).

### Tool result rendering

- `renderCall`: `idea <action> IDEA-<id> "<title>"` (relabeled from `todo <action> TODO-<id> "<title>"`).
- `renderResult` for `list`: grouped `Open ideas (N)` / `Closed ideas (M)` with collapsed/expandable per-group view (no `Assigned` group; relabeled).
- `renderResult` for mutating actions: success prefix `✓ Created` / `✓ Updated` / `✓ Appended to` / `✓ Deleted` (no `Claimed` / `Released`).

### Refine output shape

- Canonical 5-section idea body, Title Case: `## Context` / `## Goal` / `## Scope` / `## Acceptance Sketch` / `## Open Questions`. Section names align with spec section names where they overlap (`Context`, `Goal`, `Open Questions`), making the refine → spec handoff structurally consistent. Refine sketches; spec formalizes (`Requirements`, `Non-Goals`, and optional `Approach` are spec-only).

## Open Questions

1. **Priority field (`Low / Medium / High`).** Considered during design and deferred. Underlying user need: "important ideas should surface first when browsing." Approach considered: typed `priority` enum with default `Medium`, sort `status → priority → chronological`. Open risks: priority decay (everything ends up `High`), schema migration of existing files, expanded TUI surface for setting priority, expanded tool API for filtering/updating. Recommendation if revisited: design as its own spec after the restored TUI has shipped and observable friction confirms the need.
2. **Manual ordering of ideas.** Considered during design and deferred. Same underlying user need as priority. Storage approaches considered: (a) optional `pinned: boolean` per idea (lowest-cost; pinned items float to top of their status group, chronological within); (b) optional `position: number` field with fractional indexing supporting full keyboard reorder mode; (c) separate manifest file at `docs/ideas/.order.json` listing ordered ids. Each has real trade-offs (schema migration, multi-session race conditions, two-sources-of-truth). Recommendation if revisited: design as its own spec after a few weeks of using the restored TUI; pinned (a) is the most likely first step because it's a strict subset of any future positional scheme.
