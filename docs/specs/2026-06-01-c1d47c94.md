# Simplify pi-flow-ux around border status and unified TUI configuration

Source: IDEA-c1d47c94

## Goal

Redesign the `@aphotic/pi-flow-ux` package around a single, fixed UX model and a single small configuration surface. Border status is always on; Pi's duplicate default footer/status row and host working row are suppressed (activity is carried in the editor border); a custom header is added; the Nord theme ships as before; and all user-facing TUI options are configured through one command (`/tui`) and one file (`tui.json`). The current dual `status`/`working` extensions, their two config files (`status.json`, `working.json`), and two commands (`/status`, `/working`) collapse into one extension entrypoint with a flat top-level module layout. All status-placement switching and all per-state working *configuration* are removed. There are no legacy readers, migrations, aliases, or compatibility shims — this is an intentional breaking change, and the owner controls all deployments.

## Context

The package lives at `packages/pi-flow-ux/` and today exposes **two** extension entrypoints, both listed in its `package.json` `pi.extensions` and forwarded by the aggregate `@aphotic/pi-flow` `package.json`:

- `extensions/status/` — `index.ts` registers a `StatusCoordinator` (`status.ts`) that installs exactly one of three mutually-exclusive placements: `border` (the `CustomEditor` subclass in `border-status.ts`, paired with `blank-footer.ts` to blank Pi's default footer), `footer` (a custom footer in `footer.ts`), or `off`. Placement is driven by `status.json` (`{ "placement": "border" | "footer" | "off" }`), a three-tier config loader, and the `/status` command. `StatusPlacement`, the renderer-installer plumbing (`StatusInstallers`, `StatusRendererHandle`, `composeHandles`), and the coordinator registry all support this switching.
- `extensions/working/` — `index.ts` registers `indicator.ts` and `message.ts`. `working.ts` holds the `WorkingCoordinator` that tracks active-turn / tool-use / thinking state from Pi events and exposes a `WorkingSnapshot` (currently including `borderOwned`). Working settings (`working.json`) carry per-state `WorkingStyle` objects (`color`, `gleam`, `rainbow`) for `active`/`toolUse`/`thinking` plus `indicatorShape`, mutated via the `/working` command. `effects.ts` holds pure visual helpers (`buildWorkingIndicator`, `pickWorkingIndicatorFrame`, `styleIndicatorFrame`, gleam/rainbow/colour math). The working-message catalog lives in `messages.ts` (`WORKING_MESSAGES`, `pickRandomWorkingMessage`).

The border editor (`border-status.ts`) consumes the working snapshot to draw a compact activity slot just left of the model id, plus model id, optional thinking level, context token-window + percentage, and cwd, with responsive priority-drop rules; it runs its own animation timer keyed to the indicator cadence. Today the activity glyph is styled **per state** (effectively: `active` plain, `toolUse` gleam, `thinking` gleam+rainbow under the packaged Nord defaults).

Pi API surface confirmed against `@earendil-works/pi-coding-agent@0.75.x`:

- `ctx.ui.setHeader((tui, theme) => Component & { dispose?() })`, `ctx.ui.setFooter(...)`, `ctx.ui.setEditorComponent(...)`, `ctx.ui.setWorkingIndicator(...)` all exist.
- `ctx.hasUI` boolean exists (false in print/RPC mode).
- `VERSION` is exported from `@earendil-works/pi-coding-agent`.
- The `session_start` event carries `reason: "startup" | "reload" | "new" | "resume" | "fork"` — this is the "startup reason."
- Pi does **not** export a gradient-logo helper; only `VERSION` is available.

Both packages are published at `0.7.0`. The owner controls all deployments and accepts breaking changes with no backward compatibility.

## Requirements

Each requirement below is verifiable.

### Package structure and manifests

- Collapse to a single extension entrypoint `extensions/index.ts` that explicitly registers the UX pieces.
- Adopt a flat top-level module layout under `extensions/`:
  - `editor.ts` — the always-on border-status editor (today's `border-status.ts` behavior).
  - `footer.ts` — blank footer / default-footer suppression (today's `blank-footer.ts` behavior).
  - `working.ts` — working state tracking + `tui.json` config + the `/tui` command.
  - `header.ts` — the custom startup header.
  - `effects.ts` — pure, hardcoded visual effects (indicator frames, gleam, rainbow, time-based frame helpers).
  - `working-messages.ts` — the retained working-message catalog (not rendered initially).
- `packages/pi-flow-ux/package.json`: `pi.extensions` is exactly `["extensions/index.ts"]`; `pi.themes` stays `["themes"]`. Update `files` to drop `working.json`/`status.json` and include `tui.json`. Update the package `description` to the simplified model.
- Aggregate `@aphotic/pi-flow` `package.json` forwards only `node_modules/@aphotic/pi-flow-ux/extensions/index.ts` (extensions) and `node_modules/@aphotic/pi-flow-ux/themes/nord.json` (themes).

### Remove status-placement complexity

- Delete `/status`, `status.json`, the `StatusPlacement` type, the `StatusCoordinator` and its renderer-installer plumbing, and the custom-footer placement renderer.
- Border status is always installed when the package loads, paired with a blank footer that suppresses Pi's built-in footer so metadata is not duplicated.
- The border always draws: lower-left activity slot + model id + optional thinking level (only when reasoning is enabled); lower-right context token/window detail + context percentage (percentage rightmost); upper-right cwd with `~` home substitution and tail truncation; vertical editor edges and the existing responsive truncation/drop rules.

### Unified TUI config (`tui.json`)

- Replace `working.json` and `status.json` with a single `tui.json`.
- Canonical packaged/user shape:
  ```json
  { "version": 1, "working": { "indicator": "wave" }, "header": {}, "editor": {}, "footer": {} }
  ```
  Only `working.indicator` is meaningful initially. The empty `header`/`editor`/`footer` objects are placeholders, not active toggles.
- Valid indicator values: `dot | pulse | spinner | wave`. Packaged default and code fallback default are **both** `wave`.
- Resolution order: user `~/.pi/agent/tui.json` → packaged `tui.json` → code default.
- Failure semantics: missing user file → packaged default; malformed user file → packaged default; missing packaged file → code default; malformed packaged file → throw loudly.
- Do not read, write, migrate, or honor `status.json`, `working.json`, `indicatorShape`, `/status`, `/working`, dotted `/tui working.indicator=...`, short `/tui indicator=...`, or any other legacy alias/compatibility form.

### `/tui` command

- Subcommand syntax only:
  - `/tui` — reports current TUI settings.
  - `/tui working indicator=<dot|pulse|spinner|wave>` — updates `working.indicator`, applies immediately, and persists atomically to `~/.pi/agent/tui.json`.
  - Invalid input shows concise usage.
- No component on/off toggles. Loading the package means the UX is enabled.

### Working behavior simplification

- Keep: event tracking for active turn, tool use, and thinking; indicator-shape selection; border activity-slot animation; a queryable working snapshot; and the working-message catalog (in its own module).
- Remove from user configuration and from the initial runtime UI: per-state colors; per-state gleam/rainbow toggles; the `active`/`toolUse`/`thinking` style objects; the `/working` command; separately-rendered host working indicator/message surfaces; and any initial working-message display.
- `working.ts` suppresses Pi's normal working row while `pi-flow-ux` is installed (activity is represented in the editor border).
- The snapshot exposes at least: `{ visible: boolean, state: "active" | "toolUse" | "thinking", settings: { working: { indicator } } }`. (`borderOwned` is no longer needed because the border always owns the indicator.)

### Activity visual effects

- Responsibility split: `working.ts` = state/config (what is happening, which indicator is selected); `effects.ts` = pure hardcoded visuals (indicator frames, gleam, rainbow, time-based frame helpers), with colors hardcoded and independent of the Nord or any active theme; `editor.ts` = placement/composition (apply effects to the model/thinking text in the border lines, using the working snapshot to decide where).
- Hardcoded effect rules:
  - While any activity is happening (snapshot visible): the model name gleams; no rainbow on the model name.
  - Only while thinking: the thinking-level text gets a rainbow; no gleam on the thinking-level text.
  - During tool use: the model gleams; the thinking level stays normal/muted if displayed.
  - During idle: no gleam, no rainbow; the activity slot returns to border-fill dashes.
- The **activity-slot glyph itself retains today's per-state visual treatment** — `active` = plain accent, `toolUse` = gleam, `thinking` = gleam+rainbow — but these per-state styles are now **hardcoded constants in `effects.ts`**, no longer read from configuration. `pickWorkingIndicatorFrame(indicator, state, nowMs)` uses `state` to select both the animation frame and its hardcoded styling.
- The editor render timer must run whenever `snapshot.visible` is true (not only when the selected indicator has multiple frames), so static indicators such as `dot` still drive the model-gleam / thinking-rainbow redraw cadence.

### Header

- Install a custom header via `ctx.ui.setHeader(...)` on `session_start`, guarded by `ctx.hasUI`.
- Content, left-justified (not centered):
  - the pi gradient logo;
  - a blank line;
  - `version <VERSION>` (e.g. `version 0.78.0`), with `VERSION` from `@earendil-works/pi-coding-agent`;
  - the startup reason rendered as a **humanized phrase** via a small hardcoded `reason` → label map covering `startup | reload | new | resume | fork` (exact wording is editorial).
- The logo art is **ported/adapted from pi-powerline's `extensions/header.ts`** (the named reference), stripped of powerline toggles/diagnostics and re-justified left.
- The header has no Nord-theme coupling and must not introduce: `/powerline` settings/events; header on/off toggles; diagnostics/scanning; `quietStartup`; a `/builtin-header` restore command; or broad synchronous filesystem scans.

### Docs and tests

- Update README/package docs to describe the simplified UX model and remove all mention of status placement, footer mode, `/status`, `/working`, `status.json`, and `working.json`.
- Update tests to reflect the single-entrypoint structure, the removed configs/commands, `tui.json`, and `/tui` behavior.

## Constraints

- No legacy readers, migrations, aliases, or compatibility shims for old files, commands, field names, or placement modes. Pre-existing user `~/.pi/agent/status.json` and `~/.pi/agent/working.json` files are neither read nor deleted — they are simply ignored.
- This is an intentional breaking change to published packages; backward compatibility is explicitly not required (the owner controls all deployments and will change configurations directly).
- Effect colors are hardcoded in `effects.ts` and do not reflect the Nord theme or any active theme.
- Preserve the existing responsive border behavior: priority drop order (token window first, then thinking level), tail-truncated cwd that is never dropped, and model id + context percentage always kept (truncated only as a last resort).
- The activity slot uses single-width glyphs only and keeps a constant visible width across frames, so the model column never jitters between idle and active.
- The gradient logo depends on pi-powerline's `extensions/header.ts` being available to the implementer (the owner will provide it); if it proves unavailable, fall back to a hand-rolled pi gradient wordmark.

## Acceptance Criteria

- `packages/pi-flow-ux/package.json` exposes only `extensions/index.ts` for UX extensions; the aggregate `@aphotic/pi-flow` forwards only that entrypoint plus `themes/nord.json`.
- `status.json` and `working.json` are gone from the package and no runtime code reads them.
- `/status` and `/working` are no longer registered.
- `/tui` is registered and: reports current settings; updates `working.indicator` to `dot`, `pulse`, `spinner`, or `wave` via `/tui working indicator=<shape>`; and persists to `~/.pi/agent/tui.json`.
- Dotted/short forms such as `/tui working.indicator=wave` and `/tui indicator=wave` are rejected.
- `tui.json` exists at the package root with `version: 1` and `working.indicator` defaulting to `wave`; the code fallback default is also `wave`.
- No legacy compatibility code exists for old files, commands, field names, or placement modes.
- Border status is always active when the package loads; Pi's duplicate default footer/status surface is suppressed; Pi's host working row is suppressed.
- The editor border still shows activity, model, thinking level, context usage, and cwd with the existing responsive behavior.
- During any activity the model name gleams; during thinking the thinking-level text is rainbow without gleam; tool use and ordinary active work do not rainbow the model or thinking-level text.
- The activity-slot glyph keeps today's per-state treatment (active plain, tool-use gleam, thinking gleam+rainbow), now sourced from hardcoded constants in `effects.ts`.
- Static indicators such as `dot` still animate the model gleam / thinking rainbow while activity is visible.
- Pure hardcoded visuals live in `effects.ts`; working state/config logic lives in `working.ts`; the working-message catalog lives in a separate module (e.g. `working-messages.ts`) and no working message renders initially.
- A custom header is installed via `setHeader`, guarded by `ctx.hasUI`, with a left-justified pi gradient logo (ported from pi-powerline), a blank line, `version <VERSION>`, and a humanized startup-reason line; it brings in no powerline settings, toggles, diagnostics, or filesystem scanning.
- README/package docs describe the simplified model and no longer mention status placement, footer mode, `/status`, `/working`, `status.json`, or `working.json`.
- Tests reflect the new single-entrypoint structure, the removed configs/commands, `tui.json`, and `/tui` behavior.

## Non-Goals

- Backward compatibility, migrations, or cleanup/deletion of pre-existing user config files.
- Component on/off toggles in `/tui` (e.g. `header:on`, `footer:off`).
- Rendering working messages anywhere in the initial UI; the catalog is retained only for a future placement decision, which would itself fit under the `tui.json` / `/tui` model.
- Powerline-style behavior: `/powerline` settings/events, diagnostics/scanning, `quietStartup`, `/builtin-header`, broad synchronous filesystem scans.
- Release/versioning mechanics (semver bump, changesets, publishing) — handled by the existing release process, outside this spec.
- Tying effect colors to the Nord theme or any active theme.

## Open Questions

- The exact humanized wording for each startup-reason token (`startup | reload | new | resume | fork`) is editorial and left to the planner/implementer; the requirement is "a humanized phrase," not specific strings.
- The header depends on pi-powerline's `extensions/header.ts` logo art being in hand before implementation; if it cannot be obtained, a hand-rolled pi gradient wordmark is the agreed fallback.
