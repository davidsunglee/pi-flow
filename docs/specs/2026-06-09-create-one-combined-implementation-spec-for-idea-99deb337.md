# Test-runner file-write contract fix + verifier protocol-tolerant PASS path

## Goal

One coordinated change that removes two sources of false-failure friction in the pi-flow execution pipeline. First, make the `test-runner` agent and its dispatched prompt internally consistent about file writes: the temporary-script-file recommendation conflicts with the exactly-one-artifact-write rule, leaving subagents with contradictory instructions. Second, add a deterministic tolerant path to execute-plan verifier-report parsing so that a report containing clear, complete, auditable PASS evidence for every acceptance criterion is not rejected — and retries are not burned — solely because the report's syntax deviates from the strict format. Both changes preserve the fail-closed safety posture: ambiguous or missing evidence still fails, and no LLM or orchestrator judgment is introduced anywhere in either path.

This spec combines two ideas at the user's direction:

- IDEA-99deb337 — Resolve test-runner temp-file artifact contract conflict (scout brief: `docs/briefs/IDEA-99deb337-brief.md`)
- IDEA-4e20148e — Add verifier protocol-repair path for clear substantive PASS evidence (scout brief: `docs/briefs/IDEA-4e20148e-brief.md`)

## Context

**Test-runner subsystem.** `packages/pi-flow-core/agents/test-runner.md` Execution step 2 lists, as the *preferred* mechanism, writing `## Test Command` verbatim to a temporary script file and executing it with `bash <script>`; piping the command into `bash` via stdin/heredoc is listed second. But the same file's `## Rules` section mandates "exactly ONE write to `## Artifact Output Path` per dispatch. Do not append, overwrite, or write to any other path," and the dispatched prompt template `packages/pi-flow-core/skills/_shared/test-runner-prompt.md` likewise says "Do NOT modify any other file." Both files are visible to the subagent simultaneously (the agent definition is appended to the system prompt; the prompt is the task body), so the temp-file recommendation directly contradicts the single-write rule. A second latent ambiguity: both files say "do NOT run any command other than the supplied test command," which a literal reader could take to forbid invoking `bash` at all as the execution vehicle. No existing test covers the file-write contract: `test_marker_emit_contract.py` (which already reads both files) covers marker naming, `test_completion_protocol_contract.py` covers completion wording, `test_test_runner_prompt_assembly.py` covers placeholder fill, and `__tests__/guardrail-strings.test.mjs` does not read agent definitions. The artifact format, `parse-test-runner-artifact.py`, the `TEST_RESULT_ARTIFACT` marker, and caller-side reconciliation are all unaffected by the execution-mechanism choice.

**Verifier subsystem.** `packages/pi-flow-core/skills/execute-plan/scripts/parse-verifier-report.py` is strict everywhere: per-criterion headers must match `[Criterion N] PASS|FAIL` exactly (uppercase token, no trailing tokens, no `verdict:` prefix), the overall verdict must be exactly `VERDICT: PASS|FAIL`, Phase 1 evidence `command:` fields must byte-equal the recipe strings supplied via `--phase1-recipes-json`, and the final-verdict logic forces `"verdict": "FAIL"` whenever `protocol_errors` is non-empty. `skills/execute-plan/SKILL.md` Step 11.2 routes any FAIL — including pure formatting defects — into Step 13's retry loop ("Protocol errors never pass"), and `acceptance-criteria-verification.md` step f repeats this. Step 13 offers 3 automatic retries then a menu with only `(r) Retry` / `(x) Stop`; there is no path to amend a defective `Verify:` recipe, so a plan whose recipe is itself broken dead-ends at retry-or-stop. The result is the reproducible `f6eac473` failure mode: a verifier explicitly marks every criterion PASS with successful command evidence and an overall PASS summary, yet execute-plan redispatches solely to repair report syntax. The parser is fence-aware (via `_shared/scripts/fence_aware.py`); `--phase1-recipes-json` is optional and the no-flag path performs no command validation. `skills/_shared/orchestrator-verification-boundary.md` lists `parse-verifier-report.py` as a sanctioned mechanical helper and forbids the orchestrator from inspecting implementation files, synthesizing evidence, or overriding verdicts; it forbids orchestrator-initiated plan edits but not user-directed ones. Existing tests in `test_parse_verifier_report.py` assert strict FAIL for lowercase verdicts, extra tokens, command mismatches, and similar formatting defects, alongside fixtures for each report shape.

The change targets are the source package under `packages/pi-flow-core/`; the installed copy under `packages/pi-flow/node_modules/@aphotic/pi-flow-core/` is refreshed by `pnpm install` and is not edited directly.

## Requirements

### Part A — test-runner file-write contract (IDEA-99deb337)

- A1. `agents/test-runner.md` no longer recommends, mentions, or permits writing the test command to a temporary script file (or any other filesystem path besides the artifact). Feeding the command to `bash` via stdin/heredoc — or an equivalent mechanism that creates no filesystem artifact — becomes the sole sanctioned execution mechanism.
- A2. The byte-preservation guarantee is retained: the instructions still require that the bytes of `## Test Command` reach `bash` unchanged — no added quoting, no escaping, no substitution, stderr merged into stdout — and still explain how to achieve this without a temp file.
- A3. The execution guidance addresses heredoc-delimiter collision (a supplied command containing the delimiter string would truncate the heredoc), e.g. by recommending a collision-resistant delimiter choice. The exact delimiter wording is the implementer's choice.
- A4. Both `agents/test-runner.md` and `skills/_shared/test-runner-prompt.md` explicitly resolve the "no other command" ambiguity: invoking `bash` via stdin/heredoc to execute the supplied test command is the sanctioned mechanism for running that command, not a forbidden "other command"; ephemeral shell constructs that create no filesystem artifacts are allowed. The prohibition continues to cover unrelated commands (`git`, `mkdir`, ad hoc reads, etc.).
- A5. After the change, the agent definition and the prompt template agree on the file-write contract with no remaining contradiction: exactly one durable write per dispatch, to `## Artifact Output Path`, and no other file created or modified.
- A6. The artifact format, header order, `parse-test-runner-artifact.py` contract, `TEST_RESULT_ARTIFACT` marker/completion protocol, and caller-side reconciliation behavior are byte-level unchanged by this part.
- A7. Regression coverage exists that fails if contradictory temp-file guidance is reintroduced: a test reads both files and asserts (at minimum) the absence of temp-script-file guidance and the presence of the single-artifact-write rule in each. Wording-brittleness is minimized by asserting the forbidden phrase's absence rather than demanding one specific positive phrasing.
- A8. All new/changed wording stays backend-neutral — no assumptions about a specific CLI or invocation model beyond the already-declared `bash`, `write`, `read` tools.

### Part B — verifier protocol-tolerant PASS path (IDEA-4e20148e)

- B1. Strict parsing remains the primary path in `parse-verifier-report.py`: a report in the exact legacy format produces byte-for-byte the same JSON result and exit code as today.
- B2. The parser gains a deterministic second classification pass (no new script, no subagent): when strict parsing surfaces defects, each defect is classified as **protocol-only** or **substantive**. The report yields a semantic PASS with protocol warnings if and only if *all* defects are protocol-only *and* the substantive-evidence bar in B3 is fully met. Any substantive defect, or any failure of the B3 bar, forces FAIL exactly as today.
- B3. Substantive-evidence bar for a semantic PASS: every criterion 1..K is present exactly once with an unambiguous PASS verdict; every command-style criterion (when `--phase1-recipes-json` is supplied) has an evidence block whose `command` matches its recipe under the B5 rule and whose `exit_code` parses as integer 0; an unambiguous overall-PASS verdict line is present; no criterion, verdict, or required evidence is missing, duplicated, out-of-range, or ambiguous.
- B4. The protocol-only defect set is an explicit, closed, deterministic enumeration — mechanically checkable, no semantic judgment. It covers at least: per-criterion verdict token differing from `PASS`/`FAIL` only by letter case; extra trailing tokens after an otherwise-unambiguous verdict token; the forbidden `verdict:` prefix form where the verdict value is unambiguously PASS/FAIL; overall `VERDICT:` line differing only by token case or trailing annotation; and missing `stdout:`/`stderr:` field labels in an evidence block whose `command` and `exit_code` satisfy B3. Defects that always remain substantive (hard FAIL) include at least: missing, duplicate, or out-of-range criterion headers; any criterion verdict that is FAIL or not case-insensitively PASS/FAIL (e.g. `passed`, `OK`); a missing overall verdict line, or one whose token is not case-insensitively PASS/FAIL; missing evidence block for a command-style criterion; missing or non-zero or unparseable `exit_code`; missing `command` field; and evidence commands matching no recipe under B5.
- B5. Command-field tolerance is mechanical only: an evidence `command` matches a recipe when it is byte-equal after stripping leading/trailing whitespace from both. Any other difference — paraphrase, flag change, path change, internal whitespace change — remains a hard FAIL. The no-`--phase1-recipes-json` path is unchanged.
- B6. The parser's JSON output and exit code distinguish three outcomes unambiguously: strict PASS, semantic PASS with protocol warnings (warnings listed), and hard FAIL (errors listed). Exact field naming/shape is the planner's call, subject to B1's backward compatibility for strict-format reports.
- B7. The orchestrator accepts a semantic PASS with protocol warnings **automatically** — no user confirmation gate — and surfaces the warnings prominently in its output for that task. `SKILL.md` Step 11.2 and `acceptance-criteria-verification.md` are updated so routing reflects this: protocol-only-with-full-evidence passes; everything else still routes to Step 13. The updated docs explicitly reaffirm that the orchestrator may only run the sanctioned parser over verifier-produced output and may never inspect implementation files, reinterpret ambiguous reports, or create evidence.
- B8. Step 13 gains a user-gated recipe-amendment escape hatch: when verification fails and the evidence indicates the `Verify:` recipe itself is defective (e.g. it ran byte-equal and failed for recipe reasons, or the verifier reports it unrunnable), the failure menu offers an option for the user to supply or approve a corrected recipe; the orchestrator then mechanically updates the plan file with the user-approved recipe and redispatches the verifier with it. The docs frame this as user-directed (the user authorizes the change to what "verified" means), keeping it inside the orchestrator-verification boundary.
- B9. Tests cover, at minimum: exact legacy PASS and FAIL formats (unchanged behavior); a constructed `f6eac473`-style fixture (all criteria explicitly PASS, successful command evidence, human-readable formatting) yielding a semantic PASS with warnings and no redispatch; each tolerated variant in B4 individually; command surrounding-whitespace tolerance; and hard-FAIL preservation for paraphrased commands, missing criteria, missing evidence blocks, failing exit codes, ambiguous verdict tokens, duplicate/out-of-range headers, and per-criterion FAIL overriding overall PASS. Existing strict-FAIL tests for now-tolerated variants are updated deliberately to assert the new classification; fence-aware tests continue to pass.

## Constraints

- Fail-closed stays the default. Tolerance exists only through the closed, enumerated, deterministic rules in B4/B5 — no fuzzy matching beyond them, no LLM judgment, no reformatter subagent, no orchestrator reinterpretation of ambiguous output.
- The orchestrator-verification boundary is not weakened: the orchestrator never inspects implementation files to form verdicts, never synthesizes or edits evidence, and never overrides parser output. The only plan edit introduced is the user-directed recipe amendment in B8.
- Backward compatibility: strict-format verifier reports parse identically (JSON and exit code); the parser's existing CLI flags keep their semantics; `--phase1-recipes-json` remains optional with the no-flag path untouched.
- Fence-aware parsing discipline (`compute_in_fence_lines`, `split_h2_sections`) is preserved; the tolerant pass must not treat fenced payload as structure.
- The test-runner artifact format, parser, marker contract, and `test-runner-dispatch.md` four-input protocol are unchanged; Part A touches instruction wording and tests only.
- Edits land in the source package `packages/pi-flow-core/` only; the installed `node_modules` copy is refreshed by normal install, not hand-edited.
- The `verify-task-prompt.md` "BYTE-EQUAL VERBATIM" instruction to the verifier stays — tolerance is for parsing what came back, not a license for verifiers to deviate.

## Approach

**Chosen approach:** In-parser tolerant classification. `parse-verifier-report.py` itself gains the deterministic second pass that classifies defects as protocol-only vs. substantive and emits the semantic-PASS-with-warnings outcome; the orchestrator consumes the richer result from the same single sanctioned helper it already calls. The Step 13 recipe-amendment option is a documentation/routing change in `SKILL.md`, not a new script or subagent.

**Why this over alternatives:** The entire safety guarantee is an enumeration — exactly which defects are protocol-only and exactly what substantive evidence must be present. That enumeration is safest living in one deterministic, exhaustively fixture-tested script whose output the orchestrator already routes mechanically; no new orchestrator routing step, no second parsing implementation, no non-determinism.

**Considered and rejected:**

- Separate deterministic repair script (`repair-verifier-report.py`) feeding the unchanged strict parser — splits the same enumeration across two scripts, duplicates fence-aware parsing, and adds a conditional two-step routing dance in SKILL.md for no safety gain.
- LLM reformatter subagent — handles arbitrary prose but is non-deterministic, introduces the evidence-alteration risk the verification boundary exists to prevent, and costs a dispatch per repair.
- User-confirmation gate before accepting a semantic PASS — re-introduces the interruption cost the idea exists to remove; safety comes from the narrow tested enumeration, not a prompt.
- Semantic command-equivalence tolerance — would require parser heuristics or LLM judgment of whether a tweaked command "counts," silently weakening the plan's verification contract; the user-gated B8 amendment path covers the broken-recipe case with explicit authorization instead.

## Acceptance Criteria

- `agents/test-runner.md` and `skills/_shared/test-runner-prompt.md` contain no temp-script-file recommendation and agree on exactly one durable write (the artifact); both state that running the supplied command via `bash` stdin/heredoc is the sanctioned mechanism rather than a forbidden "other command"; delimiter-collision guidance is present.
- A regression test fails if temp-script-file guidance is reintroduced into either file and verifies both files carry the single-artifact-write rule; the full existing test-runner test suite (prompt assembly, marker contract, completion protocol, artifact parser) still passes unchanged.
- The strict-format fixtures (`verifier-report-pass.md`, `verifier-report-fail.md`) produce the same verdicts, JSON content, and exit codes as before the change.
- A constructed regression fixture modeling the `f6eac473` Wave 1 scenario — every criterion explicitly PASS, successful command evidence, human-readable formatting defects — parses as a semantic PASS with protocol warnings; following the updated SKILL.md routing, the orchestrator proceeds (no verifier redispatch, no user gate) while surfacing the warnings.
- Each enumerated protocol-only variant (case-only verdict tokens, trailing annotation, `verdict:`-prefix with unambiguous PASS, case/trailing-tolerant overall verdict, missing stdout/stderr labels with successful command evidence, surrounding-whitespace command difference) is covered by a passing test of the tolerant outcome.
- Each enumerated substantive defect (missing/duplicate/out-of-range criterion, non-PASS/FAIL token such as `passed`, missing overall verdict, missing evidence block, missing/non-zero exit code, paraphrased or internally-altered command, per-criterion FAIL) is covered by a test asserting hard FAIL — none reach the tolerant outcome.
- Parser output for a tolerant pass is mechanically distinguishable from both a strict pass and a hard FAIL, and hard-FAIL output still surfaces protocol errors.
- `SKILL.md` Step 11.2, Step 13, and `acceptance-criteria-verification.md` document the tolerant route, the automatic-acceptance rule with warning surfacing, the user-gated recipe-amendment menu option, and the reaffirmed orchestrator-verification boundary, with no remaining text claiming all protocol errors unconditionally fail.

## Non-Goals

- Splitting the plan's `Verify:` recipe into separate machine-command and human success-condition fields (and the corresponding `extract-plan-tasks.py` / `assemble-verifier-prompt.py` / `generate-plan` schema changes) — deferred to a follow-up idea.
- Any LLM-powered report repair, reformatting, or command-equivalence judgment.
- Ad hoc orchestrator verification: file inspection, locally-run checks, or evidence synthesis remain forbidden.
- Accepting reports with missing, failing, or ambiguous evidence under any path.
- Changes to the test-runner artifact format, artifact parser, reconciliation logic, or dispatch protocol.
- Changes to verifier behavior at dispatch time (the verifier is still instructed to run recipes byte-equal verbatim).
- Hand-editing the installed `node_modules` copy of the package.

## Open Questions (optional)

- **Breadth:** this spec intentionally combines two independent subsystems (test-runner contract docs/tests and the execute-plan verifier pipeline) at the user's direction. Downstream `generate-plan` may produce a coarse plan; grouping Part A and Part B into separate waves is the natural decomposition.
- Should a verifier redispatch following a user-approved recipe amendment (B8) consume the existing Step 13 retry budget or reset it (as `(r)` does)? Planner/implementer may pick either; resetting mirrors `(r)`'s existing semantics.
- The deferred `Verify:` field split remains the root-cause fix for command-field mismatch; a follow-up idea should be filed when this spec lands.
