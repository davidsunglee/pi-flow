# Plan: Tidy startup header via pi-flow-ux

**Source:** `IDEA-f5ddba6d`
**Spec:** `docs/specs/2026-06-03-f5ddba6d.md`

## Goal

Replace pi's busy startup surface with a calm, deterministic, terminal-width-responsive startup header owned by `@aphotic/pi-flow-ux`. The header supports three detail levels — `none` (logo + `v<version>` + optional session message), `compact` (one summary row per non-empty resource category), and `full` (exhaustive per-item listing, on demand only via bare `/tui header details`) — selected by a new `tui.json` setting `header.details` combined with core pi's `quietStartup`. Resource data comes from a per-category, loaded-truth-first resolver built on pi 0.78.0's public extension APIs (`pi.getCommands()`, `ctx.ui.getAllThemes()`, `SettingsManager`, `loadProjectContextFiles`, `DefaultPackageManager.resolve` with install-suppression), with no factory execution and no upstream pi changes.

## Architecture summary

All work lives in `packages/pi-flow-ux/extensions/`. Five modules cooperate:

- **`settings.ts`** (existing, modified) — owns the `TuiSettings` model and `/tui` grammar. Gains `header.details: "none" | "compact"` (default `compact`), the `details=` set-branch, and a bare `details` branch that delegates to an injected `showHeaderDetails` callback so the settings store stays free of resource-resolution concerns.
- **`header-data.ts`** (new) — the resolver. Defines `ResourceSnapshot` (five categories of `ResourceItem { name, detail?, active? }`), the pure display-name/path-abbreviation helpers, `collectResourceSnapshot(sources)` over an injected `SnapshotSources` bundle (testable without pi), `createDefaultSnapshotSources(pi, ctx)` (production wiring to public pi APIs), a `HeaderResources` holder with subscribe/refresh semantics for the async follow-up repaint, and `readQuietStartup(cwd)`.
- **`header.ts`** (existing, modified) — startup header rendering. `resolveHeaderLevel(quietStartup, details)` forces `none` when `quietStartup` is false; `buildHeaderLines(...)` is a pure function over `{version, reason, logo, level, resources, width, colorize}` producing two-space-margined lines with a trailing blank; compact rows use a greedy fit-with-`+N` algorithm that never wraps. `installHeader` subscribes to both the settings store and the `HeaderResources` holder.
- **`header-details.ts`** (new) — the on-demand full view. `buildFullDetailsLines(snapshot, width, colorize)` renders the exhaustive listing (wide layout with source sub-lines when usable width ≥ 72, narrow without); `showHeaderDetails(pi, ctx)` collects a fresh snapshot and posts it into chat scrollback via `pi.sendMessage({customType: "pi-flow-ux:header-details", display: true, content: <plain text>, details: snapshot})`; `createHeaderDetailsRenderer()` registers a `MessageRenderer` so the chat entry re-renders width-responsively and theme-aware from the persisted snapshot.
- **`index.ts`** (existing, modified) — wiring. Registers the message renderer and the `showHeaderDetails` callback at factory time; on every `session_start` creates a fresh `HeaderResources` holder, fire-and-forgets its refresh, reads `quietStartup`, and installs the header.

Data flow at startup: `session_start` → header installs and paints immediately (logo/version/message) → async `collectResourceSnapshot` completes → holder notifies → `tui.requestRender()` → compact rows appear → snapshot frozen for the session. On-demand flow: `/tui header details` → fresh snapshot → custom message appended to chat (also persisted in the session and visible to the LLM as plain text, like bash-execution messages).

  `buildCompactRow`: `available = width - HEADER_MARGIN.length - COMPACT_LABEL_COL`; compute `shown = fitCompactItems(names, Math.max(0, available))`; assemble `HEADER_MARGIN + colorize("mdHeading", label) + " ".repeat(COMPACT_LABEL_COL - label.length) + colorize("toolOutput", names.slice(0, shown).join(", "))` and, when `shown < names.length`, append `(shown > 0 ? " " : "") + colorize("muted", "+" + (names.length - shown))` (the space separator stays uncolored). ## Risk Assessment

- **Spec deviation — built-in theme identification.** Spec said built-in themes are identified by `path === undefined` in `ctx.ui.getAllThemes()`; the plan instead classifies a theme as user/project/package-provided by cross-referencing its resolved path against `DefaultPackageManager.resolve()`'s enabled `themes` entries (which include the auto-discovered `~/.pi/agent/themes` and `.pi/themes` dirs), because pi 0.78.0's `getAvailableThemesWithPaths()` (`dist/modes/interactive/theme/theme.js`) assigns built-ins (`dark`, `light`) concrete paths under pi's own themes directory — `path === undefined` would misclassify built-ins as user themes. The active theme is still included regardless of classification, exactly as the spec requires, and the `.d.ts` shape (`path: string | undefined`) is honored. If a future pi version changes built-in path reporting, only the `known`-set check in `collectResourceSnapshot` is affected.
- **`resources_discover` timing for the startup compact row.** The host emits `resources_discover` (which can add skills/prompts) *after* `session_start` handlers run, so a synchronous `getCommands()` snapshot at session start could miss those contributions. Mitigation: the resolver takes its `getCommands()`/`getAllThemes()` reads inside the async refresh, after awaiting `DefaultPackageManager.resolve()` (real fs work), which in practice lands after discovery completes; the on-demand full view always reflects invocation-time truth because it re-collects. Residual risk (a discover-contributed skill missing from the *startup* compact row in a pathological timing) is bounded and self-corrects on the next reload; the spec's req 18 explicitly allows async rows to land in a follow-up repaint.
- **`DefaultPackageManager.resolve()` cost.** With `onMissing → "skip"` it never installs and never touches the network, but the legacy-path fallback (`getNpmInstallPath` for user-scope packages missing from the managed dir) can synchronously spawn `npm root -g`/`pnpm list -g` once. This runs inside the async refresh after the header's first paint, so startup never blocks on it; worst case the compact rows arrive a beat later. The host itself pays the same cost during its own startup resolution.
- **Full-view chat message is persisted and LLM-visible.** `pi.sendMessage` appends a custom entry to the session and `convertToLlm` forwards custom-message content as a user message. This is the only public mechanism that gives a durable, width-responsive chat-scrollback entry (the alternative, `ctx.ui.notify("info")`, is collapsed/replaced by the next status toast in interactive mode — unacceptable for scrollback). Cost is contained: content is compact ANSI-free plain text describing the user-requested resource listing, on demand only. The renderer validates `details` and falls back to the default custom-message box when absent/corrupt, so old sessions resume cleanly even if the package is removed.
- **Background refresh in existing tests.** `index.test.ts` emits `session_start` with fake contexts, which now starts a real `collectResourceSnapshot` against the test cwd. Every source access is individually try/caught (missing `pi.getCommands` or `ctx.ui.getAllThemes` on a fake degrades to empty categories) and the refresh promise carries a `.catch(() => {})`, so fakes can't crash or fail tests; pointing fake `cwd` at temp dirs keeps `DefaultPackageManager` resolution empty and fast. Task 5 updates the fakes accordingly.
- **Compact-row width math vs ANSI.** Fit decisions are made on plain strings before colorization, and assembled rows are guarded with `visibleWidth`/`truncateToWidth` (the same ANSI-safe utilities the border editor uses), so a row can never exceed the viewport even at degenerate widths (< 14 columns).
- **`SettingsManager.create(cwd)` per session start.** Reads settings files synchronously; `editor.ts` already does this per install (`loadAutocompleteMaxVisible`), so the pattern and cost are established. All reads are wrapped (`readQuietStartup` falls back to `false`, which degrades to the calm `none` level), and the feature never calls any `SettingsManager` setter.
- **Theme token availability.** Rendering uses only core `ThemeColor` union members (`mdHeading`, `toolOutput`, `muted`, `success` via `BORDER_TOKENS.cwd`); `Theme.fg` throws only for unknown token names, and these are defined by every host-loaded theme (the host's own startup listing uses `mdHeading`/`dim` the same way).
