# Plan: Simplify pi-flow-ux around border status and unified TUI configuration

**Spec:** `docs/specs/2026-06-01-c1d47c94.md`
**Source:** `IDEA-c1d47c94`

## Goal

Collapse the `@aphotic/pi-flow-ux` package's two extension entrypoints (`extensions/status/` and `extensions/working/`) into a single `extensions/index.ts` with a flat top-level module layout. Remove all status-placement switching (`/status`, `status.json`, `footer.ts`, the `StatusCoordinator` and its renderer plumbing) and all per-state working *configuration* (`/working`, `working.json`, per-state color/gleam/rainbow). Border status becomes always-on; Pi's duplicate default footer and host working row are suppressed; a new custom startup header is added; and every user-facing TUI option is configured through one command (`/tui`) and one file (`tui.json`). Activity visual effects (model gleam, thinking rainbow, per-state activity-slot styling) become hardcoded constants in `effects.ts`, independent of any theme. This is an intentional breaking change with no legacy readers, migrations, aliases, or compatibility shims.

## Architecture summary

The package ships one extension entrypoint that wires four pieces, all loaded together:

- **`extensions/working.ts`** — the `WorkingCoordinator`: tracks active-turn / tool-use / thinking state from Pi events, loads/saves `tui.json` (three-tier resolution), registers the `/tui` command, suppresses Pi's host working row, and exposes a queryable `WorkingSnapshot`.
- **`extensions/effects.ts`** — pure, hardcoded visual effects: indicator frame generation, per-state activity-slot styling (`STATE_EFFECTS`), time-based gleam/rainbow helpers for the model name and thinking text. No theme coupling, no config inputs.
- **`extensions/editor.ts`** — the always-on border-status editor (`CustomEditor` subclass). Reads the working snapshot to draw the activity slot, applies effects to the model/thinking text, and runs a redraw timer whenever activity is visible.
- **`extensions/footer.ts`** — installs a blank footer that suppresses Pi's built-in footer.
- **`extensions/header.ts`** — installs a custom startup header (hardcoded gradient pi logo + `version <VERSION>` + humanized startup-reason line) via `setHeader`, guarded by `ctx.hasUI`.
- **`extensions/working-messages.ts`** — the retained working-message catalog (kept for a future placement decision; not rendered anywhere initially).
- **`extensions/index.ts`** — the single entrypoint: registers the coordinator (events + `/tui` command), then on `session_start` installs the blank footer, border editor, and header; disposes them on `session_shutdown`.

Data flow: Pi events → `WorkingCoordinator` updates state → emits `WorkingSnapshot` → `editor.ts` subscribes and redraws → `editor.ts` reads `snapshot.settings.working.indicator` + `snapshot.state` and calls `effects.ts` to style the activity slot, model name (gleam while visible), and thinking text (rainbow while thinking).

Responsibility split (per spec): `working.ts` = state/config; `effects.ts` = pure hardcoded visuals; `editor.ts` = placement/composition.

  function gradientColorAt(t: number): [number, number, number] {

    return [lerp(a[0], b[0], local), lerp(a[1], b[1], local), lerp(a[2], b[2], local)];

## Risk Assessment

- **pi-powerline header art unavailable (spec deviation).** The spec names pi-powerline's `extensions/header.ts` as the logo source. It is not present in this checkout or `node_modules` (verified by `**/header.ts` and `**/pi-powerline/**` globs returning nothing). Per the spec's agreed fallback, this plan ships a hand-rolled gradient pi wordmark. *Mitigation:* the art is isolated in `PI_LOGO_ART` + `applyLogoGradient`, so swapping in the real art later is a one-constant edit; `applyLogoGradient` is theme-independent and already satisfies "no Nord coupling."
- **Coordinator registry simplification.** The old `working/working.ts` used a `globalThis` `Symbol.for` registry because the two extension entrypoints loaded through separate jiti module caches. The single `extensions/index.ts` entrypoint imports `working.ts` exactly once (directly and transitively via `editor.ts`), so a plain module-level `Map` is correct and the cross-cache hazard is gone. *Mitigation:* the `getWorkingCoordinator throws on rebind` and `keys coordinators by settingsPath` tests are retained against the module-level map; the now-obsolete `shares state across isolated module instances` test is dropped intentionally.
- **Model-name gleam replaces the theme accent during activity.** While visible, `modelStyler` overrides the `colorize("model", …)` theme token with a hardcoded truecolor gleam. This is intended (effects are theme-independent per spec), but it visibly changes the model color during turns. *Mitigation:* the idle path (`snapshot.visible === false`) still uses the theme token, so the static appearance is unchanged; editor tests assert both paths.
- **Always-on redraw timer cost.** `resolveEditorTimerCadence` now returns a cadence for every visible state (including static `dot`), so the editor requests a redraw roughly every 120 ms throughout a turn. This is the same order of magnitude as the previous multi-frame indicators and only runs while a turn is active. *Mitigation:* the timer is cleared the moment `snapshot.visible` goes false (`turn_end`/`session_shutdown`), and `requestRender` is cheap (it does not recompute unless the TUI repaints).
- **`import.meta.dirname` path depth change.** Moving `working.ts` from `extensions/working/working.ts` to `extensions/working.ts` changes the packaged-config relative path from two `..` segments to one. Getting this wrong silently degrades to code defaults. *Mitigation:* the `PACKAGE_DEFAULT_TUI_SETTINGS_PATH resolves to .../tui.json` regex test in `working.test.ts` catches a wrong depth.
- **Aggregate/release tests depend on external tooling.** `packlist.test.mjs`, `aggregate-forwarding.test.mjs`, and the root `pi`-discovery test spawn `pnpm pack`/`npm pack`/`pnpm add`/`pi`. *Mitigation:* these tests already self-skip via `{"skipped": ...}` when the tooling/network is absent; the deterministic manifest assertions (updated in Task 11) are the real coverage. The pack-aggregate `REQUIRED_BUNDLED_PATHS` update (Task 10) keeps the release guard honest when packing does run.
- **Host working-row suppression API (spec deviation).** Spec said the confirmed Pi API surface includes `setWorkingIndicator(...)` but did not list `setWorkingVisible`; plan uses `setWorkingVisible` because it is present in the installed types (`@earendil-works/pi-coding-agent@0.75.3`, `dist/core/extensions/types.d.ts:82-83` — "Show or hide the built-in interactive working loader row during streaming"). *Mitigation:* suppression goes through a runtime presence-checked helper `setHostWorkingRowVisible` that prefers `setWorkingVisible` and falls back to the spec-confirmed `setWorkingIndicator({ frames: [] })` (line 92, "hide the indicator entirely") if a future Pi build drops `setWorkingVisible`, so the extension installs and cleans up safely either way. Both paths are covered by the Step 11 working.test.ts suppression tests.
- **Host working-row suppression must restore cleanly.** Hiding Pi's loader row on `session_start` would leave it hidden if the extension is later disabled mid-process. *Mitigation:* the coordinator restores the row via `setHostWorkingRowVisible(this.uiCtx.ui, true)` on `session_shutdown` using the captured `uiCtx`, and the `index.test.ts` shutdown test asserts `setWorkingVisible(true)` is called.
