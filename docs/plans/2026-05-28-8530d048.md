# Extract idea extension into its own package (`@aphotic/pi-ideas`)

**Goal:** Extract the idea extension (`idea.ts`, `storage.ts` and their tests) out of `@aphotic/pi-flow-core` into a new standalone, publication-ready workspace package `@aphotic/pi-ideas` that has zero runtime dependency on pi-flow-core or any `flow:`-specific concept. The work-menu actions, selector quick-key shortcuts, refine prompt, idea-tool description/prompt-snippet, and the slash-command name are all driven by JSON config files (`~/.pi/ideas.json` global, `<cwd>/.pi/ideas.json` project) plus an optional packaged-default config a consumer can ship. `@aphotic/pi-flow-core` re-establishes its current behavior (the `flow:ideas` command, the four `fastlane`/`scout`/`spec`/`plan` work actions with their shortcuts, the 5-section refine prompt, and the 5-section tool guidance) by shipping a packaged `ideas.json` and passing its path to `registerIdea`.

**Architecture summary:** A new `config.ts` module in the ideas package defines the config schema (`command`, `refinePrompt`, `toolDescription`, `promptSnippet`, `actions[]`) and a pure synchronous resolver that layers built-in defaults ← optional packaged-default file ← global `~/.pi/ideas.json` ← project `<cwd>/.pi/ideas.json`. Scalar fields use last-defined-wins; the `actions` array merges sequentially with the Pi-settings-style negation/replace/append rules. `registerIdea(pi, options?)` resolves the config once at registration time (using `fs.readFileSync`, mirroring the working-extension packaged-baseline pattern) and uses it to (a) register the browser command under the resolved name, (b) register the `idea` tool with the resolved description/prompt-snippet, and (c) drive the selector hint bar, selector quick-key handlers, and the work submenu. The components (`IdeaSelectorComponent`, `IdeaActionMenuComponent`, `IdeaWorkSubmenuComponent`, etc.) are parameterized on the resolved actions instead of hardcoded skills. The ideas package exposes a standalone extension entry (`extensions/index.ts`) so it is loadable on its own as `/ideas`; pi-flow-core imports `registerIdea` directly and wires its packaged config, and the aggregate reaches the ideas extension through pi-flow-core's already-forwarded `commands.ts` (no second registration).

**Tech stack:** Node.js >=20, pnpm workspaces, ESM (`"type": "module"`), TypeScript (`tsc --noEmit`, NodeNext, `allowImportingTsExtensions`), TypeBox for the tool schema, `node:test` runner, peer deps `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui`.

**Spec:** `docs/specs/2026-05-28-8530d048.md`

## Approach note (from spec `## Approach`)

The spec fixes the macro approach: file-based configuration at `~/.pi/ideas.json` (global) and `<project-root>/.pi/ideas.json` (project) merged at registration time, following Pi-settings merge conventions (`-name` negation). This plan honors that. The two open questions the spec delegated to the planner are resolved as:

1. **Tool description / prompt-snippet override mechanism:** two explicit scalar config fields, `toolDescription` and `promptSnippet`, resolved with the same project>global>packaged>built-in precedence as `command` and `refinePrompt`. No "weaving" of a single `ideaStructure` field — explicit fields are simpler and uniform with the other scalars.
2. **Config file top-level shape + how pi-flow-core ships its config:** a single JSON object with keys `command`, `refinePrompt`, `toolDescription`, `promptSnippet`, and `actions` (array of `{name, prompt, description?, shortcut?}`). pi-flow-core ships this object as a packaged file at its package root (`packages/pi-flow-core/ideas.json`, listed in `files`) and passes its absolute path to `registerIdea(pi, { defaultConfigPath })`. This is the exact pattern the working extension already uses for its packaged baseline (`PACKAGE_DEFAULT_SETTINGS_PATH`), so it introduces no new mechanism and satisfies "Configuration is read from the filesystem at extension registration time" with "no programmatic inter-extension configuration channel" (the path is passed by the package that owns the registration, not pushed between extensions at runtime).

**Project-root resolution decision:** the project config path is resolved as `path.join(cwd, ".pi", "ideas.json")` where `cwd` defaults to `process.cwd()` at registration time (overridable via the `cwd` option for tests). This avoids spawning `git` at every extension load and matches the spec's `<project-root>/.pi/ideas.json` under Pi's normal convention of launching with cwd at the project root.

  ```ts
  function isPlainObject(v: unknown): v is Record<string, unknown> {
    return typeof v === "object" && v !== null && !Array.isArray(v);
  }

  interface RawActionEntry {
    name: string;
    prompt?: string;
    description?: string;
    shortcut?: string;
  }

  export function normalizeRawActions(value: unknown): RawActionEntry[] {
    if (!Array.isArray(value)) return [];
    const out: RawActionEntry[] = [];
    for (const item of value) {
      if (!isPlainObject(item)) continue;
      if (typeof item.name !== "string" || item.name.length === 0) continue;
      const entry: RawActionEntry = { name: item.name };
      if (typeof item.prompt === "string") entry.prompt = item.prompt;
      if (typeof item.description === "string") entry.description = item.description;
      if (typeof item.shortcut === "string") entry.shortcut = item.shortcut;
      out.push(entry);
    }
    return out;
  }

  export function mergeActions(base: WorkMenuAction[], incoming: RawActionEntry[]): WorkMenuAction[] {
    const result = base.map((a) => ({ ...a }));
    for (const entry of incoming) {
      if (entry.name.startsWith("-")) {
        const target = entry.name.slice(1);
        const idx = result.findIndex((a) => a.name === target);
        if (idx !== -1) result.splice(idx, 1);
        continue;
      }
      if (entry.prompt === undefined) continue; // prompt required for non-negation entries
      const action: WorkMenuAction = {
        name: entry.name,
        prompt: entry.prompt,
        ...(entry.description === undefined ? {} : { description: entry.description }),
        ...(entry.shortcut === undefined ? {} : { shortcut: entry.shortcut }),
      };
      const idx = result.findIndex((a) => a.name === entry.name);
      if (idx !== -1) result[idx] = action; // replace in place, preserving position
      else result.push(action); // append new
    }
    return result;
  }
  ```
- [ ] **Step 4: Add the file reader and the resolver** — In `config.ts`:
  ```ts
  function readConfigObject(filePath: string): Record<string, unknown> | undefined {
    let raw: string;
    try {
      raw = fs.readFileSync(filePath, "utf8");
    } catch {
      return undefined; // missing/unreadable — treat as absent
    }
    let parsed: unknown;
    try {
      parsed = JSON.parse(raw);
    } catch {
      return undefined; // malformed — ignore rather than crash extension load
    }
    return isPlainObject(parsed) ? parsed : undefined;
  }

  function pickString(
    field: keyof IdeasConfig,
    layers: Array<Record<string, unknown> | undefined>,
    fallback: string,
  ): string {
    let value = fallback;
    for (const layer of layers) {
      const v = layer?.[field as string];
      if (typeof v === "string" && v.length > 0) value = v;
    }
    return value;
  }

  export interface ResolveIdeasConfigOptions {
    defaultConfigPath?: string;
    homeDir?: string;
    cwd?: string;
  }

  export function resolveIdeasConfig(opts: ResolveIdeasConfigOptions = {}): IdeasConfig {
    const homeDir = opts.homeDir ?? os.homedir();
    const cwd = opts.cwd ?? process.cwd();

    const packaged = opts.defaultConfigPath ? readConfigObject(opts.defaultConfigPath) : undefined;
    const global = readConfigObject(path.join(homeDir, ".pi", "ideas.json"));
    const project = readConfigObject(path.join(cwd, ".pi", "ideas.json"));
    const layers = [packaged, global, project];

    let actions: WorkMenuAction[] = [...BUILTIN_IDEAS_CONFIG.actions];
    for (const layer of layers) {
      if (layer && "actions" in layer) {
        actions = mergeActions(actions, normalizeRawActions(layer.actions));
      }
    }

    return {
      command: pickString("command", layers, BUILTIN_IDEAS_CONFIG.command),
      refinePrompt: pickString("refinePrompt", layers, BUILTIN_IDEAS_CONFIG.refinePrompt),
      toolDescription: pickString("toolDescription", layers, BUILTIN_IDEAS_CONFIG.toolDescription),
      promptSnippet: pickString("promptSnippet", layers, BUILTIN_IDEAS_CONFIG.promptSnippet),
      actions,
    };
  }
  ```

## Risk Assessment

- **Cross-package deep TS import (`@aphotic/pi-ideas/extensions/idea.ts`) failing to resolve at typecheck or Pi load.** The monorepo already deep-imports into `node_modules/@aphotic/pi-flow-ux/extensions/working/index.ts` from the aggregate manifest, and none of the packages use an `exports` map (so deep paths are unrestricted). pnpm links the workspace package into pi-flow-core's `node_modules`. Mitigation: run `pnpm install` in Task 7 Step 2 before typechecking; the Task 7 `check` acceptance directly exercises the import. If `tsc` cannot resolve the `.ts` extension cross-package, fall back to a re-export barrel (`packages/pi-ideas/extensions/idea.ts` is already the entry) — the existing `allowImportingTsExtensions` + NodeNext config supports `.ts` specifiers.
- **Test pollution from a developer's real `~/.pi/ideas.json` overriding the packaged `flow:ideas` command.** Because resolution is built-in ← packaged ← global ← project, a stray global `ideas.json` with a different `command` could change what pi-flow-core registers and break `commands.test.ts` / `pi-loader-smoke.test.mjs`. Mitigation: Task 7 Steps 7–8 isolate `HOME`/`USERPROFILE` (and cwd) in those tests; node's `--test` runs each file in its own process so the env mutation does not leak to sibling test files. `idea-tool-only.test.mjs` already isolates HOME and chdirs.
- **Behavior changes mandated by the spec that alter existing assertions.** Three user-visible changes are intentional: (1) hint-bar text is now all-lowercase (`ctrl+shift+r refine`, `enter to confirm`, `esc back`); (2) the action-menu order moves `other` before `close/reopen` (was view/refine/work/close/other); (3) the refine prompt no longer embeds the idea title (only `${idea}` substitution is supported, per the non-goal excluding other placeholders) — pi-flow-core's packaged `refinePrompt` retains the 5 section headers so section guidance still reaches the assistant, and the tool `description`/`promptSnippet` continue to carry the 5-section shape on pi-flow installs. The moved `idea.test.ts` is updated accordingly in Task 5.
- **`process.cwd()` not being the project root in unusual launch contexts.** The project config path uses `process.cwd()` (overridable via the `cwd` option). If a user launches Pi from a subdirectory, a project `.pi/ideas.json` at the true repo root would be missed. This matches Pi's normal convention (launch at project root) and the spec's `<project-root>/.pi/ideas.json` wording; resolving via `git rev-parse` was deliberately avoided to keep extension load free of subprocess spawns. Documented as the project-root resolution decision in the Approach note.
- **typebox removal from pi-flow-core breaking a hidden import.** Grep confirmed only `extensions/idea.ts` imported typebox in pi-flow-core (`workflow.ts`, `router.ts`, `setup.ts`, `commands.ts` do not). After the move, dropping typebox from pi-flow-core is safe; it resolves transitively through `@aphotic/pi-ideas` for the loaded extension. The Task 7 `check` acceptance (full typecheck + tests) catches any missed import.
