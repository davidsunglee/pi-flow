# Plan — `/flow:doctor`: keep pi-flow shims and symlinks aligned to the intended package version

**Source:** IDEA-b79bac29
**Spec:** docs/specs/2026-06-09-b79bac29.md

## Goal

Build a pi-flow-owned `/flow:doctor` extension command, a sibling to `/flow:setup`, that **diagnoses** pi-flow version skew across every relevant surface (the `~/.pi/agent/bin/pi-flow` helper shim, the bundled-agent symlinks, the project/user package installs, `node_modules/.bin` entries, and the `.pi/settings.json` declared packages) by reporting each surface's resolved realpath and pi-flow version relative to the package actually executing the session, and — only on explicit `--fix` — **repairs** the links pi-flow itself manages (helper shim + agent symlinks), either reconciling them to the active/declared source or repointing them to a user-named target. Diagnosis is the default and is read-only; repair is opt-in. doctor introduces no pin store of its own and never edits Pi's `.pi/settings.json` or runs installs.

## Architecture summary

The feature reuses `/flow:setup`'s existing machinery: `resolveScope()` (active-package/scope resolution via `pi.getCommands()` → `sourceInfo.baseDir` realpath matching), the `SetupConflict`/`DurableTarget` types, and the `created` / `skipped` / `conflict` / `preserved-other` outcome vocabulary. It adds two new source modules under `packages/pi-flow-core/extensions/`:

- **`package-resolution.ts`** — the parity-critical primitives. It resolves a pi-flow-core package root from a `bin/pi-flow.mjs` realpath *exactly* as `bin/pi-flow.mjs` does (`PACKAGE_ROOT = realpath(dirname(bin))/..`, no fallback), and reads/validates a `@aphotic/pi-flow-core` package (name + version) at a root. These primitives guarantee doctor's version verdicts match real helper/template resolution.
- **`doctor.ts`** — the feature: surface inventory + classification (`active` / `local-dev` / `stale-skew` / `absent` / `unresolved`), report rendering with an overall skew verdict, settings-`packages` parsing, reconcile-target resolution with ambiguity detection, explicit `--source` target validation, never-overwrite-silently link repair with a new `repaired` outcome, argument parsing (`--fix` / `--source` / `--help`), and `registerDoctor(pi)` that wires the pure functions to `ctx.ui.notify`.

The executing ("intended") package is `realpath(import.meta.dirname/..)` of the doctor extension — the same anchor `setup.ts` uses for its own package root. Every surface's resolved root is compared against it. A surface that resolves to a checkout inside the active working tree is an informational **local-dev override**; one that resolves to a different package that is neither active nor a recognized checkout is **stale-skew** and trips the failure verdict. `--fix` repoints only the helper shim and agent symlinks; when the intended target is ambiguous (multiple distinct pi-flow packages declared/loaded, as in this self-hosting repo) it refuses and requires `--source`. doctor only ever advises on `.pi/settings.json` alignment — it never writes it.

## Tech stack

- TypeScript ES modules, Node ≥ 20, run via `node --experimental-strip-types` (no build step).
- Filesystem via `node:fs/promises` (`lstat` / `readlink` / `realpath` / `symlink` / `unlink`), `node:os`, `node:path` — same primitives `setup.ts` uses (macOS / Linux).
- Pi extension API: `@earendil-works/pi-coding-agent` (`ExtensionAPI`, `ExtensionCommandContext`, `SlashCommandInfo`, `SourceInfo`).
- Tests: `node:test` + `node:assert/strict`, temp-dir sandboxes (mirrors `setup.test.ts`). Auto-discovered by the package's `test:node` script (`find ... extensions ... -name '*.test.ts'`).

export interface PiFlowCorePackage {
  /** realpath of the package root directory */

  /** package.json "name" (expected "@aphotic/pi-flow-core") */
  name: string;
  /** package.json "version" */
  version: string;
}

/** realpath(p), or null if it does not resolve (ENOENT/ENOTDIR/etc.). */
export async function realpathOrNull(p: string): Promise<string | null>;

/**

 * parent of its containing bin/ directory. Returns the realpath of the root, or
 * null if the bin path does not resolve.

 * name === "@aphotic/pi-flow-core" AND root/bin/pi-flow.mjs exists; otherwise null.
 * `root` in the returned object is the realpath of the input root.
 */
export async function readPiFlowCorePackage(root: string): Promise<PiFlowCorePackage | null>;

/**
 * Walk up from `start` (a realpath to any file/dir inside a package) to the
 * nearest enclosing directory that readPiFlowCorePackage accepts. Returns it or
 * null. Stops at the filesystem root.
 */
export async function findEnclosingCoreRoot(start: string): Promise<PiFlowCorePackage | null>;

  realpathOrNull,

export type SurfaceKind =

  | "user-agents"
  | "project-agents"
  | "project-install"
  | "user-install"
  | "node-bin"
  | "declared-package";

export type Classification =
  | "active"       // realpath === active package root
  | "local-dev"    // a source checkout within the active working tree (intentional)
  | "stale-skew"   // a different package that is neither active nor a recognized checkout
  | "absent"       // the surface path does not exist (informational)
  | "unresolved"   // the surface exists but its pi-flow target could not be resolved
  | "non-pi-flow"; // resolves to something that is not a pi-flow-core package

export interface SurfaceReport {
  kind: SurfaceKind;
  label: string;            // human label, e.g. "helper shim (~/.pi/agent/bin/pi-flow)"
  inspectedPath: string;    // the path doctor looked at, pre-realpath
  realpath?: string;        // resolved realpath of the surface's pi-flow target root
  pkg?: PiFlowCorePackage;  // resolved package (name@version) at realpath
  classification: Classification;
  detail?: string;          // e.g. declared spec string + "pinned"/"floating", or notes
}

export interface BinResolution {
  /** the pi-flow-core package that actually executes when the bin runs, or null */
  core: PiFlowCorePackage | null;
  /** set when resolution passed through the aggregate @aphotic/pi-flow wrapper */
  viaAggregate?: { name: string; version: string; root: string };
}

/**
 * Resolve a bin/pi-flow(.mjs) path to the pi-flow-core package that actually
 * executes, mirroring runtime delegation. First compute PACKAGE_ROOT via
 * packageRootFromBin (runner parity) and try readPiFlowCorePackage on it (a
 * direct core runner). If that root is instead the aggregate `@aphotic/pi-flow`
 * wrapper, reproduce its `createRequire(...).resolve(
 * "@aphotic/pi-flow-core/bin/pi-flow.mjs")` delegation and resolve the bundled/
 * dependency core. Returns { core } with viaAggregate set when the path went
 * through the wrapper; core is null only when the bin is genuinely not pi-flow.
 */
export async function resolveBinToCore(binPath: string): Promise<BinResolution>;

export interface DeclaredPackage {
  /** raw spec: "npm:@aphotic/pi-flow@0.8.0", "npm:@aphotic/pi-flow", or a local path */
  spec: string;
  /** "npm" | "local" — classified from the spec form */
  kind: "npm" | "local";
  /** true when an npm spec carries an explicit @<version> pin */
  pinned: boolean;
}

export interface DoctorDiagnosis {
  active: PiFlowCorePackage;     // the executing ("intended") package
  scope: SetupScope;
  surfaces: SurfaceReport[];
  hasSkew: boolean;              // overall failure verdict
  skewKinds: SurfaceKind[];      // resolution-path surfaces classified stale-skew
}

export interface BuildDiagnosisOptions {
  activeRoot: string;            // realpath(import.meta.dirname/..) from the handler
  cwd: string;
  homeDir: string;
  scope: SetupScope;
  /** injectable for tests; defaults read the real filesystem */
}

## Risk Assessment

- **Skew-verdict scope (which surfaces trip failure).** The spec requires a clear failure signal "when helper/template/skill resolution could come from a different pi-flow version than the active skills." This plan scopes `hasSkew` to the active resolution-path surfaces (helper shim, agent symlinks, `node_modules/.bin`) classified `stale-skew`; installs and declared packages are reported with classification but do not by themselves trip the hard failure (they are inputs, not the resolving path), and `local-dev` overrides never trip it. Mitigation: the report still shows every surface and its classification, so an informational-only mismatch is visible even when the verdict is `OK`.
- **No process exit code for an extension command.** `/flow:doctor` runs inside Pi and reports via `ctx.ui.notify`, so "non-zero / explicit error state" is realized as an `error`-level notify carrying the exact `SKEW DETECTED …` verdict line plus the structured `DoctorDiagnosis.hasSkew === true`. Mitigation: the pure `buildDiagnosis`/`renderReport` functions are unit-tested on the boolean and the verdict string, decoupling the verdict from UI plumbing.
- **Resolving declared npm specs to on-disk roots.** doctor cannot reproduce Pi's package-manager resolution of an npm spec to an install directory without Pi internals (the spec forbids depending on them). Mitigation: declared-package rows resolve `local` paths best-effort (relative to the settings dir) and leave npm specs `unresolved` with the raw spec shown; they are informational and never set `hasSkew`, and reconcile-target ambiguity is detected from distinct *resolved* roots among the active package and loaded `flow:` command base dirs (which doctor can always realpath), not from unresolved specs.
- **`--fix` overwriting under the never-overwrite posture.** `--fix` is the explicit repair path, so repointing a `stale-skew` symlink (`repaired`) is intended and authorized; the posture is preserved by refusing to clobber a `local-dev` override (`preserved-other`) or a real file/dir (`conflict`), exactly mirroring `runHelperShimSetup`. Mitigation: `repairLink` tests assert the preserved/conflict targets are byte-for-byte unchanged.
- **Ambiguity in the self-hosting repo.** This repo declares pi-flow twice (npm + local checkout), so reconcile-mode `--fix` will (correctly) refuse and require `--source`. This is the designed behavior, not a bug; the docs and the ambiguity error message both instruct the user to pass `--source`. Mitigation: the ambiguity path is unit-tested via `resolveReconcileTarget` with two distinct roots.
- **Test auto-discovery / no build step.** New `*.test.ts` files under `extensions/` are picked up automatically by the package's `test:node` find-glob, and sources run under `--experimental-strip-types`; `import.meta.dirname` is only evaluated inside the handler (not at registration), so `commands.test.ts` registration stays side-effect-free, as it is for `setup.ts` today. Mitigation: Task 4 Step 9 runs the full `check` (typecheck + node + helper tests) before completion.
