# Plan: Reusable Release skill (`@aphotic/pi-release`)

**Source:** IDEA-863a3580
**Spec:** `docs/specs/2026-06-12-863a3580.md`

## Goal

Ship a single reusable, project-agnostic Release skill as a new standalone package `@aphotic/pi-release` at `packages/pi-release/`, exporting `skills/release/SKILL.md`. The skill drives the full release workflow for both single-package and monorepo projects through one interface: it auto-detects project shape (with user confirmation and override), runs shared release gates and guardrails — including a full core security audit (secret scan, clean-tree check, full + prod dependency audit, audited-commit record, audit artifact) on every path — generates commit-derived release notes with a mandatory manual review pause, keeps every credentialed action user-owned (prints commands, never runs npm publish / git push / tag push / `gh release create`), and absorbs a governed `.pi/release-profile.md` when present. pi-flow's `docs/RELEASING.md` knowledge moves into the skill (generic parts, including the security audit) and into pi-flow's new `.pi/release-profile.md` (irreducible specifics), leaving `docs/RELEASING.md` reduced to a pointer. The new package joins the `@aphotic/pi-flow` aggregate as a fifth bundled, publishable package.

## Architecture summary

- **Standalone package** `@aphotic/pi-release` at `packages/pi-release/`, modeled on the `@aphotic/pi-ideas` precedent (drops the `pi-flow-` infix, exports via its own `"pi": { "skills": [...] }` manifest, no dependency on `@aphotic/pi-flow-core`). Markdown-only: no TypeScript, no runtime/peer dependencies.
- **Spine + two shape reference files.** `skills/release/SKILL.md` is the always-loaded spine carrying the single interface, shape detection/confirmation/override, ALL shared gates and guardrails (full core security audit + user-owned-action rules + readiness gate + mandatory notes review), profile absorption, and verification. Two one-level-deep sibling files — `single-package.md` and `monorepo.md` — carry only shape-specific *mechanics* and are loaded after the user confirms shape. Shape files never restate guardrails and never fan out to further files.
- **Governed profile.** At runtime the spine checks the consumer repo's `.pi/release-profile.md`. When present it absorbs the project's overrides (publishable set/order, publish tooling, extra gates, persistent notes destination, post-publish smoke tests, hazards) as LLM-read markdown with a recommended (not rigidly parsed) layout. Profiles may *add* gates but never remove or weaken the core security audit.
- **Aggregate integration.** `@aphotic/pi-release` is added to the `@aphotic/pi-flow` aggregate's `dependencies` + `bundledDependencies` and to the aggregate's `pi.skills` glob, making it the fifth publishable package. The deterministic `pack-aggregate.mjs` staging helper gains a fourth bundled subpackage and a required-bundled-path guard for the release skill. The root workspace manifest forwards the new skill for git installs / dogfooding.
- **pi-flow as first consumer.** A new `.pi/release-profile.md` captures pi-flow's specifics (publishable set/order including the new package, aggregate `pack:aggregate`/`publish:aggregate` tooling + isolated-linker hazard, `pi install` smoke test, `docs/releases/<version>.md` notes destination) and carries NO security-audit content. `docs/RELEASING.md` is reduced to a pointer.

## Tech stack

- **Markdown** skill authoring (spine + shape files + profile), following `.pi/skills/writing-workflow-skills/SKILL.md` guidance (imperative steps, exact emitted text in fenced blocks, references one level deep, preserve gates/guardrails).
- **Node.js ≥20** ESM for package manifests, the `pack-aggregate.mjs` staging helper, and `node:test` test files (`--test`, tap reporter).
- **pnpm** workspace (`pnpm-workspace.yaml: packages/*`); `eslint` (flat config) + `typescript-eslint` for lint; manual version bumps (no Changesets).

## Risk Assessment

- **Skill-name collision (`release`).** The exported skill is named `release`; `pi-mux-subagents` ships a project-local `.pi/skills/release`. Pi resolves project-local `.pi/skills/<name>` ahead of package-shipped skills, so in any project carrying its own `.pi/skills/release` the local skill wins and the bundled `@aphotic/pi-release` skill is shadowed — which is exactly the desired non-goal behavior (do not migrate or dedupe pi-mux-subagents). pi-flow has no project-local `release` skill (only `.pi/skills/writing-workflow-skills`), so the bundled skill is active there. **Mitigation/verify:** confirm precedence empirically with `pi -e .` skill discovery before relying on it in a dual-exposed project; document the precedence expectation in the pi-release README. If Pi's resolution differs from "project-local overrides packaged," surface it and revisit naming (the spec flagged this open question for the planner; this plan resolves it as project-local-wins and flags the verification).
- **Aggregate bundling regression (isolated-linker hazard).** Adding a fourth bundled subpackage touches the load-bearing `pack-aggregate.mjs` staging path. The package has no runtime dependencies, so `stageSubpackage`'s dependency-materialization loop is a no-op for it, minimizing risk. **Mitigation:** Task 5's in-process tarball build plus Task 6's full aggregate suite (packlist + install-smoke, which exercise `REQUIRED_BUNDLED_PATHS`) verify the skill is bundled and the tarball stays safe/self-contained before any release.
- **Guardrail leakage into shape files.** The spec hard-requires safety gates (audit + user-owned actions) in the always-loaded spine, never only in a shape file or profile. **Mitigation:** Task 4's structure test asserts the audit/forbidden-action strings are in the spine and that the `gitleaks detect` command is absent from both shape files; Task 8's test/verify asserts the profile carries no audit content.
- **`docs/RELEASING.md` knowledge loss.** Reducing the runbook to a pointer risks dropping an irreducible fact. **Mitigation:** Task 9 Step 2 cross-checks every pi-flow-specific fact against `.pi/release-profile.md` (authored first, Task 8) before the runbook is reduced; the dependency Task 9 → Task 8 enforces ordering. Disposition chosen: **reduce to a pointer** (not full removal) to preserve discoverability — resolves the spec's second open question.
- **Test interleaving on the aggregate manifest.** Task 5 changes `bundledDependencies` to length 4 while the old `=== 3` assertion still stands until Task 6. **Mitigation:** Task 5 acceptance verifies via static inspection + in-process tarball build (not the full suite); Task 6 (which depends on Task 5) updates the assertions and runs the suite green. Execute Task 5 before Task 6.
- **Package-manager adaptation breadth.** The skill claims package-manager-agnostic audit/publish but is authored with pnpm primary and npm/yarn equivalents inline. **Mitigation:** the spine + shape files give npm/yarn equivalents for audit and publish; the detection step reads the lockfile to pick commands. Projects with exotic toolchains fall back to the profile's `Extra gates`/`Publish tooling` overrides.
