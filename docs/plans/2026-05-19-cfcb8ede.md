## Goal

Stand up the initial `pi-flow` pnpm workspace with two distributable Pi packages — `pi-flow-core` (workflow skills, bundled agent definitions, shared markdown contracts, Python helpers/tests, helper runner, and model-tier template) and aggregate `pi-flow` (depends on `pi-flow-core` and re-exposes its resources through `node_modules/`). All 15 non-browser workflow skills are extracted from `../pi-config/agent/skills/` with their templates, fixtures, and per-skill helper scripts. Skill prose that previously executed `python3 agent/skills/...` or `python3 ~/.pi/agent/skills/...` is rewritten to call a stable, package-local `pi-flow helper <id>` / `pi-flow template <id>` runner that resolves logical resource identifiers against the installed package. The slice intentionally stops before `/flow:*` commands, `/flow:setup`, idea storage, and the UX package.

## Architecture summary

- **Workspace root** owns pnpm workspace configuration (`pnpm-workspace.yaml`), shared TS base config, root scripts that fan out into the workspace packages, and project-level docs.
- **`packages/pi-flow-core/`** ships the workflow resources Pi loads (skills, shared markdown contracts, prompt templates) plus the runtime helper-runner CLI binary (`bin/pi-flow.mjs`) used by skill prose. It also ships bundled `agents/*.md` definitions as passive package files (not yet symlinked into `pi-interactive-subagent` discovery paths). Python helpers and their existing unit tests are preserved with the `skills/<skill>/scripts/` shape so `sys.path.insert(... "_shared/scripts")` continues to resolve.
- **`packages/pi-flow/`** is the primary aggregate install package. It declares `pi-flow-core` as a workspace dependency and exposes the same skill set through a `pi` manifest that points at `node_modules/pi-flow-core/skills/...`. No source duplication; aggregate behavior is dependency forwarding only.
- **Helper runner** is a Node CLI (`bin/pi-flow.mjs`) registered as an npm `bin` entry in `pi-flow-core`. It resolves logical IDs of the form `<location>/<name>` to package-internal paths via `import.meta.url` resolution, executes Python scripts with `child_process.spawnSync('python3', ...)`, and forwards stdin/stdout/stderr/exit-code faithfully. Templates use a parallel `pi-flow template <id>` subcommand that prints the absolute path for use in `$()` subshells.
- **Resource ID grammar** is uniform across helpers and templates: `_shared/<name>` resolves to `skills/_shared/scripts/<name>.py` (helper) or `skills/_shared/<name>.md` (template); `<skill>/<name>` resolves to `skills/<skill>/scripts/<name>.py` (helper) or `skills/<skill>/<name>.md` (template).
- **Skill rewrite scope** is constrained: shell command invocations of `python3 agent/skills/...` or `python3 ~/.pi/agent/skills/...` are rewritten to `pi-flow helper <id>` / `pi-flow template <id>` form; human-facing prose cross-references switch to package-relative `skills/<id>` paths. Guardrail-heavy byte-equal blocks (menu strings, status messages, error templates), step ordering, and parsing contracts are preserved verbatim. The skill-authoring audit is bounded to descriptions and clearly redundant non-load-bearing sentences.

## Tech stack

- **Workspace manager:** pnpm with `pnpm-workspace.yaml`. Node ≥ 20.
- **Package format:** Pi packages with `keywords: ["pi-package"]` and a `pi` manifest. `type: "module"` ESM.
- **TypeScript:** ESNext / NodeNext, strict, `allowImportingTsExtensions: true`. Node strip-types runtime (no build).
- **Test runner — Node:** built-in `node:test` + `node:assert/strict`, invoked via `node --experimental-strip-types --test`.
- **Test runner — Python:** standard-library `unittest`, invoked via `python3 -m unittest discover`. Python 3.10+. No third-party Python dependencies.
- **CLI binary:** Plain Node ESM script (`bin/pi-flow.mjs`) — no compile step, executable shebang `#!/usr/bin/env node`.
- **Linting:** none in this slice. Type checking via `tsc --noEmit` for any future `.ts` files in the package; the helper-runner is `.mjs` for friction-free shipping.

## Risk Assessment

- **Pi package manifest schema is unverified.** The scout brief flagged this as an open question. The plan ships a conservative manifest (`keywords: ["pi-package"]` + `pi.skills` glob) plus the conventional `skills/` directory layout. If the installed Pi rejects this exact key shape, the fix is to adjust the manifest key/path in Task 2 (core) and Task 12 (aggregate) without restructuring the directory layout. **Mitigation:** Task 11's manifest test asserts the file structure independently of Pi's loader, so a manifest-shape mismatch surfaces as a single localized failure rather than a broken extraction.
- **npm `bin` entries may not be on PATH in Pi's skill-execution environment.** This is the spec's open question. **Mitigation:** the helper-runner doc names a fallback invocation (`node node_modules/pi-flow-core/bin/pi-flow.mjs`), and skill prose uses the bare `pi-flow helper <id>` form so PATH availability is the only swap point needed. If PATH isn't auto-populated by Pi, the follow-up setup/commands spec can wire a setup step that puts the bin on PATH or rewrites skills to the fallback form. The plan's extraction does not depend on PATH availability for verification — Task 10 invokes the binary as `node bin/pi-flow.mjs` explicitly.
- **Bounded skill-authoring audit may drift into behavior changes.** The spec is explicit that style edits must not weaken guardrails. **Mitigation:** Task 11's `guardrail-strings.test.mjs` enforces byte-equal preservation of the most load-bearing prompts (customize submenu, BLOCKED banner, model-tier templates, define-spec missing-file error, refine-code STATUS handlers, execute-plan verifier-dispatch boundary). Task descriptions explicitly forbid editing fixture content or rewriting guardrail prose for style.
- **Python `sys.path.insert` depth assumption.** Per-skill scripts compute `parents[N]` or `"..", "..", "_shared", "scripts"` paths relative to `__file__`. These remain valid only because the extraction preserves `skills/<skill>/scripts/` and `skills/_shared/scripts/` at the same relative depth as the source repo. **Mitigation:** Task 3 Step 4 and Task 4 Step 6 explicitly audit these references; Task 3 acceptance verifies `test_fence_aware.py` and `test_plan_fence_hardening.py` still pass under the new layout (the path-portability-sensitive helpers called out by the spec).
- **Cross-skill `refine-plan/scripts/prepare-plan-edit-prompt.py` default template path.** The DEFAULT_TEMPLATE expression resolves `parents[1] / ".." / "generate-plan" / "edit-plan-prompt.md"`. This only works because Task 7 also extracts `generate-plan/edit-plan-prompt.md` to the same package. **Mitigation:** Task 7's acceptance verifier explicitly resolves this path against the in-package `generate-plan/edit-plan-prompt.md` it creates, catching breakage at the point where both files exist together.
- **Aggregate manifest path syntax.** The plan ships `pi.skills: ["node_modules/pi-flow-core/skills/*/SKILL.md"]` from the aggregate. If Pi's loader does not resolve `node_modules/...` relative to the consuming package, the aggregate forwarding will fail. **Mitigation:** Task 12's `aggregate-forwarding.test.mjs` validates the glob expansion independently of Pi's loader behavior. If Pi's loader uses a different forwarding convention (e.g., re-exports via the `pi` key from each dependency), the manifest can be updated without touching `pi-flow-core` source.
- **`pi-interactive-subagent` version pin deferred.** The plan uses `peerDependencies: { "pi-interactive-subagent": "*" }`. This is intentional and documented in both READMEs; the spec defers pinning to the follow-up setup/commands spec. **Mitigation:** README explicitly flags `"*"` as a placeholder.
- **Skill description rewrites are subjective.** The audit in Task 5 Step 5, Task 6 Step 5, and Task 7 Step 6 may produce inconsistent results across executions. **Mitigation:** the audit is bounded to descriptions only and is explicitly skip-allowed when the existing description is already trigger-focused — the safer choice is to leave the description byte-equal.
- **Fixture files contain `agent/skills/...` strings.** Some test fixtures (e.g., spec-fit fixtures, fence-aware fixtures) embed `agent/skills/...` as sample content. **Mitigation:** Task 4 Step 3 explicitly preserves fixture content verbatim; Task 13 Step 3's grep audit excludes fixture directories.
- **Pi-driven package-loading smoke test depends on an unresolved spec open question.** The spec's Open Questions #1 and #2 explicitly flag that Pi's package manifest schema and the working-directory contract Pi uses when running skill shell commands are not documented in this repo. Writing a test that asserts a specific Pi CLI command shape would be fragile against an unverified API. **Mitigation:** Tasks 11 and 12 ship both (a) deterministic Node-level checks that the manifest shape and the `pi.skills` glob expand to the expected 15 SKILL.md files — these are the proxy the plan stands behind — and (b) a best-effort conditional `pi CLI discovery probe` test that detects `pi` on PATH, runs an actual `pi -e <package>` invocation when present, and emits a structured `skipped` message (without failing) when absent. The follow-up setup/commands spec is the right place to harden this into an unconditional assertion once Pi's loader contract is documented.
