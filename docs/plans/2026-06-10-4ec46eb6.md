# Plan: Add frontier model tier, rename cheap→efficient, standardize tier fields to model_tier

Source: IDEA-4ec46eb6
Spec: docs/specs/2026-06-10-4ec46eb6.md

## Goal

Introduce a new abstract logical model tier `frontier` above `capable`, rename the existing `cheap` tier to `efficient`, route `spec-designer` (via `define-spec`) and the initial `planner` (via `generate-plan`) through `modelTiers.frontier`, and standardize every consumer-side tier field/flag onto a single `model_tier` naming convention (`**Model tier:**` plan label, `model_tier` JSON key, `model_tier` fastlane run-state, `--model-tier` CLI flag). This is a clean hard cutover across config, the dispatch contract, skill docs, the planner rubric, execute-plan tables/ladders, scout/fastlane menus, the README, and the full test + fixture body — no `cheap`, `model_recommendation`, `coder_tier`, or `--tier` spelling, alias, or fallback may remain in pi-flow-owned code for model-tier resolution or workflow settings.

## Architecture summary

Dispatch resolution is centralized in `packages/pi-flow-core/skills/_shared/scripts/resolve-model-dispatch.py`, which takes a **section-qualified** tier path (e.g. `modelTiers.capable`, `crossProviderModelTiers.cheap`) via a CLI flag and prints a `{model, cli, provider, tier, executionPolicy}` envelope read from `~/.pi/agent/flow.json` (mirrored by `.pi/flow.json` and `packages/pi-flow-core/flow.example.json`). The config holds two tier sections — `modelTiers` (provider-preferred) and `crossProviderModelTiers` — each currently with `capable` / `standard` / `cheap`.

Two orthogonal axes change here:

1. **Tier vocabulary** (`cheap`→`efficient`, plus new `frontier`) — an *abstract tier alias* that appears as the leaf of a section-qualified path (`modelTiers.efficient`, `modelTiers.frontier`) and as a bare selectable value in planner/execute-plan/scout/fastlane menus and `extract-plan-tasks.py`'s `VALID_MODELS`. The JSON section objects `modelTiers` / `crossProviderModelTiers` and the section-qualified path form are **not** renamed — the section prefix encodes provider-preferred vs cross-provider routing, which a bare token cannot carry.
2. **Consumer-side field/flag naming** (`model_recommendation` / `coder_tier` / `--tier` → `model_tier` / `model_tier` / `--model-tier`) — the names by which consumers *pass* a bare tier alias. The section-qualified path string the `--model-tier` flag carries is unchanged in form.

The resolver is section-prefix-agnostic (it walks an arbitrary dot path), so adding `frontier` and renaming `cheap` requires **no resolver logic change** beyond the flag rename and docstring — `frontier` resolves the moment the config key exists. `frontier` provider mappings are fixed: provider-preferred `modelTiers.frontier` = `anthropic/claude-fable-5`; cross-provider `crossProviderModelTiers.frontier` = `openai-codex/gpt-5.5`. Cross-provider frontier resolution reuses the existing `openai-codex` entry in `subagentDispatch` — no new dispatch-map plumbing.

Routing changes are localized: `define-spec` Step 3a and `generate-plan` Step 2 swap their hardcoded `modelTiers.capable` tier path to `modelTiers.frontier`. All other dispatch sites (refine-plan's planner edit-pass, plan-reviewer/code-reviewer, coordinator chain, test-runner, scout, fastlane coder) keep their current tiers — they only pick up the `--model-tier` flag rename.

The executor (`extract-plan-tasks.py`) parses planner output, so the `**Model recommendation:**`→`**Model tier:**` label rename and `model_recommendation`→`model_tier` key rename must move together across the parser, its tests, and every `plan-*.md` fixture; the parser's `missing_model_recommendation` error-kind string is renamed to `missing_model_tier` to keep the cutover total.
