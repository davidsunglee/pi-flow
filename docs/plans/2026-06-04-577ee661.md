# Plan: Explicit Pi Coordinator Dispatch Configuration

**Source:** IDEA-577ee661
**Spec:** `docs/specs/2026-06-04-577ee661.md`

## Goal

Decouple coordinator runtime capability from provider-prefix model dispatch. Today the coordinator agents (`plan-refiner`, `code-refiner`) resolve their dispatch through the same tier→provider→`dispatch[<prefix>]` path leaf workers use (a fixed four-tier chain in `skills/_shared/coordinator-dispatch.md`), so a perfectly valid leaf-worker config with no `dispatch` entry resolving to `pi` (e.g. `anthropic → claude`, `openai-codex → codex`) breaks coordinator dispatch entirely. This plan introduces a dedicated `coordinatorDispatch.modelChain` section in `model-tiers.json` — an ordered list of exact model identifiers attempted in order via `subagent_run_serial` with `cli: "pi"` hardcoded as a system invariant — backed by a new validation helper script with byte-equal canonical error templates, a rewritten shared procedure, reconciled consumers, updated docs/examples, and Python + Node tests. There is no fallback to tier-based coordinator resolution under any failure; leaf-worker resolution is untouched.

## Architecture summary

The spec's chosen approach (script-backed validation) is expanded as follows:

- **New helper script** `skills/_shared/scripts/resolve-coordinator-dispatch.py` owns reading `~/.pi/agent/model-tiers.json` and validating the `coordinatorDispatch` section. On success it prints `{"modelChain": [...], "cli": "pi"}` (single-line JSON, `cli` hardcoded) on stdout; on failure it prints the byte-equal canonical template on stderr and exits 1. A **new script** (rather than a mode flag on `resolve-model-dispatch.py`) was chosen because the existing script's CLI contract (`--tier` required, four leaf templates) does not fit coordinator resolution (no tier, no provider-prefix extraction, no `dispatch` lookup); a separate single-purpose script matches the `_shared/scripts/` convention and guarantees the existing `test_resolve_model_dispatch.py` assertions pass unmodified. The helper-runner (`bin/pi-flow.mjs`) resolves `pi-flow helper _shared/resolve-coordinator-dispatch` to the new file automatically — no runner changes needed.
- **Rewritten procedure** `skills/_shared/coordinator-dispatch.md` remains the single authority for coordinator dispatch: invoke the validation helper → iterate `modelChain` entries in order via `subagent_run_serial` with the entry passed verbatim as `model` and hardcoded `cli: "pi"` → emit the runtime-exhaustion template verbatim if every entry fails. The four-tier chain, the skip-silently rule, and both old hard-stop strings are removed from the package's shipped content. The `## Note on worker subagents` contract (workers re-resolve via leaf-worker rules in `model-tier-resolution.md`) is preserved.
- **Canonical templates** (contract surface, byte-equal everywhere they appear — note every `—` is an em-dash, U+2014):
  - Reused Template 1 (emitted by the helper): `~/.pi/agent/model-tiers.json missing or unreadable — cannot dispatch <agent>.`
  - Missing section (helper): `model-tiers.json has no coordinatorDispatch section — cannot dispatch <agent>.`
  - No usable modelChain (helper): `model-tiers.json coordinatorDispatch has no usable modelChain — cannot dispatch <agent>.`
  - Runtime exhaustion (emitted by the orchestrating procedure, NOT the script, since only the orchestrating session can attempt `subagent_run_serial`): `coordinator-dispatch: all coordinatorDispatch.modelChain models failed; last attempt: <model> via pi — <error>`
- **Consumers** `refine-plan/SKILL.md` and `refine-code/SKILL.md` keep deferring to the shared file as single authority; their dispatch-resolution subsections, dispatch blocks (`cli: "pi"` literal), role-to-tier mapping line, and Edge Cases entries are reconciled. `model-tier-resolution.md` (schema example + `## Coordinator dispatch` section) and `orchestrator-verification-boundary.md` (mechanical-surface bullet) are updated to match.
- **Tests**: a new Python suite `test_resolve_coordinator_dispatch.py` asserts the success JSON shape and each config-failure template byte-equal (style of `test_resolve_model_dispatch.py`), plus a leaf-coexistence test proving `resolve-model-dispatch.py` is unaffected by the new section. New Node assertions in `__tests__/guardrail-strings.test.mjs` lock the new templates byte-equal in `coordinator-dispatch.md` and lock the absence of the old chain strings (durable grep-clean).
- **Leaf workers unchanged**: tier aliases, provider-prefix `dispatch` resolution, the four existing canonical templates, and all leaf consumers (`scout`, `define-spec`, `generate-plan`, `execute-plan`, `requesting-code-review`, `fastlane`, plus worker re-resolution inside the refiner prompts) behave exactly as before and never read `coordinatorDispatch`. The TS extension layer does not read `model-tiers.json` and is not touched.

```python
#!/usr/bin/env python3
"""
resolve-coordinator-dispatch — validate the coordinatorDispatch section of model-tiers.json.

Coordinator agents (plan-refiner, code-refiner) must run under the `pi` CLI because
nested orchestration tools (subagent_run_serial) exist only there. The Pi requirement
is a system invariant, not user configuration: the output hardcodes cli "pi" and
there is no cli key in the config. modelChain entries are exact model identifiers
passed verbatim to subagent_run_serial — no provider-prefix extraction and no
dispatch[<prefix>] lookup occurs for coordinator dispatch. Unknown extra keys inside
coordinatorDispatch are ignored.

Inputs:
  --agent        Coordinator agent name used in error messages
                 (e.g. "plan-refiner", "code-refiner")
  --model-tiers  Path to model-tiers JSON file (default: ~/.pi/agent/model-tiers.json)

Output (stdout, JSON) on success:
  {
    "modelChain": ["<exact model id>", ...],
    "cli":        "pi"
  }

Failure templates (written to stderr, exit 1):
  Template 1 — file missing or unreadable (shared with resolve-model-dispatch.py):
    ~/.pi/agent/model-tiers.json missing or unreadable — cannot dispatch <agent>.
  Missing section — coordinatorDispatch absent or not a JSON object:
    model-tiers.json has no coordinatorDispatch section — cannot dispatch <agent>.
  No usable modelChain — modelChain missing, not an array, empty, or containing any
  non-string or empty entry (rejected wholesale, no entry-skipping):
    model-tiers.json coordinatorDispatch has no usable modelChain — cannot dispatch <agent>.
"""
import argparse
import json
import os
import sys


def die(msg):
    sys.stderr.write(msg + "\n")
    sys.exit(1)


def main():
    parser = argparse.ArgumentParser(
        description=__doc__,
        formatter_class=argparse.RawDescriptionHelpFormatter,
    )
    parser.add_argument(
        "--agent",
        required=True,
        help="Coordinator agent name for error messages (e.g. 'plan-refiner')",
    )
    parser.add_argument(
        "--model-tiers",
        default="~/.pi/agent/model-tiers.json",
        help="Path to model-tiers JSON file (default: ~/.pi/agent/model-tiers.json)",
    )
    args = parser.parse_args()

    path = os.path.expanduser(args.model_tiers)
    try:
        with open(path) as f:
            data = json.load(f)
    except (IOError, OSError, json.JSONDecodeError):
        die(f"~/.pi/agent/model-tiers.json missing or unreadable — cannot dispatch {args.agent}.")

    section = data.get("coordinatorDispatch") if isinstance(data, dict) else None
    if not isinstance(section, dict):
        die(f"model-tiers.json has no coordinatorDispatch section — cannot dispatch {args.agent}.")

    chain = section.get("modelChain")
    if (
        not isinstance(chain, list)
        or not chain
        or any(not isinstance(entry, str) or not entry for entry in chain)
    ):
        die(
            f"model-tiers.json coordinatorDispatch has no usable modelChain — "
            f"cannot dispatch {args.agent}."
        )

    print(json.dumps({"modelChain": chain, "cli": "pi"}))


if __name__ == "__main__":
    main()
```

```markdown
# Coordinator dispatch resolution

## Why this exists

A coordinator (`code-refiner` or `plan-refiner`) must run on a `pi` CLI because `subagent_run_serial` is exposed only on `pi`; without `pi`, the coordinator cannot dispatch its workers. The Pi requirement is a system invariant, not user configuration: coordinator dispatch hardcodes `cli: "pi"` and there is no `cli` key to configure. Coordinator dispatch is therefore decoupled from the leaf-worker tier→provider→`dispatch[<prefix>]` path — a perfectly valid leaf-worker `dispatch` map (e.g. `anthropic → claude`, `openai-codex → codex`) needs no entry resolving to `pi`. Instead, the coordinator model chain is named explicitly in the `coordinatorDispatch` section of `~/.pi/agent/model-tiers.json` (see `docs/model-tier-setup.md` for the schema). When that section is missing or unusable, a hard stop is the only correct outcome — silently falling back to tier-based coordinator resolution or to an inline review is forbidden, as it conceals a broken dispatch path.

## Procedure

1. Run `pi-flow helper _shared/resolve-coordinator-dispatch --agent <agent>`, where `<agent>` is the coordinator agent name (`plan-refiner` or `code-refiner`). The helper reads `~/.pi/agent/model-tiers.json`, validates the `coordinatorDispatch` section wholesale (no entry-skipping), and on success prints `{"modelChain": [...], "cli": "pi"}` on stdout.
2. If the helper exits non-zero, surface its stderr message verbatim — it is one of the canonical templates in `## Hard-stop conditions` below — and do NOT dispatch. There is no fallback to tier-based coordinator resolution under any failure.
3. On success, attempt the coordinator dispatch for each `modelChain` entry in order via `subagent_run_serial` with that entry passed verbatim as `model` (entries are exact model identifiers, not tier aliases — no provider-prefix extraction and no `dispatch[<prefix>]` lookup occurs) and `cli: "pi"`. There is no up-front availability probing. On dispatch failure (model unavailable, transport error, etc.), record the failure and advance to the next entry.
4. Stop iterating when a dispatch succeeds. The successful `(model, "pi")` pair is the outcome of the procedure; the caller uses those exact values for its `subagent_run_serial` task.

## Hard-stop conditions
```

## Risk Assessment

- **Byte-drift in canonical templates.** The contract strings contain em-dashes (U+2014) and exact phrasing; a retyped hyphen or reworded clause silently breaks the byte-equal contract. Mitigation: every template appears verbatim in this plan at each site that writes it; Python tests (Task 1) and Node guardrail tests (Task 7) assert byte-equality; verify recipes use `grep -F` with the full literals.
- **Over-eager "skip silently" cleanup.** The package contains unrelated, legitimate "skip silently" phrasing (`skills/_shared/idea-closure.md`, `skills/fastlane/SKILL.md`, `skills/execute-plan/SKILL.md`, `extensions/setup.ts`, `skills/_shared/scripts/tests/test_parse_coder_report.py`). The grep-clean criterion targets only the hyphenated `skip-silently` and the coordinator-specific strings; tasks name the exact lines to edit and Task 7's negative test scopes to the four files that carried the old rule. Workers must not edit the unrelated files.
- **Grep-clean sweep vs. negative-assertion test data.** Task 7's new guardrail test intentionally contains the stale literals as assertion data, so the package-wide sweep excludes `__tests__`/`tests` directories. This matches the spec's intent ("appear nowhere in the package"): `package.json` `files` excludes those directories from the published tarball, so the swept surface equals the shipped package.
- **Spec under-specifies the non-object `coordinatorDispatch` case.** The spec enumerates "missing section" and "modelChain missing/not-array/empty/bad-entry" but not `"coordinatorDispatch": "pi"`. Plan decision: a non-object value (or JSON `null`, or a non-object top-level document) maps to the missing-section template, because a non-object cannot be a section; `test_non_object_section_is_missing_section` locks the behavior. This is an interpretation within the spec's fail-hard intent, not a deviation.
- **Reason-string wrapping in `refine-plan`.** The old Step 8 reason format (`coordinator-dispatch: <verbatim error message>`) would double-prefix the new exhaustion template and wrap the config templates, violating the spec's "consumers must not paraphrase or wrap them" constraint. The rewrite (Task 5) sets the verbatim template itself as the failed reason. This intentionally changes the skill's failure-reason surface; the `STATUS`/`FAILURE_REASON` line shapes in Step 11 are unchanged.
- **Cross-suite fixture coupling.** New tests use a new fixture (`model-tiers-coordinator.json`) plus inline tempfiles; the three existing fixtures and `test_resolve_model_dispatch.py` are untouched, guaranteeing the spec's "existing assertions pass unmodified" criterion structurally rather than by luck.
- **Helper discoverability.** `bin/pi-flow.mjs` resolves `_shared/<name>` to `skills/_shared/scripts/<name>.py` generically, and `run-helper-tests.ts` discovers `test_*.py` under the existing suite directory — no runner or test-harness changes are needed. Task 1 Step 7 smoke-tests the runner path to confirm.
- **Refiner prompt files are intentionally untouched.** `refine-plan-prompt.md` / `refine-code-prompt.md` mention `coordinator dispatch unavailable` — that failure mode concerns `subagent_run_serial` availability inside the already-running coordinator session, and their worker re-resolution rules are explicitly out of scope (workers re-resolve via leaf rules). Editing them would be overreach.
- **Runtime exhaustion template cannot be script-tested.** Only the orchestrating session can attempt `subagent_run_serial`, so the exhaustion template is LLM-emitted per the spec's approach. Mitigation: the Node guardrail test (Task 7) and the docs greps (Task 4) lock its byte-equal presence in `coordinator-dispatch.md` and `model-tier-setup.md`, which are the strings the orchestrator copies from.
