### Config resolution (current vs. required)

Current: `working.ts` coordinator `session_start` calls `loadSavedWorkingSettings(this.settingsPath)` → falls back to `DEFAULT_WORKING_SETTINGS` (spinner shape, generic color).

Required two-tier model: load packaged `working.json` as the intermediate default, then apply user `~/.pi/agent/working.json` on top if present. This requires adding a `packageDefaultPath` parameter to `WorkingCoordinator` (or a `loadPackageDefault` function) so the coordinator can merge: code minimum → packaged default → user override.

## Risk Areas

**1. `@mariozechner/*` → `@earendil-works/*` API compatibility**  
The package name change is confirmed (the devcontainer Dockerfile installs `@earendil-works/pi-coding-agent`), and the spec treats it as a rename not a port. However, `WorkingIndicatorOptions` type used in `effects.ts` must exist in the new package. The `ctx.ui.setWorkingIndicator` and `ctx.ui.setWorkingMessage` call signatures must match. The `footerData.getExtensionStatuses()` → `Map<string, string>` API must remain unchanged. These must be verified at typecheck time; API drift would require local type adjustments.

**2. `getWorkingCoordinator` singleton and two-tier config**  
The coordinator is a module-level singleton keyed only by `settingsPath`. Adding a packaged default path requires changing the `WorkingCoordinator` constructor signature or the `getWorkingCoordinator` factory. Since `indicator.ts` and `message.ts` both call `getWorkingCoordinator(settingsPath)` with the same path, they share one coordinator — this is intentional. The package default path must be threaded through without breaking this sharing invariant. The `resetWorkingCoordinatorForTests()` export must remain for tests.

**3. Working config default divergence**  
`DEFAULT_WORKING_SETTINGS` in `working.ts` uses `indicatorShape: "spinner"`, while `agent/working.json` uses `"pulse"`. Tests (e.g., `/working` command status shows `indicatorShape=spinner`) depend on the code-level default. If the packaged default JSON uses `"pulse"`, those tests must be updated to reflect that the packaged default now takes precedence over the code-level default on a fresh install — or the test setup must continue to bypass the package default path.

**4. TypeScript compilation in the package**  
`pi-flow-core` has a `tsconfig.json` and no compile step (it ships `.md` and `.mjs` files). `pi-flow-ux` needs TypeScript sources to be usable by Pi at runtime. Three options: (a) ship `.ts` files and rely on Pi's runtime TS support (consistent with how `pi-config` works), (b) pre-compile to `.js` with declaration files, (c) ship both. Pi appears to load `.ts` extensions via Node's `--experimental-strip-types` or a similar mechanism. This is the most likely intended approach given that the source test files also import `.ts` directly. Must be confirmed — if Pi cannot load `.ts` at runtime, a build step is required.

**5. Pi manifest `pi.extensions` and `pi.themes` field schema**  
No existing pi-flow package demonstrates these fields. The exact field names, glob format, and whether Pi supports multi-glob arrays must be verified from Pi documentation or the `pi-coding-agent` package manifest schema. Using the wrong field name or format would silently prevent resources from loading.

**6. Nord theme `$schema` URL**  
`nord.json` references `https://raw.githubusercontent.com/badlogic/pi-mono/main/...`. This is an old URL. The spec open question asks if this needs updating. It is unlikely to cause a runtime failure (schema URLs are typically advisory), but it may be flagged by validators.

**7. Test migration format**  
Migrating TypeScript tests to `.mjs` requires either (a) rewriting type-annotated test code as plain JS, or (b) keeping `.ts` extension and using `--experimental-strip-types` in the test runner command (matching the `pi-config` approach). The workspace `test:node` script pattern uses `find __tests__ -name '*.test.mjs'` which excludes `.ts` files — so the package would need its own `test:node` script with `--experimental-strip-types` if keeping TypeScript tests.

## Possible Misses

**Pi manifest field names for extensions and themes**  
The `pi-flow-core` and `pi-flow` packages only use `pi.skills`. The actual field names for extensions (e.g., `pi.extensions`, `pi.agents`) and themes (e.g., `pi.themes`) are not demonstrated in this repo. The spec says "accurate `pi` manifest entries" — but the exact schema is external to this codebase. If the field name is wrong (e.g., `"extensions"` vs. `"agent.extensions"` or some other nesting), Pi will silently not load the resources. This is the highest-risk unknown.

**Working.json path written by `/working` command**  
The `/working` command persists changes to `this.settingsPath` (the user config path). If the package default path is added as a separate concept, the persist logic must never write to the package-bundled file. The current `saveWorkingSettings` is path-agnostic — care is needed to ensure `persistWithToast` always targets the user path, not the package path.

**`index.ts` entry point uses default exports (already pre-called)**  
`working/index.ts` calls `workingIndicator(pi)` and `workingMessage(pi)` where `workingIndicator = default export of indicator.ts = createExtension()` (already called). This means the `index.ts` default export is `function(pi)` that registers both sub-extensions without accepting a settings path. For package-default config to work, either `index.ts` must be updated to pass the package default path through, or the coordinator must auto-detect the package default path when no user config is present. The current `createExtension(settingsPath)` factory pattern supports explicit path injection — this path injection mechanism needs to reach `index.ts`.

**`message.test.ts` shared coordinator dependency**  
`message.test.ts` boots both `createWorkingMessageExtension` and `createWorkingIndicatorExtension` with the same settings path to exercise the shared coordinator. This pattern will still work after migration, but if the coordinator signature changes (adding a package default path parameter), both factory call sites in the test must be updated consistently.

**Excluded extensions referencing working utilities**  
Several excluded extensions (e.g., `session-breakdown.ts`, `todos.ts`) may import from `working/` or share utilities. These are unrelated personal extensions not being migrated, but if any excluded file imports from `effects.ts` or `working.ts`, removing them from the scope is safe since they won't be in the package — but this is worth confirming no circular import into the retained files exists.

## Open Questions / Ambiguities

1. **Pi manifest field names for extensions and themes**: What are the exact field names and value format in `package.json`'s `pi` block for registering extension entry points and theme files? No in-repo example exists. Must be confirmed from Pi docs or `@earendil-works/pi-coding-agent` package metadata.

2. **Runtime TypeScript loading**: Does Pi load `.ts` extension files natively at runtime (via Node `--experimental-strip-types` or equivalent), or must they be pre-compiled to `.js`? The `pi-config` approach ships `.ts` and runs them directly — but the packaging mechanism may differ.

3. **Two-tier config API design**: The `getWorkingCoordinator(settingsPath)` singleton is currently keyed by `settingsPath`. Adding a `packageDefaultPath` changes the coordinator's initialization contract. The simplest approach: `getWorkingCoordinator(packageDefaultPath, userPath?)` — but this would break the existing singleton key logic if both paths differ across callers. A cleaner approach may be to embed the package default into the `normalizeWorkingSettings` call chain so the user override always wins and missing fields fall back to the packaged JSON rather than the hardcoded `DEFAULT_WORKING_SETTINGS`.

4. **Nord theme schema URL**: Should `nord.json`'s `$schema` be updated from the old `badlogic/pi-mono` URL to the current `earendil-works` equivalent? Is the correct URL known, or is it advisory-only?

5. **Aggregate manifest UX forwarding**: Should the aggregate `pi-flow` package expose UX resources to all Pi installs by default (making `pi-flow` opinionated), or should the README recommend that headless/minimal setups use `pi-flow-core` directly? The spec's open question acknowledges this; the implementation must choose whether to wire UX into the aggregate's `pi` manifest or leave it undeclared.

6. **`@earendil-works/*` API compatibility verification**: Which specific types and call signatures from `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui` need to be verified? The main risk points are `WorkingIndicatorOptions`, `ctx.ui.setWorkingIndicator`, `ctx.ui.setWorkingMessage`, `footerData.getExtensionStatuses()`, `theme.getColorMode()`, and `theme.getThinkingBorderColor()`.
