## Context
Pi package semantics allow a user-scoped package to be installed globally, while a project-scoped package of the same identity overrides it in that project; if the project has no entry, it inherits the user package. `/flow:doctor` currently does not model that effective-scope behavior. It compares every discovered pi-flow surface against one active root and unconditionally inventories both user and project install locations. As a result, an installed-but-overridden global pi-flow can render as `[SKEW]` when a project package is active, and a leftover project install can render as `[SKEW]` when the user package is active.

There is also a bootstrap limitation: `~/.pi/agent/bin/pi-flow` is a symlink to one concrete `@aphotic/pi-flow-core` root. One global symlink cannot simultaneously be correct for global-only sessions and every project that overrides pi-flow with a different root/version. Current doctor/setup can repoint it for the current cwd, but that makes the previous scope look skewed.

Related implementation observations:
- `classifySurface` only compares `realpath === activeRoot`, then labels any other install root `stale-skew`.
- `buildDiagnosis` always inspects both project and user installs/node bins regardless of which scope is effective.
- `hasSkew` only counts selected resolution kinds, but `renderReport` still prints `[SKEW]` for stale inactive inventory rows.
- declared package parsing/resolution is incomplete for npm entries: string `npm:` entries are treated as local paths, and npm declarations are reported unresolved.

## Goal
Allow `/flow:doctor` to report a clean, visually non-skewed state in all intended package-scope scenarios when the effective runtime surfaces are aligned:
1. user/global pi-flow only;
2. user/global pi-flow plus a project pi-flow override at the same version;
3. user/global pi-flow plus a project pi-flow override at a different version.

A project with no pi-flow package entry should inherit the user install. A project with a pi-flow package entry should override the user install. Doctor should distinguish inactive installed packages from actual helper/template/agent resolution skew.

## Scope
- Add an explicit effective-package model for pi-flow:
  - normalize user and project `packages` entries by package identity (`@aphotic/pi-flow`, aggregate-to-core, local/git/npm forms);
  - apply Pi's project-overrides-user package identity rule;
  - determine the active/effective root from loaded `flow:*` command `sourceInfo` and/or package settings;
  - classify discovered roots as `active`, `inactive-overridden`, `inactive-shadowed`, `local-dev`, `stale-skew`, etc.
- Change doctor rendering so inactive installs are not shown as `[SKEW]` by default. Consider a `--all`/inventory mode for inactive installs.
- Make helper-runner bootstrap scope-aware. Replace the single-root symlink model for `~/.pi/agent/bin/pi-flow` with a stable dispatcher shim that chooses the project effective target for the current cwd and falls back to the user target when no project override exists. The dispatcher must support aggregate npm installs and, if practical, local/git package sources.
- Keep project and user agent symlink management separate and scope-aware. A project override should be allowed to have project agents while the user install still provides user agents elsewhere.
- Fix declared package parsing/resolution for npm specs, including string-form `"npm:@aphotic/pi-flow"`, object-form `{ "source": "npm:@aphotic/pi-flow" }`, pinned versions, and aggregate-to-core resolution.

## Acceptance Sketch
- Add diagnosis tests for:
  - global-only pi-flow: no `[SKEW]`, `hasSkew === false`;
  - global pi-flow plus project override at same version but different root: no `[SKEW]`, project root is active, user install rows are absent or marked inactive;
  - global pi-flow plus project override at different version: no `[SKEW]`, project root is active, user install is inactive/overridden;
  - no project package entry with a global install and stale project `.pi/npm` directory: user root remains effective, stale project install is inactive inventory, not resolution skew;
  - helper dispatcher invoked from different cwds resolves the expected core root.
- `/flow:doctor --fix` repairs only active-scope resolution surfaces and does not require deleting valid inactive installs to get a clean report.
- `/flow:doctor` output can be visually clean (no `[SKEW]` rows) while both user and project pi-flow packages are installed.

## Open Questions
- Can pi-flow reuse Pi's package manager/settings APIs to compute effective package identity and roots, or must it reimplement just enough of package resolution?
- How should the dispatcher respect project trust? Should it refuse untrusted project settings and fall back to user scope?
- Should `local-dev` rows count as visually clean, or should doctor offer a stricter mode that requires every active surface to be the same install root?
- Where should the dispatcher store/cache resolved targets, if anywhere, so it remains robust after package updates or project moves?
- Should inactive install rows be hidden by default or shown with a neutral `[inactive]` tag?
