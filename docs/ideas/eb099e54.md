## Context
pi-flow-core workflow skills and dispatch helpers currently reference `~/.pi/agent/flow.json` as the runtime flow config source. Meanwhile, pi-flow already supports project-local package installs and project-scoped `.pi` state, and this repo has a project-local `.pi/flow.json`. The `pi-flow helper` / `pi-flow template` runner resolves helpers and templates from the active package root, but the dispatch configuration defaults to the global user file. That can produce mixed-version behavior: project-pinned workflow code may execute against a global flow config schema or model-tier set intended for a different pi-flow-core version.

## Goal
Centralize flow config resolution into a single project-aware contract and shared executable implementation so workflow skills, helper scripts, diagnostics, setup guidance, and docs all agree on which `flow.json` is active. Project-specific pi-flow versions should be able to use project-specific config without losing the existing user/global fallback.

## Scope
- Add a shared contract document, e.g. `packages/pi-flow-core/skills/_shared/flow-config-resolution.md`, and have call sites reference it instead of duplicating path logic.
- Add shared executable resolution logic under `packages/pi-flow-core/skills/_shared/scripts/`, used by dispatch/provenance helpers so behavior cannot drift from the contract.
- Add a public diagnostic helper, e.g. `pi-flow helper _shared/resolve-flow-config`, returning JSON such as `{ "path": "...", "scope": "explicit|project|user", "searched": [...] }`.
- Define resolution precedence:
  1. Explicit `--flow-config <path>` wins after `~` expansion / absolute normalization; if it is unreadable, fail and do not fall back.
  2. Project-local `<working-dir>/.pi/flow.json` when present/readable.
  3. User/global `~/.pi/agent/flow.json` as fallback.
  4. If none is usable, emit one canonical missing-config error from the shared contract.
- Define `working-dir` as the active workflow workspace root. Helpers should accept `--working-dir` and default to process cwd; workflows that already compute `WORKING_DIR` should pass it explicitly. Coordinator prompts and nested helper calls should thread the same `WORKING_DIR`. Git worktrees use the worktree root; if it lacks `.pi/flow.json`, resolution falls back to the user/global config unless an explicit `--flow-config` was supplied.
- Do not add a separate trust gate for project-local `.pi/flow.json`; package-resolution trust remains separate, and workflow execution already occurs in the project context.
- Update dispatch-related helpers (`resolve-model-dispatch`, `resolve-coordinator-dispatch`) and provenance validation (`validate-review-provenance`) to use the shared resolver, accept `--working-dir`, and preserve explicit `--flow-config` override behavior.
- Update skill prose and contracts (`dispatch-contract.md`, `refine-plan`, `refine-code`, coordinator prompts, and other dispatch call sites) to say “resolved flow config” and reference the shared contract rather than hard-coding `~/.pi/agent/flow.json`.
- Intentionally migrate canonical missing-config wording to name the searched location(s), with coordinated guardrail/test updates. For example: `flow.json missing or unreadable; searched <locations> — cannot dispatch <agent>.`
- Update `/flow:doctor` to report the resolved flow config path/scope for the current cwd, distinguish active package root from active flow config, and warn when no usable config exists or when a project-local package is active but resolution falls back to user/global config.
- Update `/flow:setup` guidance without changing its default mutation boundary: it should not silently create or overwrite flow config files, but should tell the user where to place project-local vs user/global config and how to copy from `flow.example.json` when config is missing.
- Update README and docs (`docs/flow-config-setup.md`, plus `helper-runner.md` / `version-alignment.md` where relevant) so they describe project `.pi/flow.json` for pinned/project-specific workflows and `~/.pi/agent/flow.json` as the user/global fallback.
- Add tests for explicit/project/user/missing precedence, unreadable explicit override failure, `--working-dir` behavior, updated canonical strings, doctor reporting, and setup/readme/doc guidance where covered by existing test patterns.

## Acceptance Sketch
- From a project containing `.pi/flow.json`, running `pi-flow helper _shared/resolve-model-dispatch --model-tier modelTiers.frontier --agent planner` uses the project config and succeeds even when the user/global config lacks that tier.
- Passing `--flow-config /some/path/flow.json` uses only that explicit file; if it is unreadable, the helper fails rather than falling back.
- Running from a workspace without `.pi/flow.json` continues to use `~/.pi/agent/flow.json`.
- The public `resolve-flow-config` helper reports the resolved absolute path, scope, and searched paths.
- Coordinator and nested helper flows thread the same `WORKING_DIR` and therefore resolve the same config consistently.
- `/flow:doctor` shows both the active pi-flow package root and the resolved flow config path/scope, with actionable warnings for missing config or project-local package + user-global fallback.
- `/flow:setup` remains non-destructive but gives current, useful guidance for creating either project-local or user/global flow config.
- README and flow-config docs explain when to use project `.pi/flow.json` versus `~/.pi/agent/flow.json`.
- Guardrail and helper tests pass with the new canonical missing-config wording.
