## Context

`refine-plan` and `refine-code` dispatch coordinator subagents (`plan-refiner` and `code-refiner`) that must themselves spawn worker subagents. That nested orchestration depends on `pi-mux-subagents` tools such as `subagent_run_serial`, which are available when the coordinator runs under Pi.

The current `model-tiers.json` provider-prefix dispatch map is suitable for leaf workers, but it conflates model/provider selection with runtime capability. If GPT/OpenAI models map to Codex and Anthropic models map to Claude Code, then no configured tier may resolve to `cli: "pi"`, causing coordinator dispatch to fail even though leaf workers are correctly routed.

## Goal

Make coordinator dispatch explicit, mandatory, and capability-aware so coordinator agents always run under Pi while leaf workers can continue using the normal provider-prefix dispatch map.

## Scope

Introduce a required `coordinatorDispatch` section in `model-tiers.json`, separate from `dispatch`:

```json
{
  "dispatch": {
    "anthropic": "claude",
    "openai-codex": "codex"
  },
  "coordinatorDispatch": {
    "cli": "pi",
    "modelChain": [
      "openai-codex/gpt-5.4"
    ]
  }
}
```

Semantics:

- Applies only to coordinator agents such as `plan-refiner` and `code-refiner`.
- `coordinatorDispatch.cli` must currently be exactly `"pi"`.
- `coordinatorDispatch.modelChain` is an ordered list of exact model names, not tier aliases.
- A single-entry `modelChain` is valid.
- Coordinator dispatch does not consult `dispatch[provider]`.
- Leaf workers continue to use existing tier aliases plus provider-prefix `dispatch` resolution.
- If `coordinatorDispatch` is missing, malformed, has an unsupported CLI, or has no usable models, fail hard. Do not fall back to the old tier-based coordinator resolution.

- `packages/pi-flow-core/model-tiers.example.json`

## Acceptance Sketch

- A config with `dispatch.openai-codex = "codex"` and `coordinatorDispatch.cli = "pi"` dispatches `plan-refiner` / `code-refiner` through Pi using the first available model from `coordinatorDispatch.modelChain`.
- Worker agents inside those coordinators still resolve through normal tier/provider dispatch and may run via Codex or Claude Code.
- A missing `coordinatorDispatch` causes a clear hard failure, e.g. `model-tiers.json has no coordinatorDispatch section — cannot dispatch coordinator agent.`
- A non-`pi` coordinator CLI causes a clear hard failure explaining that coordinator agents require Pi.
- Documentation explains why coordinator dispatch is separate from provider-prefix dispatch.

## Open Questions

- Should `coordinatorDispatch` be global for all coordinator agents only, or should future per-agent overrides be supported?
- What exact canonical error strings should be used for missing/malformed `coordinatorDispatch`?
- Should the resolver verify model availability up front, or simply attempt each model in `modelChain` in order and report the last dispatch error?
- Should `modelChain` eventually support per-model metadata, such as thinking level or execution policy, or stay as exact model strings only?
