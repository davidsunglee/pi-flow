## Problem

A `generate-plan` run for `docs/specs/2026-05-19-ux-package.md` produced a phase-style plan that was human-readable but not parseable by `execute-plan/extract-plan-tasks`. The likely cause is Claude Code's external `superpowers:writing-plans` skill activating during a planner or planner edit-pass dispatch and overriding/competing with pi-flow's executable-plan schema instructions.

## Goal

Harden pi-flow planner/refiner prompts so dispatched planner agents do **not** invoke, follow, or blend in external planning skills/plugins (e.g. Claude Superpowers `writing-plans`) and must obey the pi-flow executable-plan schema exactly.

## Likely files

- `packages/pi-flow-core/agents/planner.md`
- `packages/pi-flow-core/skills/generate-plan/generate-plan-prompt.md`
- `packages/pi-flow-core/skills/generate-plan/edit-plan-prompt.md`
- `packages/pi-flow-core/skills/refine-plan/refine-plan-prompt.md` (planner edit-pass instructions)
- Any prompt/template tests that assert required planner/refiner wording

## Acceptance criteria

- Planner prompts explicitly state that host/Claude/plugin/external planning skills are out of scope and must not be invoked or followed.
- Planner prompts explicitly state that pi-flow's executable-plan schema (`## Goal`, `## Architecture summary`, `## Tech stack`, `## File Structure`, `### Task N: ...`, `## Dependencies`, `## Risk Assessment`, optional `## Test Command`) takes precedence over any other planning format.
- Refiner planner edit-pass instructions preserve the executable schema and do not allow phase-style rewrites.
- Tests or prompt-contract checks cover the new anti-external-skill instruction and required schema priority wording.
- A plan generated/refined through the normal flow passes `pi-flow helper execute-plan/extract-plan-tasks --plan <plan>` before being reported as approved/executable.
