## Context

`@aphotic/pi-flow-ux` now has both a footer status renderer and a border-status editor renderer. The desired default is to use the border-status editor, while keeping the footer renderer available for users who prefer it. Only one status placement should be active at any point in time.

## Goal

Create a single owning status extension that coordinates status UI placement and installs exactly one of: border-status editor, footer renderer, or no status UI.

## Scope

- Add a unified status extension, likely `packages/pi-flow-ux/extensions/status/index.ts` or `packages/pi-flow-ux/extensions/status.ts`.
- Move or wrap the existing border-status and footer installation logic behind the coordinator.
- Support a persisted configuration value such as `status.placement` with allowed values: `border`, `footer`, and `off`.
- Default missing configuration to `border`.
- Ensure mutual exclusion: when `border` is active, the footer renderer is not installed; when `footer` is active, the border editor is not installed; when `off`, neither is installed.
- Provide a command such as `/status-ui` to inspect and change placement interactively or via arguments, e.g. `/status-ui border`, `/status-ui footer`, `/status-ui off`.
- Update package manifests so the unified status extension is loaded by default instead of independently loading both status renderers.
- Preserve the existing working indicator/message extension behavior.
- Keep a clean migration path for eventually removing the footer renderer implementation.

## Acceptance Sketch

- Loading `@aphotic/pi-flow-ux` defaults to the border-status editor.
- Users can switch to footer status and back without enabling both renderers simultaneously.
- Users can turn status UI off.
- The selected placement persists across Pi reloads/sessions.
- Existing footer and border-status behavior is preserved when selected.
- Tests cover default placement, switching, persistence, manifest wiring, and mutual exclusion.

## Open Questions

- Where should the persisted configuration live: a new `~/.pi/agent/pi-flow-ux.json`, the existing `working.json`, or another package-specific config file?
- Should direct `footer.ts` and `border-status.ts` entry points remain as compatibility shims, or should manifests expose only the new coordinator?
- Should switching placement take effect immediately in the current session, require `/reload`, or support both?
