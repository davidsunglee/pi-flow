## Context

`define-spec` currently has its own helper at `packages/pi-flow-core/skills/define-spec/scripts/detect-mux-backend.py` that duplicates terminal multiplexer detection logic. That copy is now out of sync with `@aphotic/pi-mux-subagents`: the runtime detector supports the shared `pi-mux-detect` script and includes backends such as `herdr`, while the define-spec helper still manually checks only the older backend set (`cmux`, `tmux`, `zellij`, `wezterm`).

The define-spec skill still needs a small wrapper because it has define-spec-specific behavior:

- it scans slash-command text for inline override phrases such as `--no-subagent`, `without a subagent`, `without subagent`, `no subagent`, and `skip subagent`;
- it emits define-spec branch names (`mux` vs `inline`) and the existing user-facing `status_message` strings;
- it is invoked through `pi-flow helper define-spec/detect-mux-backend`, so downstream skill instructions and helper-runner docs should not need a new helper ID.

Recon already performed:

- `pi-mux-detect` exists in `@aphotic/pi-mux-subagents` as the package-level detector CLI.
- Its JSON payload contains `backend` (`pane` or `headless`), `mux` (e.g. `herdr`, `cmux`, `tmux`, `zellij`, `wezterm`, or `null`), `modeForced`, `muxPreference`, `muxPreferenceInvalid`, and `reason`.
- Searching workflow skills for mux-detection terms found only define-spec doing actual multiplexer detection. Other hits are references to subagent dispatch, mux terminal completion, or `@aphotic/pi-mux-subagents` parallel caps, not independent detectors.

## Goal

Make `define-spec` delegate mux detection to `pi-mux-detect` so its branch decision stays aligned with `@aphotic/pi-mux-subagents`, including `herdr`, while preserving the define-spec helper contract used by the skill.

## Scope

Implement this as a fastlane-sized adapter change.

Suggested implementation checklist:

1. Update `packages/pi-flow-core/skills/define-spec/scripts/detect-mux-backend.py` so it no longer manually probes mux environment variables or `command -v` state. Instead, invoke `pi-mux-detect` and adapt its JSON output.
2. Keep the helper's define-spec output contract: one JSON object on stdout with `branch`, `backend`, `reason`, and `status_message`; no extra stdout text.
3. Preserve existing override phrases. Prefer evaluating the user-input override before invoking `pi-mux-detect` so a deliberate inline run does not fail just because the external detector is unavailable.
4. Resolve `pi-mux-detect` robustly: try `PATH` first, then reasonable package-local / repo-local `node_modules/.bin/pi-mux-detect` locations so both the monorepo and installed package layouts work.
5. On detector execution failure or invalid detector JSON, exit non-zero and write a structured JSON failure to stderr. Do not silently choose `inline`, because that would mask broken subagent infrastructure.
6. Update `packages/pi-flow-core/skills/define-spec/SKILL.md` to say the helper delegates runtime mux detection to `pi-mux-detect`, and that the helper only adapts output plus applies define-spec's inline override phrases. Remove stale wording about duplicating runtime precedence rules byte-for-byte.
7. Update helper-runner documentation only if the helper contract text needs to mention the delegation.
8. Replace duplicate rule-by-rule tests in `packages/pi-flow-core/skills/define-spec/scripts/tests/test_detect_mux_backend.py` with wrapper-contract tests that use a fake `pi-mux-detect` on `PATH`.
9. Keep or add an audit note/test expectation documenting that no other workflow skill currently carries its own mux detector.

Out of scope:

- Changing `@aphotic/pi-mux-subagents` itself.
- Changing `subagent_run_serial` / pane selection behavior.
- Renaming the define-spec helper ID.
- Broad refactors of define-spec or the helper runner.
- Creating a new multiplexer detection abstraction in `pi-flow-core`; `pi-mux-detect` is the shared source of truth.

## Acceptance Sketch

Behavioral acceptance:

- With a fake `pi-mux-detect` returning `{ "backend": "pane", "mux": "herdr", ... }`, `pi-flow helper define-spec/detect-mux-backend` returns `branch: "mux"`, `backend: "herdr"`, and the existing mux status message: `Running spec design in subagent pane (mux detected, no override).`
- With a fake detector returning `backend: "headless"`, the helper returns `branch: "inline"`, `backend: null`, and the existing no-mux status message: `Running spec design in this session (no multiplexer detected).`
- With `--user-input` containing any existing override phrase, the helper returns the existing override status message and `branch: "inline"`; this path does not require invoking the detector.
- Detector stderr / nonzero exit and invalid JSON are reported as structured failures on stderr with a nonzero exit code.
- The helper stdout remains exactly one JSON object plus one trailing newline on success.
- `define-spec/SKILL.md` no longer claims the helper duplicates runtime mux precedence rules; it points maintainers to `pi-mux-detect` as the source of truth.
- A repo search confirms there are no other workflow skill helpers or skill docs implementing independent mux detection logic that should be migrated.

Verification commands for fastlane:

```bash
cd packages/pi-flow-core
python3 -m unittest discover -s skills/define-spec/scripts/tests -p "test_*.py"
pnpm run test:helpers
pnpm run test:node
```

## Open Questions

- Should the wrapper's `reason` field be a direct pass-through of `pi-mux-detect.reason`, or should it normalize to shorter define-spec-specific reason codes? Recommendation: pass through the detector reason (or include it in the wrapper reason) because the source-of-truth detector is now external; tests should assert the branch/status contract rather than preserving the old duplicated reason strings.
- Should helper resolution fail hard when `pi-mux-detect` is unavailable? Recommendation: yes for normal detection, because missing `pi-mux-detect` means the peer dependency/runtime detector is not installed or not discoverable. The only exception is an explicit user inline override, which can succeed without detection.
