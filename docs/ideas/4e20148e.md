## Context

Current `execute-plan` verifier handling still fails closed on report syntax even when the report contains clear substantive PASS evidence. As of the current codebase:

- `packages/pi-flow-core/skills/execute-plan/scripts/parse-verifier-report.py` still requires exact `[Criterion N] PASS|FAIL` per-criterion headers and an exact `VERDICT: PASS|FAIL` line.
- Any parser `protocol_errors` still force final `"verdict": "FAIL"`.
- Phase 1 command evidence still requires each `command:` field to byte-match the extracted command-style recipe.
- `packages/pi-flow-core/skills/execute-plan/SKILL.md` and `acceptance-criteria-verification.md` still route malformed output / Phase 1 protocol errors as `VERDICT: FAIL`; protocol errors never pass.
- Existing tests still assert strict failures for common human-readable variants such as lowercase/extra-token verdicts and for command-field mismatches.

This means the original `f6eac473` failure mode remains reproducible: a verifier can explicitly mark every criterion PASS, show successful command evidence, and summarize an overall PASS, yet `execute-plan` will redispatch/remediate solely because the report shape or command field is syntactically nonconforming.

## Goal

Improve execute-plan verifier ergonomics so the orchestrator does not waste retries or re-run verification solely to repair report syntax when a verifier-produced report already contains clear, auditable PASS evidence for every acceptance criterion.

The solution must remain safe: the orchestrator must not inspect implementation files itself, invent evidence, or silently reinterpret ambiguous verifier output as passing.

## Scope

Implement an explicit tolerant/repair path for verifier protocol-only defects. Candidate shape:

- Keep strict parsing as the primary path for exact legacy-format verifier reports.
- Add a second path that can identify `semantic_pass_with_protocol_warnings` only when the verifier report itself contains all required substantive evidence: every criterion is explicitly PASS, command-style criteria include successful command evidence, and no criterion/evidence is missing or ambiguous.
- Distinguish protocol-only formatting defects from hard verification failures in parser/orchestrator output.
- Consider a mechanical report-reformat helper/subagent that rewrites an existing verifier report into the strict format without re-running commands and while preserving original evidence verbatim.
- Consider replacing byte-equal matching against full natural-language `Verify:` prose with a machine-copyable command field in generated prompts/plans, if that is the root cause of command-field mismatch.
- Update execute-plan documentation so the allowed repair/tolerant path is explicit and remains within the orchestrator-verification boundary.

Out of scope: ad hoc orchestrator verification, file inspection by the orchestrator to prove acceptance criteria, or accepting reports with missing/failing evidence.

## Acceptance Sketch

- A regression fixture based on the `f6eac473` Wave 1 verifier reports no longer requires verifier redispatch when all criteria are explicitly PASS and command outputs show success; it either parses as a semantic pass with protocol warnings or is mechanically repaired into the strict format.
- True verifier failures still fail: missing criteria, failing command exit codes, absent command evidence, ambiguous PASS/FAIL wording, or missing evidence for a command-style criterion must not be accepted silently.
- Parser/orchestrator output clearly distinguishes hard `FAIL` from protocol-only formatting defects / repairable reports.
- Existing exact-format verifier reports continue to parse as before.
- Tests cover at least: exact legacy format, common human-readable PASS format, command-field paraphrase with preserved successful evidence, malformed/ambiguous verdicts, missing evidence, and failing command evidence.
- execute-plan docs explain the repair/tolerant route and reaffirm that the orchestrator may only parse or mechanically reformat verifier-produced evidence, not create evidence itself.

## Open Questions

- Should tolerance live in `parse-verifier-report`, in a separate repair helper, or in execute-plan routing around the strict parser?
- Is user confirmation required before accepting a semantic PASS with protocol warnings, or can tightly defined protocol-only cases pass automatically?
- Should plan generation split `Verify:` recipes into separate machine-command and human-success-condition fields to avoid byte-equal matching against prose?
