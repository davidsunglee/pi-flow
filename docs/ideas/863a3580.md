## Context
pi-flow currently uses `releasing.md` as its release guideline. The `pi-mux-subagents` project has an existing Release skill with a very similar process and should be used as the baseline reference for the formalized workflow.

The shared release process should preserve the same safety model: the LLM can inspect the repo, run local checks, draft or update release artifacts, and provide exact instructions, but the user performs credentialed actions such as NPM publishing, git pushes, tag pushes, and GitHub release publication.

pi-flow is a multi-module project, so its release process has extra steps beyond a normal single-package release. Those additions should be incorporated into the skill rather than left only in a separate `releasing.md` document if possible.

## Goal
Create one reusable Release skill that can handle both single-package/normal projects and multi-module projects, rather than forking a pi-flow-only copy of the `pi-mux-subagents` skill.

The skill should formalize the release workflow enough that `releasing.md` is no longer needed unless it contains vital project-specific context that cannot reasonably be incorporated into the skill.

## Scope
- Review the existing Release skill in `pi-mux-subagents` and use its structure and release gates as the starting point.
- Review pi-flow’s `releasing.md` and evaluate its additions one-by-one, deciding where and how each belongs in the reusable skill.
- Support both single-package and multi-module release paths.
- Auto-detect project shape from repository/package structure where possible, especially workspace or multi-module metadata.
- Ask the user to confirm the detected project shape before proceeding, and allow an explicit override.
- Preserve shared release gates and guardrails, including:
  - git leaks/secrets checking before release;
  - release readiness checks from the baseline skill;
  - release notes generation or preparation in the expected format/style;
  - an explicit manual review and edit opportunity for release notes;
  - clear instructions for user-run NPM authentication and publishing;
  - clear instructions for user-run git pushes, tag pushes, and GitHub release publication when applicable.
- Add multi-module handling needed by pi-flow, based on `releasing.md`, without weakening the shared gates.
- Keep credentialed activities user-owned: the skill should provide instructions and pause for confirmation, not perform authenticated publishing or release pushes itself.

## Acceptance Sketch
- A Release skill exists and can be invoked for both single-package and multi-module projects.
- The skill uses the `pi-mux-subagents` Release skill as its baseline process.
- The skill incorporates pi-flow’s multi-module release additions from `releasing.md` after explicitly considering each addition.
- The skill detects likely project shape, asks the user to confirm it, and supports explicit override.
- The skill runs or instructs the user through the required local release gates, including git leaks/secrets checking.
- The skill gives release notes format/style guidance and pauses for manual review/editing before publication.
- The skill has guardrails requiring the user to perform credentialed actions, including NPM publishing, git pushes, tag pushes, and GitHub release publication.
- `releasing.md` can be removed or reduced to a pointer unless implementation discovers essential project-specific context that cannot be incorporated into the skill.
