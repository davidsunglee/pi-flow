## Context

The current `@aphotic/pi-flow-ux` package has accumulated complexity from supporting multiple status placements (`border`, `footer`, `off`) and separate configuration/commands for status and working UI:

- `/status` controls border/footer/off placement via `status.json`.
- `/working` controls working indicator/message styling via `working.json`.
- The status coordinator has to install mutually-exclusive renderers and pair border status with a blank footer.
- The working coordinator has to coordinate host working-row rendering versus border-owned working rendering.
- Separate extension entrypoints (`extensions/status/index.ts`, `extensions/working/index.ts`) and nested file structure obscure the core UX shape.

After using border status, we want to make it the sole design direction. We do not need runtime switching between border status and footer status. We also do not need backward compatibility for old config names or files; the owner controls all deployments and is willing to change configurations directly. There should be no legacy readers, migrations, aliases, or compatibility shims for the old design.

A useful structure reference is `jwu/pi-powerline`, whose `extensions/` directory uses explicit top-level extension modules such as `index.ts`, `editor.ts`, `footer.ts`, `header.ts`, `settings.ts`, and helper modules. We want to borrow the clarity of that layout without inheriting its heavier per-feature toggles or `/powerline` settings model.

## Goal

Redesign `pi-flow-ux` around a simple, fixed UX model:

1. Border status is always enabled.
2. Pi's default footer/status duplication is suppressed by a small footer override.
3. Pi's host working row is suppressed because activity is incorporated into the editor border.
4. A custom header is added as part of the package UX.
5. All user-facing TUI options are configured through one command and one config file:
   - command: `/tui`
   - config: `tui.json`
6. The only initially supported user-configurable working option is the indicator shape, named `indicator` everywhere.
7. The command syntax is subcommand-based, not dotted:
   - `/tui`
   - `/tui working indicator=wave`
8. No legacy readers, migrations, aliases, or compatibility band-aids for `status.json`, `working.json`, `/status`, `/working`, `indicatorShape`, dotted `/tui working.indicator=...`, or short `/tui indicator=...` forms.

The package should be easier to explain as: `pi-flow-ux` owns the editor border, working activity cues, blank footer, header, Nord theme, and a small `/tui` configuration surface.

## Scope

### Package structure

Move toward a top-level extension layout similar to:

```text
packages/pi-flow-ux/
  extensions/
    index.ts              # single pi extension entrypoint; explicitly registers UX pieces
    editor.ts             # current border-status editor behavior
    footer.ts             # blank footer / default footer suppression
    working.ts            # working state tracking + tui.json config + /tui command
    header.ts             # custom startup header
    effects.ts            # pure visual effects for indicators, gleam, rainbow, colors
    working-messages.ts   # retained catalog of possible working messages; not rendered initially
  themes/
    nord.json
  tui.json                # packaged defaults
```

Keep the existing working-message strings in source control, but move them out of the state/config module. A separate `working-messages.ts` keeps `working.ts` focused on state, config, and `/tui`, while preserving the message catalog for a future placement decision.

Update manifests so the standalone package and aggregate package expose only the single UX entrypoint:

```json
"pi": {
  "extensions": ["extensions/index.ts"],
  "themes": ["themes"]
}
```

The aggregate `@aphotic/pi-flow` should forward only:

```text
node_modules/@aphotic/pi-flow-ux/extensions/index.ts
node_modules/@aphotic/pi-flow-ux/themes/nord.json
```

### Remove status-placement complexity

Remove the concept of configurable status placement entirely:

- Delete `/status`.
- Delete `status.json`.
- Delete `StatusPlacement = "border" | "footer" | "off"`.
- Delete the `StatusCoordinator` and renderer installer plumbing.
- Delete the custom status footer renderer as a user-selectable placement.
- Keep only the border editor behavior and a blank footer override.

Border status should always draw:

- lower-left: activity slot, model id, optional thinking level when reasoning is enabled;
- lower-right: context token/window detail and context percentage;
- upper-right: cwd with home substitution and tail truncation;
- vertical editor edges and responsive truncation/drop rules from the current border editor.

### Unified TUI config

Replace separate `working.json`/`status.json` with `tui.json`.

Canonical packaged/user config shape:

```json
{
  "version": 1,
  "working": {
    "indicator": "wave"
  },
  "header": {},
  "editor": {},
  "footer": {}
}
```

Only `working.indicator` is meaningful initially. The empty `header`, `editor`, and `footer` objects are placeholders for future UX options, not active toggles.

Valid indicator values:

```ts
"dot" | "pulse" | "spinner" | "wave"
```

Default indicator:

- packaged default: `wave`
- code fallback default: `wave`

Config resolution:

1. User override: `~/.pi/agent/tui.json`.
2. Packaged default: `packages/pi-flow-ux/tui.json` / installed package `tui.json`.
3. Code default.

Failure semantics:

- Missing user `tui.json` → packaged default.
- Malformed user `tui.json` → packaged default.
- Missing packaged `tui.json` → code default.
- Malformed packaged `tui.json` → throw loudly.

Explicitly do not read, write, migrate, or honor:

- `status.json`
- `working.json`
- `indicatorShape`
- `/status`
- `/working`
- `/tui working.indicator=...`
- `/tui indicator=...`
- any other legacy aliases or compatibility forms

### `/tui` command

Add a small unified command using a subcommand syntax:

```text
/tui
/tui working indicator=dot|pulse|spinner|wave
```

Behavior:

- `/tui` reports current TUI settings.
- `/tui working indicator=<shape>` updates `working.indicator`, applies immediately, and persists to `~/.pi/agent/tui.json` atomically.
- Invalid input shows concise usage.

Do not add component toggles yet (`header:on`, `footer:off`, etc.). Loading the package means the UX is enabled.

### Working behavior simplification

The old working configuration can be dramatically simplified.

Keep:

- event tracking for active turn, tool use, and thinking state;
- indicator shape selection;
- border activity slot animation;
- ability for editor rendering to query a working snapshot;
- the source-code catalog of possible working messages, stored separately from `working.ts`.

Remove from user configuration and initial runtime UI:

- per-state colors;
- per-state gleam/rainbow toggles;
- active/tool-use/thinking style objects;
- `/working` command;
- separately rendered host working message/indicator surfaces;
- initial working-message display.

The working module should suppress Pi's normal working row while `pi-flow-ux` is installed, because activity is represented in the editor border. It can still expose a snapshot such as:

```ts
{
  visible: boolean;          // true while any activity is happening
  state: "active" | "toolUse" | "thinking";
  settings: { working: { indicator: Indicator } };
}
```

Working messages may be revisited later. Do not over-design their placement now. If added later, they should fit under the unified `tui.json`/`/tui` model.

### Activity visual effects

Add clearer activity indication in the editor border because the current activity glyph alone can be too subtle.

Desired effects:

- Whenever the working indicator is displayed / any activity is happening:
  - apply a gleam effect to the model name;
  - no rainbow on the model name.
- Only while thinking is happening:
  - apply a rainbow effect to the thinking level text;
  - no gleam on the thinking level.
- During tool use:
  - model gleams;
  - thinking level remains normal/muted if displayed.
- During idle:
  - no gleam;
  - no rainbow;
  - activity slot returns to border-fill dashes.

Responsibility split:

```text
working.ts   # state/config: what is happening and which indicator is selected
effects.ts   # pure hardcoded visuals: indicator frames, gleam, rainbow, time-based frame helpers
editor.ts    # placement/composition: apply effects to model/thinking text in border lines
```

`effects.ts` should contain pure helpers such as:

```ts
pickWorkingIndicatorFrame(indicator, state, nowMs)
renderGleam(text, nowMs)
renderRainbow(text, nowMs)
```

The gleam/rainbow effect colors should be hardcoded in `effects.ts`. They do not need to reflect the Nord theme or any other active theme.

`editor.ts` should use the working snapshot to decide where effects are applied.

Important animation detail: the editor render timer must run whenever `snapshot.visible` is true, not only when the selected indicator has multiple frames. If the user selects a static indicator such as `dot`, the model gleam and thinking rainbow still need redraw cadence.

### Header

Add a custom header module using `ctx.ui.setHeader(...)`.

The initial header should:

- use the pi gradient logo;
- be left-justified, not centered;
- include a blank line between the logo and metadata;
- include two metadata lines below the blank line:
  - `version <pi version>` (for example, `version 0.78.0`)
  - the startup reason, also left-justified
- avoid any connection to the Nord theme;
- avoid diagnostics/scanning and settings toggles.

Reusable implementation ideas from `pi-powerline/extensions/header.ts`:

- `ctx.hasUI` guard.
- `ctx.ui.setHeader(...)` on `session_start`.
- component shape with `render(width)` and `invalidate()`.
- `VERSION` display from `@earendil-works/pi-coding-agent`.

Avoid inheriting:

- `/powerline` settings and events;
- header on/off toggles;
- heavy package/extension/theme diagnostic scanning;
- `quietStartup` behavior;
- `/builtin-header` restore command;
- broad synchronous filesystem scans.

## Acceptance Sketch

A future implementation is acceptable when:

- `packages/pi-flow-ux/package.json` exposes only `extensions/index.ts` for UX extensions.
- `packages/pi-flow/package.json` forwards only `node_modules/@aphotic/pi-flow-ux/extensions/index.ts` for UX extensions.
- `status.json` and `working.json` are gone from the package and no runtime code reads them.
- `/status` and `/working` are no longer registered.
- `/tui` is registered and supports:
  - reporting current settings;
  - updating `working.indicator` to `dot`, `pulse`, `spinner`, or `wave` using `/tui working indicator=<shape>`;
  - persisting to `~/.pi/agent/tui.json`.
- Dotted and short command forms such as `/tui working.indicator=wave` and `/tui indicator=wave` are not accepted unless deliberately introduced later as new features.
- `tui.json` exists at the package root with `version: 1` and `working.indicator` defaulting to `wave`.
- The code fallback default for `working.indicator` is also `wave`.
- No legacy compatibility code exists for old files, old commands, old field names, or old placement modes.
- Border status is always active when the package loads.
- Pi's duplicate default footer/status surface is blanked/suppressed.
- Pi's host working row is suppressed while the package UX is installed.
- The editor border still shows activity, model, thinking level, context usage, and cwd with existing responsive behavior.
- During any activity, the model name gleams.
- During thinking, the thinking level is rainbow-colored without gleam.
- Tool use and ordinary active work do not rainbow the model or thinking level.
- Static indicators such as `dot` still animate the model gleam / thinking rainbow while activity is visible.
- Hardcoded visual effects live in `effects.ts`, not in `working.ts`.
- Working state/config logic lives in `working.ts`.
- The existing working message catalog is retained in a separate source module, such as `working-messages.ts`, but no working message is rendered initially.
- A custom header is installed through `setHeader` with a left-justified pi gradient logo, blank line, `version <VERSION>`, and startup reason.
- The header does not bring in powerline settings, toggles, diagnostics, or filesystem scanning.
- Tests are updated to reflect the new single-entrypoint structure, removed configs/commands, `tui.json`, and `/tui` behavior.
- README/package docs describe the simplified UX model and no longer describe status placement, footer mode, `/status`, `/working`, `status.json`, or `working.json`.

## Open Questions

None for this pass. The initial choices are:

- header: left-justified pi gradient logo with version and startup reason below it;
- command syntax: `/tui working indicator=<shape>` only;
- working messages: retained as source data but not displayed initially;
- defaults: `wave` in both packaged `tui.json` and code fallback;
- effects: hardcoded in `effects.ts`;
- config placeholders: keep `header`, `editor`, and `footer` empty objects in `tui.json`.
