## Context

`pi-flow` workflow skills invoke helper scripts as `pi-flow helper ...`, but Pi package loading does not always expose a package's npm `bin` entry on the shell `PATH` used by Pi tools and subagents. This is especially visible for Git package installs such as `pi install git:...`.

Observed failure shape:

```text
/bin/bash: pi-flow: command not found
```

The helper runner already exists and works when invoked directly:

```sh
node <installed-pi-flow-core>/bin/pi-flow.mjs <args>
```

Pi prepends `~/.pi/agent/bin` to PATH, so setup can use that directory as the stable bootstrap point for a `pi-flow` command shim.

This is not about bundled agent discovery. `/flow:setup` already links bundled `pi-flow-core/agents/*.md` into the `@aphotic/pi-mux-subagents` discovery directory, and `packages/pi-flow-core/__tests__/setup-dispatch-smoke.test.mjs` covers that seam.

## Goal

Make an explicit setup/bootstrap path ensure `pi-flow` resolves on PATH inside Pi bash/tool/subagent execution contexts, without relying on npm `bin` exposure and without install-time side effects.

The likely target is a conflict-safe shim:

```text
~/.pi/agent/bin/pi-flow -> <this pi-flow-core package>/bin/pi-flow.mjs
```

## Scope

In scope:

- Extend `/flow:setup` or its setup helpers so user/global setup creates or verifies the `~/.pi/agent/bin/pi-flow` shim.
- Derive the installed `pi-flow-core` package root at runtime; do not hard-code user-specific paths.
- Keep shim handling idempotent and conflict-safe:
  - missing target → create it
  - already points to this package's `bin/pi-flow.mjs` → report `skipped`
  - real file, directory, or divergent symlink → report `conflict` and do not overwrite silently
- Preserve existing `/flow:setup` bundled-agent symlink behavior.
- Preserve the no-install-side-effects policy in `package.json`; this should be an explicit setup action, not a `postinstall` script.
- Use the safer first-pass project policy: project-target setup must not silently replace a global `~/.pi/agent/bin/pi-flow` shim with a project-specific runner. If project setup does not create the global shim, it should leave clear user-facing guidance when `pi-flow` is unavailable on PATH.
- Update docs so users know when to run `/flow:setup --target user` versus project setup and how to recognize/resolve shim conflicts.

Out of scope:

- Redesigning bundled agent discovery.
- Changing every skill to use `node node_modules/pi-flow-core/bin/pi-flow.mjs` fallbacks.
- Replacing unrelated existing `~/.pi/agent/bin/pi-flow` files or symlinks automatically.
- Adding npm `preinstall`, `install`, `postinstall`, or `setup` scripts.

### Suggested Fastlane checklist

1. Add failing tests for helper shim creation, idempotent skip, real-file conflict, divergent-symlink conflict, and project-target non-overwrite behavior.
2. Implement the explicit user-scope shim setup for `~/.pi/agent/bin/pi-flow` pointing at this package's `bin/pi-flow.mjs`.
3. Ensure project-target setup preserves existing global shims and reports clear guidance instead of silently replacing them.
4. Update `/flow:setup` notifications and docs to mention both bundled agent links and the helper-runner shim.
5. Run the targeted setup tests plus `pnpm --filter pi-flow-core run check`.

## Acceptance Sketch

- After installing `pi-flow-core` through a Pi package source that does not expose npm `bin` entries, running the explicit setup/bootstrap path makes `command -v pi-flow` succeed inside Pi bash/tool execution contexts.
- First helper calls in packaged skills such as `generate-plan`, `execute-plan`, `fastlane`, and `refine-code` no longer fail with `pi-flow: command not found` after setup.
- User/global setup creates or verifies `~/.pi/agent/bin/pi-flow` and reports `created`, `skipped`, or `conflict` consistently with existing agent-link reporting.
- Project-target setup does not unexpectedly replace another install's global helper runner.
- Existing `/flow:setup` agent symlink behavior remains unchanged and the setup/dispatch smoke test continues to pass.
- Tests cover shim missing/skipped/conflict behavior and project-vs-user behavior.
- Documentation describes the explicit setup path, conflict handling, and the relationship between npm `bin`, the `~/.pi/agent/bin` shim, and the direct `node <package>/bin/pi-flow.mjs` fallback.

## Open Questions

- Should the shim always be a symlink, or should setup create a tiny wrapper script on platforms where symlinks are unreliable? Prefer symlink first unless tests or Pi runtime constraints show a wrapper is needed.
- For project-target setup, should the command only warn when `pi-flow` is missing from PATH, or should it offer an explicit follow-up instruction such as `Run /flow:setup --target user to install the global helper-runner shim`?
