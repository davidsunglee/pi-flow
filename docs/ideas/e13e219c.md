## Remaining problem

`pi-flow` skills invoke helpers as `pi-flow helper ...`, but Pi package loading (especially Git package installs such as `pi install git:...`) does not necessarily expose the package's npm `bin` entry on the shell `PATH` used by Pi tools/subagents.

Observed/expected failure shape:

```text
/bin/bash: pi-flow: command not found
```

The runner itself exists and works when invoked directly, for example:

```sh
node <installed-pi-flow-core>/bin/pi-flow.mjs ...
```

Pi prepends `~/.pi/agent/bin` to PATH, so a stable wrapper or symlink there is a likely bootstrap point.

## Correct scope

This todo is now **only about making the `pi-flow` helper runner available on PATH** for Pi package installs where npm `bin` entries are not exposed.

It is **not** about bundled agent discovery anymore:

- Agent symlinks are generally necessary for package-bundled `agents/*.md`, not just Pi Git installs.
- That broader agent-discovery problem is now handled by `/flow:setup`, which links bundled `pi-flow-core/agents/*.md` into the `pi-interactive-subagent` discovery directory.
- `packages/pi-flow-core/__tests__/setup-dispatch-smoke.test.mjs` covers the real setup/discovery/dispatch seam.

## Candidate direction

Extend `/flow:setup` or an equivalent explicit bootstrap path so the helper runner is available as `pi-flow` in Pi's tool shell.

Likely behavior:

- Create or verify a conflict-safe symlink/wrapper such as:

  ```text
  ~/.pi/agent/bin/pi-flow -> <this pi-flow-core package>/bin/pi-flow.mjs
  ```

- Keep the behavior explicit, idempotent, and safe:
  - missing entry → create it
  - already points to this package's runner → report `skipped`
  - real file or divergent symlink → report `conflict`, do not overwrite silently
- Avoid hard-coded user-specific paths; derive the installed package root at runtime.

## Scope decision to make before implementation

Decide how project-target `/flow:setup` should treat the global `~/.pi/agent/bin/pi-flow` shim.

Safer first-pass policy:

- user/global setup may create the `~/.pi/agent/bin/pi-flow` shim
- project setup should not silently replace a global shim with a project-specific runner
- project setup may warn with clear instructions if `pi-flow` is unavailable on PATH, or require an explicit user/global setup step

## Acceptance criteria draft

- After installing pi-flow through a Pi package source that does not expose npm `bin` entries (especially Git installs), running the explicit setup/bootstrap path makes `command -v pi-flow` succeed inside Pi bash/tool execution contexts.
- First helper calls in packaged skills such as `generate-plan`, `execute-plan`, `fastlane`, and `refine-code` no longer fail with `pi-flow: command not found`.
- The solution is robust across Git installs, npm/package installs, and local development installs.
- The symlink/wrapper behavior is idempotent and conflict-safe.
- Project-vs-user behavior is documented and tested so one project's setup does not unexpectedly replace another install's global helper runner.
- Existing `/flow:setup` agent symlink behavior remains unchanged and continues to pass the setup/dispatch smoke test.
