## Context

Recent pi-flow development exposed a dev-environment maintenance problem: workflow code and docs from the current checkout can be used in the same session where command shims and package symlinks still resolve to an older installed pi-flow package. The visible symptom can look like a workflow or subagent bug, but the core issue is version skew across the pi-flow project setup: `pi-flow` shims, package symlinks, project-local `.pi` configuration, and installed package copies can point at different versions or different source trees.

This is especially confusing for self-hosted workflow development, where the active skill instructions may reference helpers or templates that exist in the checkout, while `pi-flow helper ...` resolves through a stale user-level shim under `~/.pi/agent/bin` / `~/.pi/agent/npm`.

## Goal

Make pi-flow development environments self-consistent: every shim, symlink, and project-local override associated with a pi-flow project should resolve to the intended package version or source tree, and updates should repoint those links predictably.

## Scope

- Inventory the shims, symlinks, and project-local settings that affect pi-flow resolution, including `~/.pi/agent/bin/pi-flow`, user-level npm installs under `~/.pi/agent/npm`, project `.pi` installs, package `node_modules/.bin` entries, and `{project}/.pi/agent/settings` overrides.
- Define version-selection semantics:
  - when an explicit version is configured, all managed links should point to that exact version;
  - when no explicit version is configured, updates should track the latest installed/upgraded version;
  - local development overrides should point to the intended checkout/package path and should not be silently shadowed by stale user-level installs.
- Add a setup/update/doctor path that detects and repairs stale or inconsistent pi-flow shims/symlinks.
- Ensure project-specific overrides in `{project}/.pi/agent/settings` are included in validation and point to the correct local or versioned package location.
- Document the expected maintenance workflow for upgrading pi-flow, pinning a version, and using a local checkout for pi-flow development.

## Acceptance Sketch

- A diagnostic command reports every relevant pi-flow shim/symlink/settings path, the resolved realpath, and the package version/source tree it points to.
- The diagnostic fails clearly when active skill/helper/template resolution can come from different pi-flow versions.
- An update or repair command repoints managed shims and symlinks according to the configured version policy.
- Explicit version pins remain pinned after update/repair; unpinned setups move to the latest upgraded version.
- Project-local override settings are validated and either point at the intended local checkout/package path or produce actionable repair guidance.
- Documentation explains how to verify which pi-flow version a session is using and how to keep user-level and project-level links aligned.

## Open Questions

- Where should the source of truth for an explicit pi-flow version pin live: user settings, project settings, package metadata, or a dedicated pi-flow config file?
- Should repair be automatic during upgrade/setup, or should it require an explicit doctor/fix command?
- How should the tool distinguish an intentional local checkout override from an accidentally stale symlink into an old checkout or package install?
- Should this belong in pi-flow itself, pi package setup infrastructure, or pi’s broader extension/package manager?
