## Context
`execute-plan` and related workflows rely on the shared four-input `test-runner` dispatch contract in `packages/pi-flow-core/skills/_shared/test-runner-dispatch.md`. In this environment, `agent=test-runner` still resolves through `crossProviderModelTiers.cheap` to Codex:

```json
{"model":"openai-codex/gpt-5.4-mini","cli":"codex","provider":"openai-codex","tier":"crossProviderModelTiers.cheap","executionPolicy":"unrestricted"}
```

The original failure mode was a malformed shortened artifact from Codex-backed `test-runner` runs. The subagent ran the supplied command, but wrote only:

```text
PHASE: <phase>
FAILING_IDENTIFIERS:
NON_RECONCILABLE_FAILURES:
```

That omitted required parser headers/markers (`COMMAND`, `WORKING_DIRECTORY`, `EXIT_CODE`, `TIMESTAMP`, count fields, end markers, and the raw-output delimiter), and `parse-test-runner-artifact.py` correctly rejected it with `header_missing`.

Fresh evidence from the `execute-plan` run for `docs/plans/2026-06-10-create-one-combined-implementation-spec-for-idea-99deb337.md` changes the picture. Codex-backed `test-runner` produced parser-valid full artifacts for baseline, wave 1, wave 2 retry, and final gate. That suggests the shortened-artifact failure may have been caused or amplified by stale runtime / identity-delivery issues.

However, the same run exposed a second reliability failure: `wave-2-attempt-1` produced a parser-valid artifact with `EXIT_CODE: 0`, `FAILING_IDENTIFIERS_COUNT: 0`, and no stable failures, but also set `NON_RECONCILABLE_COUNT: 1` and copied the entire passing test output into `NON_RECONCILABLE_FAILURES`. Reconciliation therefore blocked the gate even though the suite passed. A debugger pass diagnosed this as false-positive artifact classification by the `test-runner` subagent; a fresh `wave-2-attempt-2` test-runner dispatch produced the expected clean artifact (`NON_RECONCILABLE_COUNT: 0`) without code changes.

So the unresolved problem is no longer only “Codex may write a shortened artifact.” It is broader: Codex-backed `test-runner` artifact generation and failure classification are not yet deterministic enough for workflow gates. Parser strictness remains correct, and the orchestrator must not run the configured test command or synthesize artifacts itself.

## Goal
Make `test-runner` artifact production reliable when `test-runner` resolves to Codex, or intentionally route protocol-heavy `test-runner` work away from Codex with documented and tested dispatch policy.

The solution must preserve the workflow boundary:

- Integration test commands are executed by `test-runner` subagents.
- Artifacts are accepted only after validation by `pi-flow helper _shared/parse-test-runner-artifact` and reconciliation helpers.
- The orchestrator never runs the configured test command itself and never synthesizes a test-runner artifact from local output.

## Scope
1. **Runtime and prompt-delivery verification**
   - Verify the active `pi-flow` shim/version and loaded `@aphotic/pi-mux-subagents` runtime are aligned to intended current source/package versions.
   - Confirm Codex receives the full `test-runner` agent identity/body and dispatched prompt in both pane and headless paths, including the artifact format and stable/non-reconcilable classification rules.

2. **Live Codex smoke coverage**
   - Re-run a Codex-backed `test-runner` smoke using `crossProviderModelTiers.cheap`.
   - Validate the artifact with `parse-test-runner-artifact.py` and reconcile it against an empty/known baseline.
   - Include both a passing command and a command with a known stable test failure or known non-reconcilable failure so classification behavior is exercised, not just header formatting.

3. **Artifact-generation and classification hardening**
   - Prevent shortened artifacts and false non-reconcilable blocks.
   - Prefer a deterministic helper/wrapper callable by the `test-runner` subagent that accepts structured inputs, runs the supplied command, captures combined output/exit code, and writes the parser-valid artifact.
   - If a helper is not chosen, simplify and localize the artifact/classification instructions enough that Codex reliably emits:
     - all required headers/markers exactly once and in order,
     - stable identifiers only under `FAILING_IDENTIFIERS`,
     - true non-reconcilable evidence only under `NON_RECONCILABLE_FAILURES`, and
     - `NON_RECONCILABLE_COUNT: 0` for clean passing runs.

4. **Dispatch-policy fallback**
   - If Codex cannot reliably satisfy the protocol, add an intentional non-Codex dispatch policy for `agent=test-runner`.
   - Document and test the policy so `test-runner` does not silently inherit an unreliable generic cheap cross-provider tier.

5. **Caller surfacing**
   - Ensure execute-plan/fastlane callers surface malformed artifacts or suspect non-reconcilable classification clearly, with parser JSON/detail plus transcript/artifact paths when available.
   - Avoid loops that treat subagent process success as protocol success when artifact validation or reconciliation failed.

Out of scope:

- Weakening `parse-test-runner-artifact` to accept partial artifacts.
- Moving test execution into the orchestrator.
- Synthesizing artifacts in the orchestrator from locally run output.

## Acceptance Sketch
- Runtime alignment is explicitly verified before judging current Codex behavior (`pi-flow` shim realpath/version and relevant `@aphotic/pi-mux-subagents` source/version match the intended runtime).
- Codex-backed `test-runner` smoke runs produce parser-valid artifacts containing, in order when a phase is present:

```text
PHASE: <phase>
COMMAND: <command>
WORKING_DIRECTORY: <working directory>
EXIT_CODE: <integer>
TIMESTAMP: <ISO-8601 UTC timestamp>
FAILING_IDENTIFIERS_COUNT: <N>
FAILING_IDENTIFIERS:
...
END_FAILING_IDENTIFIERS
NON_RECONCILABLE_COUNT: <M>
NON_RECONCILABLE_FAILURES:
...
END_NON_RECONCILABLE_FAILURES

--- RAW RUN OUTPUT BELOW ---
<full raw output>
```

- For a clean passing command, the parsed/reconciled result has:
  - `exit_code: 0`,
  - `failing_identifiers: []`,
  - `non_reconcilable_failures: []`,
  - `current_non_baseline_stable: []`, and
  - `current_non_reconcilable: []`.
- For a known stable failure, only stable suite-native identifiers appear in `FAILING_IDENTIFIERS`; no full-output dump appears in `NON_RECONCILABLE_FAILURES`.
- For a known true non-reconcilable failure, the non-reconcilable entry is scoped to the relevant crash/build/collection evidence rather than the entire run output.
- Regression coverage exists for:
  - Codex prompt/identity delivery of the `test-runner` artifact contract,
  - parser rejection of shortened artifacts,
  - clean passing runs not being classified as non-reconcilable,
  - caller surfacing of malformed artifacts and reconciliation failures, and
  - any intentional non-Codex dispatch policy for `agent=test-runner`.
- `execute-plan` baseline/post-wave/final-gate test-runner dispatches can proceed without protocol failure or false non-reconcilable gates under the chosen policy.

## Open Questions
- Was the original shortened-artifact failure fully caused by stale runtime / missing Codex identity delivery, or can it still reproduce with aligned current runtime?
- What caused `wave-2-attempt-1` to classify an entirely passing run as one non-reconcilable failure while `wave-2-attempt-2` classified the same suite cleanly?
- Should artifact writing/classification move to a deterministic helper callable by subagents, rather than relying on LLM-authored artifact text?
- Should protocol-heavy agents such as `test-runner` have provider preferences/exclusions separate from generic tier resolution?
- If a parser-valid artifact has internally suspicious classification (for example `EXIT_CODE: 0`, no failing identifiers, and a huge full-output non-reconcilable block), should callers stop immediately, retry once with a stronger prompt, or route through debugger-first flow?
