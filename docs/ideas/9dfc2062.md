## Context
While executing `docs/plans/2026-06-03-f5ddba6d.md` with the `execute-plan` skill, Step 7 baseline capture dispatched the `test-runner` subagent using the resolved model tier `crossProvider.cheap`, which resolved to `cli: codex`, `model: openai-codex/gpt-5.4-mini`.

The Codex-backed test-runner ran the test command successfully multiple times:

```bash
pnpm --filter @aphotic/pi-flow-ux test
```

The package tests passed each time. However, Codex wrote an invalid shortened artifact to:

```text
docs/test-runs/2026-06-03-f5ddba6d/baseline.log
```

The malformed artifact shape was approximately:

```text
PHASE: baseline
FAILING_IDENTIFIERS:
NON_RECONCILABLE_FAILURES:
```

It omitted required `test-runner` artifact fields and markers, including:

```text
COMMAND:
WORKING_DIRECTORY:
EXIT_CODE:
TIMESTAMP:
FAILING_IDENTIFIERS_COUNT:
END_FAILING_IDENTIFIERS
NON_RECONCILABLE_COUNT:
END_NON_RECONCILABLE_FAILURES
--- RAW RUN OUTPUT BELOW ---
```

As a result, the orchestrator-side parser rejected the artifact:

```bash
BASELINE=$(cat /tmp/f5ddba6d-baseline-mtime.txt)
printf '%s\n' 'TEST_RESULT_ARTIFACT: /Users/david/Code/pi-flow/docs/test-runs/2026-06-03-f5ddba6d/baseline.log' \
  | pi-flow helper _shared/parse-test-runner-artifact \
      --artifact /Users/david/Code/pi-flow/docs/test-runs/2026-06-03-f5ddba6d/baseline.log \
      --final-message - \
      --expected-path /Users/david/Code/pi-flow/docs/test-runs/2026-06-03-f5ddba6d/baseline.log \
      --freshness-baseline "$BASELINE"
```

Parser failure:

```json
{"failure": "header_missing", "artifact": "/Users/david/Code/pi-flow/docs/test-runs/2026-06-03-f5ddba6d/baseline.log", "detail": "expected 'COMMAND', got 'FAILING_IDENTIFIERS:'"}
```

Adding an extra `systemPrompt` reminder containing the exact required artifact header order did not fix Codex behavior; it still wrote the shortened artifact.

A manual fallback dispatch of the same `test-runner` task with `cli: claude`, `model: anthropic/claude-haiku-4-5` completed and emitted the expected artifact marker. This suggests the problem is specific to Codex subagent adherence or tool behavior, not the test command itself.

Current relevant files/protocols:

- Test-runner agent definition: `/Users/david/.pi/agent/agents/test-runner.md`
- Shared dispatch contract: `packages/pi-flow/node_modules/@aphotic/pi-flow-core/skills/_shared/test-runner-dispatch.md`
- Prompt template: `/Users/david/.pi/agent/npm/node_modules/@aphotic/pi-flow-core/skills/_shared/test-runner-prompt.md`
- Parser helper: `pi-flow helper _shared/parse-test-runner-artifact`
- Model dispatch helper: `pi-flow helper _shared/resolve-model-dispatch --tier crossProvider.cheap --agent test-runner`

Observed resolved test-runner dispatch:

```json
{"model": "openai-codex/gpt-5.4-mini", "cli": "codex", "provider": "openai-codex", "tier": "crossProvider.cheap"}
```

The broader execute-plan issue: the orchestrator repeatedly saw successful subagent exits but invalid artifacts. This creates a confusing loop where the test command passes but the execute-plan protocol cannot proceed. The orchestrator should not treat Codex subagent completion as sufficient when artifact validation fails, and ideally Codex test-runner artifacts should be made valid in the first place.

## Goal
Make Codex-backed `test-runner` subagents reliably produce artifacts accepted by `pi-flow helper _shared/parse-test-runner-artifact`, or prevent `test-runner` from resolving to Codex until that reliability exists.

The fix should preserve execute-plan's boundary: integration test commands are still run by `test-runner` subagents, not by the orchestrator directly, and artifacts are still validated by the existing parser before baseline/reconcile state is trusted.

## Scope
Investigate and implement one or more of the following, based on codebase reality:

1. **Prompt/agent hardening for Codex**
   - Adjust `test-runner.md` and/or `_shared/test-runner-prompt.md` so Codex reliably writes the full artifact format.
   - Consider making the artifact format harder to summarize away, e.g. minimal explicit skeleton with all required lines, repeated near the final task, or instruction to generate artifact via a script.

2. **Tool-assisted artifact generation**
   - Add or use a helper that `test-runner` subagents can invoke to create a valid artifact from structured inputs (`phase`, `command`, `working_dir`, `exit_code`, `timestamp`, identifiers, non-reconcilable entries, raw output).
   - This would reduce reliance on the model manually formatting the artifact.
   - Ensure it is still the subagent that runs the test command and writes the artifact, preserving execute-plan's integration-test boundary.

3. **Codex-specific dispatch policy**
   - If Codex cannot be made reliable for this protocol, change model tier configuration or dispatch resolution so `agent=test-runner` does not select `cli: codex` for `crossProvider.cheap`.
   - A safer fallback observed in this session was `cli: claude`, `model: anthropic/claude-haiku-4-5`.
   - Any policy change should be documented and tested.

4. **Better orchestration surfacing**
   - When a `test-runner` artifact is malformed after a successful subagent exit, surface the parser failure clearly instead of repeatedly redispatching without explanation.
   - Retain existing parser strictness; do not synthesize an artifact from orchestrator-run output.

Out of scope:

- Weakening `parse-test-runner-artifact` to accept partial artifacts.
- Having the execute-plan orchestrator run the configured test command itself.
- Synthesizing test-runner artifacts in the orchestrator from local command output.

## Open Questions

- Should `test-runner` artifact writing be moved to a deterministic helper callable by subagents?
- Should `crossProvider.cheap` ever resolve to Codex for protocol-heavy agents like `test-runner`, or should such agents prefer providers with stronger instruction adherence?
- Where is the best place to encode agent-specific provider exclusions or preferences: `model-tiers.json`, `resolve-model-dispatch`, agent frontmatter, or execute-plan dispatch logic?
- How should execute-plan retry malformed artifacts: automatic one-shot retry with stronger prompt, immediate user-visible protocol error, or provider fallback?
